# Transaction crash recovery

File-backed statement transactions, explicit transactions and physical shrinking use `PersistentRollbackJournal` in addition to the pager's in-process undo log. The persistent journal stores raw bytes, so encrypted database pages remain encrypted. Non-file streams retain in-process rollback only.

## Write ordering

1. Before the first physical statement spill or final commit write, create `<database>.jdw-journal.preparing` under exclusive database coordination. Copy the complete original database with bounded buffers, record its length and SHA-256, and flush the completed header and snapshot to disk. Close it, promote it by a non-overwriting adjacent rename to `.jdw-journal`, then reopen the published journal before permitting writes. An existing final journal is never overwritten. An abandoned preparation file authorizes no writes: recovery and readers ignore it, and the next preparation replaces it.
2. Before each physical page write, append its aligned offset and encoded after-image with a SHA-256 checksum, then flush the journal to disk. A page can have several recorded versions across statement spills. Before truncation, append and flush a record with the intended retained length. Physical shrinking prepares the snapshot before secure tail erasure and records each encoded erase image through the same write path.
3. After every database page is written, flush the database to disk. Append a commit record containing the SHA-256 of the complete committed file and flush that decision before removing the sidecar.
4. For in-process rollback, detach intent recording, restore the original bytes and length, flush the database, record a terminal decision containing the restored file hash, then remove the journal. Before restoring a truncated tail, flush a recovery-start record that authorizes the zero-filled gaps a partial re-extension can expose. Original bytes are already authorized by the snapshot, so undo needs no additional intent records.

A failure while recording the commit decision has an uncertain outcome. The writer faults and leaves the database and journal available for recovery rather than starting rollback behind a potentially durable commit record. Cleanup failure after a completed durable decision does not turn a successful commit into a rollback. Each completed journal attempts cleanup once; disposing it again cannot delete a later transaction's journal. Journal creation failure faults the writer; live preparation failures attempt to remove their unused sidecar without masking the original error.

The existing pager and store gates serialize journal creation, raw intent recording and physical writes. Existing cooperative commit/page locks remain in place. File statement commits request durable flushes even when `UseTransactionalWrites` is false.

## Validation and recovery

Writer open recovers before reading database headers or checking passwords. A journal has a fixed 128-byte header, the original raw snapshot and fixed-size intent records. Header, snapshot and records have independent checksums. Only 2 KiB and 4 KiB pages are accepted; database length is capped at 2 GiB and journal length at 16 GiB. Buffers are bounded independently of lengths supplied by the journal.

Recovery validates the header, original snapshot, every complete record, full-path identity and current database before writing any recovery bytes. For an undecided transaction, the current length must be between the smallest authorized retained length (the original length if no truncation was recorded) and the largest authorized write end. Before recovery starts, a shortened file must match an exact recorded truncation target; intermediate restored lengths are accepted only after the recovery-start record. Each current byte must equal the original byte or a recorded version for the same page. This permits torn writes and a recovery that was interrupted after restoring only some original bytes. Bytes on untouched pages must match the snapshot. After a validated recovery-start record, zero bytes are also permitted within the authorized removed tail so recovery can restart after a partial re-extension; the retained prefix still requires original or recorded bytes. An incomplete final intent is ignored because it could not authorize a database write; a complete record with an invalid checksum is refused.

A valid final commit or rollback decision must match the complete current database hash; recovery then keeps those bytes and removes the stale journal. Otherwise a fully validated undecided journal records recovery-start authorization when needed, restores the original bytes and length, flushes the database, records its terminal hash and removes the journal. Repeating recovery after an interruption is safe because restored bytes still match the original snapshot and authorized tail gaps can be restored again. Before appending a recovery or terminal record, an incomplete trailing record is removed so records remain aligned. Invalid final journals and conflicting content are retained and refused without replay. A complete snapshot promoted before a crash can be recovered even if no database write has started; a crash during staging leaves the original database untouched. A truncated final snapshot is corruption and is refused.

After successful journal recovery, an abandoned `.ldb` or `.laccdb` is removed only if it can be opened exclusively. This cleanup precedes journal deletion: if another holder or an I/O failure prevents lockfile cleanup, the validated terminal journal remains available for a later writer-open retry. Invalid recovery evidence never authorizes lockfile cleanup. Ordinary opens still respect existing lockfiles. Recovery and lockfile removal are distinct from successful password validation.

## Access and identity

Path writers request `FileShare.None`. Path readers restrict sharing to `FileShare.Read` (or the caller's stricter choice) and reject pending journals before parsing. Caller-supplied file readers acquire a second read-only lease; conflicting supplied handles are refused. These lifetime sharing rules prevent a pre-existing reader from mixing cached pages with interrupted writes by a cooperating writer. Windows enforces sharing; Unix and arbitrary caller streams require cooperating access. A caller-supplied writer stream must exclude all other readers and writers throughout its lifetime.

Identity combines the full database path (case-normalized on Windows) with validation of all raw contents. It is not an operating-system file ID: byte-identical replacement at the same path is indistinguishable, and path aliases are not a recovery discovery mechanism. Preserve the original path, the database and its journal together; do not move, replace or independently edit them while recovery is pending. Checksums detect damage, not deliberate replacement by an attacker who can rewrite both journal data and checksums. Recovery assumes exclusive access to trusted local journal files.

Microsoft Access has no knowledge of this sidecar. After a crash, recover through `AccessWriter` before letting Access or another program open the file.

## Costs and boundaries

A transaction copies the entire original database and hashes the committed file. Journal storage adds a raw after-image record for each physical page write, and each record requires a flush. Grouping mutations into one explicit transaction amortizes the initial snapshot. File shrinking also takes a complete snapshot. Ordinary intents reserve space for recovery-start and terminal records within the journal size bound. Recovery uses bounded memory but can rescan all intents for each changed page. Selective before-images and faster validated recovery remain performance work.

The process-crash protocol does not establish power-loss atomicity: creating or deleting the journal changes directory entries, and this implementation does not flush the containing directory. On Linux, a file `fsync` alone does not guarantee its directory entry; a separate directory flush is required ([Linux fsync documentation](https://www.man7.org/linux/man-pages/man2/fsync.2.html)). Windows file flushing pushes buffered data toward the device, but filesystem and storage ordering still require separate verification ([Microsoft file flushing documentation](https://learn.microsoft.com/en-us/windows/win32/fileio/flushing-system-buffered-i-o-data-to-disk)).

Path-based database creation initializes a unique adjacent private staging file, disposes its initialization writer, flushes the completed file to disk, and publishes it with a non-overwriting move. Failures before publication clean up only owned staging artifacts. A failure opening the published database retains the completed file. A process crash before publication may leave an unused staging file. Encryption replacement retains a flushed original backup through its replacement boundaries. These namespace operations still have the power-loss boundary described above. Non-file streams retain in-process undo; no explicit persistent journal-stream API is provided.

## Regression evidence

`PersistentRollbackJournalTests` exercises torn writes, partial final records, multiple page versions mixed with partial undo, interrupted recovery replay followed by repeated reopen, authorized truncation and zero-filled tail restoration, corrupt headers/snapshots/records, checksum-valid wrong paths and offsets, invalid lengths, stale commit decisions, incomplete final snapshots, abandoned staging and Windows path casing. `TransactionCrashRecoveryTests` kills a child process without disposal during statement spills and final commit writes, then compares recovered files byte for byte. It also kills after successful commit and compares against an independently committed image. `ShrinkCrashRecoveryTests` kills during secure tail erasure, after truncation and after successful shrink, comparing plain and encrypted databases with exact original or committed images. `ReplacementCrashRecoveryTests` kills a child process after backup preparation, replacement and the final file flush, then verifies complete destination and original backup images. `CreationCrashRecoveryTests` kills during partial initialization, after the staging file is flushed and after publication, checking absent or byte-exact complete destinations for plain and encrypted creation and preserving competing files. `RecoveryLockFileTests` retains a completed recovery journal while lockfile cleanup is refused, then verifies exact-byte recovery on retry; invalid evidence preserves the lockfile. Completed-journal disposal regressions verify that cleanup cannot delete a successor journal. These checks cover process termination, not power interruption or Access-native recovery.
