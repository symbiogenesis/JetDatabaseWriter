## What the five commits fixed
- **The service-locator problem is gone.** Nothing outside the facades takes `AccessWriter`, `AccessReader` or `AccessBase` any more. `WriterServices` and `ReaderServices` now wire everything explicitly, the two dependency cycles are removed, and `ServiceGraphTests` guards this.
- **Duplicate code was merged:**
  - one `TableCatalog` replaces the two `GetUserTablesAsync` copies;
  - the shared index-descriptor helpers live on `IndexCatalogReader`;
  - the row primitives exist only in `TableRowStore`;
  - `AccessWriter` no longer has its own snapshot copies.
- **The row decoders no longer depend on the reader facade.** `RowDecoder` and `LongValueDecoder` now take `DatabaseFile`, and `ReaderPageCache` reads straight through to pending transaction writes when one is active. That makes the main fix below cheap.
- **The concurrency doc now gives the correct `UseTransactionalWrites` default.**
- **No new defects, apart from one small one, now fixed.** A before/after comparison over all 92 test databases found identical results. The only change was that the "Total rows scanned" diagnostic also counted catalog rows it couldn't decode (25 became 28 on one fixture). It affected only the diagnostic text; see "Fixed since 6eab703". The 28 later turned out to be right; see the row-bound entry.

## Fixed since 6eab703
- **Bug 1: a large MEMO dropped the rows after it on the same data page.** One ~1.4 MB MEMO row plus 29 small rows made `Rows()` return 1 of 30 rows. `ReaderPageCache` gave evicted pages back to the shared pool while a scan still read them, so the next page read overwrote the scan's data page. The read-ahead guards that worked around this bug have since been re-evaluated; see the read-ahead entry at the end of this section.
- **Bug 3: any commit on a Jet4 `.mdb` made it reopen as ACCDB.** `TransactionLifecycle.CommitTransactionAsync` incremented page-0 offset `0x14` after every commit, treating it as a "commit lock byte". - **Bugs 2, 5, 6, 7 and 8: the writer's reads inside a transaction did not see the transaction's own writes.** Every workflow that reads a table before changing it (update, delete, cascades, full index rebuilds, AddColumn/DropColumn/RenameColumn, AutoNumber seeding, unique checks and relationship enforcement) decoded rows through `TableSnapshotReader`. That class opened a separate uncached `AccessReader` with no journal, and the writer paired its rows by position with row locations read through the journal. So a delete then an update in one transaction rewrote the wrong row, AddColumn dropped the rows inserted earlier in the transaction, a relationship created in the transaction was not enforced, and a cascade delete under `UseTransactionalWrites` left the child's primary-key and foreign-key indexes pointing at the wrong rows. - **Dropping a table in a relationship left its partners pointing at a freed page.**
  - The bug. `DropTableAsync` never looked at relationships. The public API had no way to remove it. `RelationshipManager.CaptureForRewriteAsync` now keeps only entries whose partner links back (`PartnerLinksBackAsync`): another FK entry whose `rel_tbl_page` and `rel_idx_num` name this table and this entry, as on both sides of every writer-created relationship and every relationship in the Access fixtures. - **Jet3 rows longer than 256 bytes read back truncated or wrong, without an error, and the writer could not write them; on every format, a row too large for a data page appended an empty page and threw `ArgumentOutOfRangeException`.**
  - The format. A Jet3 (Access 97) row stores the EOD and each variable-column offset in one byte. A row longer than 256 bytes carries `(rowLength - 1) / 256` one-byte jump entries between the offset table and `var_len`. Each holds the index of the first offset at or past its 256-byte boundary, and an entry no offset reaches is a dummy (Access writes 0xFF). See mdbtools `mdb_crack_row3` and Jackcess `TableImpl.readJumpTableVarColOffsets`.

## Open: found while fixing
The Jet3 long-value bug and the UTF-8 text of new Jet3 databases, which were listed here, are fixed; see "Fixed since 6eab703". These were found while the follow-ups were investigated or fixed. Each says whether its fix is in progress, planned or waiting on evidence:
- **An update whose re-insert fails loses the row.** An update deletes the row and then inserts its new version, and if the insert throws, the delete stays. One way to hit it is an update that grows a row past one data page, which now throws `JetLimitationException`; the README says to use `UseTransactionalWrites` or a transaction for such updates. Planned with the write-atomicity work (wave 2).
- **The library's Jet4 RC4 and ACCDB legacy-password schemes may not be what Access writes.** No Access-authored encrypted Jet4 or legacy-password file is among the fixtures: AesEncrypted.accdb, which the legacy-password scheme was built from, turned out to hold no password (see the header-password entry), and mdbtools and Jackcess describe Jet RC4 differently. The writer reads and writes these schemes consistently, but whether Access opens its files, or the writer opens Access's, is unchecked. It needs Access-authored encrypted fixtures or a DAO run. The README's Encryption Support section, its feature table and the `AccessEncryptionFormat` docs now say so: Jet4 RC4, the ACCDB legacy password and ACCDB AES-128 (CFB-wrapped) are the library's own schemes, Access may not open their output, and none of the encrypted formats has been checked against a file Access encrypted. They no longer name Access versions for these schemes or describe `;pwd=` as an Access format.
- **A full index rebuild of a large index throws `NotSupportedException`.** `UsageMap.WriteInlineRow` writes an index's `used_pages` map only in the inline form, and throws "REFERENCE usage maps for index pages are not yet supported" when the rebuilt B-tree's pages span more than one inline bitmap window. The tooling benchmarks hit it twice: `CreateRelationshipAsync` over 20,000 Orders rows that already have two indexes, and the 338th `AddAttachmentAsync` on an 800-row table. Any table with a foreign-key index takes the full rebuild on every write, so a large child table can reach it. b2d6b49 fails the same way. Planned with the owned usage-map work (wave 2, pager-b).
- **`AddAttachmentAsync` and `AddMultiValueItemAsync` rebuild every index of the hidden flat table on each call, so adding items one at a time grows quadratically in time and file size.**
  - The cause. `ComplexColumnManager.AddComplexItemCoreAsync` inserts the flat row and then calls `MaintainIndexesAsync`, which is `RebuildIndexesAsync` without the written row. Each call decodes every live flat row and builds every flat-table index again. The trees it replaces are never freed, because `RebuildIndexesAsync` frees replaced index pages only for tables without long-value or complex columns, and never for flat tables.
  - Repro, measured on 2026-10-03 with a Release build on a shared Arm64 machine. Create an ACCDB table `Docs` (`Id` primary key, `Files` attachment) with 800 rows, then add one 1 KB attachment to each row, with no transaction.
    - Calls averaged 9.2 ms over the first 100 and 183 ms over the last 100.
    - The file grew from 196 KB to 23 MB, and 5,015 of its 5,860 pages were index pages.
    - The control: the same 800 1 KB values inserted into an indexed table, one `InsertRowAsync` each, took 1.4-2.8 ms per call throughout and left a 3.3 MB file with 14 index pages.
    - A 400-row fill threw the usage-map `NotSupportedException` above at call 256. Where it throws depends on where the rebuilt trees land: this 800-row run finished, and an earlier one threw at call 338.
  - The rebuilt trees, written at new pages on every call, are what reach that throw, which is why `Attachments_150_v1.accdb` stops at 150 rows. Writing REFERENCE usage maps would remove the throw, but not the rebuilds or the growth.
  - Fix: insert through `InsertRowDataLocAsync`, pass the row and its location to `TryMaintainIndexesIncrementalAsync` as `TableDataWriter`'s inserts do, and rebuild only when that bails. Not planned yet.
- **Dropping a table, or a complex column, leaves the hidden flat table's pages allocated.** `ComplexColumnManager.DropComplexChildrenForTableAsync`, which `DropTableAsync` calls, and `DropSingleComplexChildAsync`, which a schema rewrite calls for a dropped Attachment or multi-value column, delete only the `MSysComplexColumns` and `MSysObjects` rows. The flat table's TDEF, data, index and usage-map pages stay allocated until Compact & Repair, as the code's own comment says, while complex-columns-format-notes.md row C6 says they go back to the free list. Repro: on a new ACCDB, create `Docs` (`Id` primary key, `Files` attachment), insert a row and add one attachment, read the flat table's TDEF page from `GetComplexColumnsAsync("Docs")[0].FlatTableId` (36), then `DropTableAsync("Docs")`: the page keeps type 0x02 and `PageAllocator.IsPageFreeAsync` returns false. Found while fixing droptable-fk; `DropSingleComplexChildAsync` was read, not run. Not planned yet.

## Design flaw status
| Flaw | Status | What changed |
|---|---|---|
| Facade is the engine / service locator | **Partly resolved** | Locator and cycles are gone. `DatabaseFile` (about 1,470 lines, injected into about 35 types) is the new catch-all: pager, transaction journal, encryption and table-definition parsing in one class. |
| Reader and writer are separate engines | **Resolved** | The writer no longer opens a second `AccessReader` over its own file. `TableSnapshotReader` decodes through the shared `RowDecoder`, `LongValueDecoder` and `CatalogReader` over the writer's own `DatabaseFile`, so its reads see the transaction journal (bugs 2 and 5–8 fixed). Each decoded row comes back with its location (`LocatedRow`), so nothing pairs rows and locations by position any more. |
| No pager or buffer manager | Open, critical | The cache moved into `ReaderPageCache`, and its eviction bug (bug 1) is now fixed, so table-scan read-ahead no longer needs a cache of at least three pages. There is now one journal-aware end of file, `DatabaseFile.PageCount`, used by every page-number bound and every caller that numbers new pages (see the end-of-file entry above). The writer still has no page cache, and there are no page leases or pins. |
| Transactions not atomic | Open, critical | Rollback no longer breaks the writer: it restores the cached catalog, insert hint and constraint registry (bugs 10–11 fixed). Cancellation can no longer tear a commit, a commit that fails after it started writing pages is no longer reported as rolled back, and the docs now say commit writes in-memory after-images in place, which is not crash-atomic. The format-byte bump is fixed (bug 3). The writer's own reads inside a transaction now see its pending writes (bugs 2 and 5–8). Still no WAL or before-image, so a crash or I/O failure during replay tears the file, and no savepoints. |
| Schema isn't a model | Open | Three duplicate parsers merged. The index paths now read the whole TDEF chain and share `IndexCatalogReader.LocateRealIdxDescStart` instead of their own column-name walks, and in-place TDEF patches go through `LogicalTDefChain.WriteInPlaceAsync` (the wide-table fixes above). Schema rewrites now copy each column whole (`ColumnDefinition.WithName`), project indexes through one `IndexHelpers.ProjectIndexes` that keeps every flag, and carry the table's foreign-key indexes and partner links. `DropTableAsync` now refuses a table in a relationship and `RenameColumnAsync` rewrites the expressions that name the column (entries above), but there is still no in-process schema model. |
| No write pipeline or real B-tree | Open | Moved into `TableDataWriter`. Update and delete now change exactly the rows they decoded (`LocatedRow`), and updates run the NOT NULL, AutoNumber and rule checks on the columns they assign. Each operation still wires the insert, tombstone and index-maintenance primitives by hand, an update is still a delete plus re-insert, and the B-tree algorithms are unchanged apart from the multi-level rebuild reserving its pages through `PageAllocator` (end-of-file entry), every index path giving back a run it reserved but never linked, and a full single-leaf root growing into a tree instead of bailing (index page-run entry). |
| Constraints live in the process, not the file | **Partly resolved** | Every writer now loads the column `DefaultValue`, `ValidationRule` and `ValidationText` from `MSysObjects.LvProp` and enforces them, including those Access wrote, and a CLR `DefaultValue` applies after reopen. Inserts follow Access SQL for defaults: an explicit NULL stores NULL, and an omitted column or `DbDefault.Value` takes the default. A numeric CLR default, or one of the column's own type, stores the same value in every writer. Updates run the NOT NULL, AutoNumber and rule checks on the columns they assign (bug 4). A rollback restores the registry (bugs 10–11). AutoNumber seeding now reads the TDEF counter, so IDs are no longer reused across sessions or schema rewrites. Still open: a CLR `ValidationRule` delegate binds only the writer that declared it; expressions the calculated-column engine can't evaluate and table-level rules are skipped; and the registry still skips every check on a table whose constraint list doesn't line up with the TDEF column count. |
| Lossy value model | Open | Complex-column cells are no longer lossy: `Rows()` and the other row reads return every attachment, decoded, and every multi-value item, and version-history cells carry their `Modified` timestamps (see "Fixed since 6eab703"). Updates, cascades and schema rewrites no longer lose data either: the writer's snapshot carries OLE bytes exactly and refuses a MEMO or OLE value it cannot read instead of storing placeholder text. The OLE signature heuristic on the normal read path is unchanged. |
| Format knowledge scattered | Open | The TDEF header offsets (row count, AutoNumber counter, table type, column and index counts, usage-map pointers, and now the complex AutoNumber) live per format in `TDefHeaderLayout`, and the Jet4-only constants that corrupted Jet3 headers are gone. LVAL pages follow a per-format `LvalPageLayout`, which fixed Jet3 long values. The foreign-key index helpers read and write real-index descriptors, logical entries and name records through the per-format `IndexLayout` instead of Jet4's hard-coded offsets, which let the writer emit Jet3 foreign-key entries (index page-run entry). Elsewhere no change: files importing `JetTypeInfo` went from 35 to 40 in the five commits and are 41 now. |
| Read API doesn't compose | Open | Moved into `TableReader`. The read loops now agree on which rows they return, on `maxRows` and on calculated-column types (bug 12 and the drift fix above), but they are still separate loops with no shared scan primitive. `IndexRowReader` still returns nothing for linked tables (`ListIndexesAsync`, `EnumerateIndexRowsAsync`), `CatalogReader.ResolveTableAsync` still re-reads the TDEF uncached and rescans MSysObjects (for a system table, now through `CatalogRowReader`, which decodes every catalog row; see the overflow-row entry's performance follow-up), and unknown tables still read as empty, unlike the writer. |
| Encryption isn't a page layer | Open | Opening a file now reads only page 0 to detect flat Agile, and the writer refuses flat Agile instead of corrupting it. The cached AES page transforms now run under their own lock, so concurrent page reads on an AES file no longer fail. Flat Agile and the CFB Office Crypto formats are still decrypted whole into memory, and the writer still has no page cipher for flat Agile. |
| Failures aren't modeled | Open | `LastDiagnostics` is now built from a typed record internally. Index paths that silently skipped an index they could not parse now throw `JetLimitationException`, a MEMO or OLE value the writer cannot read refuses the write (`InvalidDataException`) instead of storing placeholder text, and a commit that fails after it starts writing is reported as neither committed nor rolled back. `JetLimitationException` is still the only custom exception type. |
| No CI; untested netstandard2.1 build | **Resolved** | `ci.yml` builds the solution in Release with every analyzer as an error and runs the suite on net10.0 and on net8.0, which loads the netstandard2.1 build, on every push to main and every pull request. A release tag publishes the package that run built and tested, versioned from the tag by MinVer, with package validation (CI parts 1–4). CI runs on Windows only. |
| LINQ layer has no mapping model | **Partly resolved** | It depends on reader services instead of the facade, which makes a package split easier. `EntityMap` is now the one mapping model: every typed path maps properties to columns through it, honouring `[Column]`, `[NotMapped]` and `[Table]`. There is still no query plan: reads compile materializers per call, `RowMapper` and `RuntimeRowMapper` coerce values differently, the IQueryable surface runs sync-over-async, the index walk builds a `List` instead of streaming, and nothing is annotated for AOT. |

## Suggested next steps
1. **Finish the follow-up fixes (wave 1, in progress).** Every follow-up was reproduced and given a fix plan, and the fixes are being made in sixteen groups. Each group lands with regression tests, as described in the intro. Already on main:
   - the Jet3 long values, the row-bound bug, overflow rows, the system-table lookup, reading and writing Jet3 rows longer than 256 bytes, and the one-page row-size limit;
   - encryption detection from the unmasked header password, the header `DecryptAsync` leaves, one open per `AccessWriter.OpenAsync(path)`, and the Jet3 header and code page of new databases;
   - `RenameColumnAsync` rewriting the expressions that name the column, `DropColumnAsync` refusing a column an expression names, and the check order of `CreateTableAsync` and `AddColumnAsync`;
   - `DropTableAsync` refusing a table in a relationship, as Access does, and schema rewrites dropping dangling FK entries;
   - defaults: an explicit NULL stores NULL and `DbDefault.Value` asks for the default, floating-point defaults are exact and the same in every writer, and generated columns take no default;
   - complex columns: index keys, references, the ComplexID counter, Access's attachment format, type names and version-history timestamps;
   - calculated-column result types and the expression semantics;
   - the index page-run release, the ACCDB 301-table limit and Jet3 foreign-key entries;
   - decimal columns: `ColumnDefinition.IsCurrency`, Jet3 decimal columns created as Currency, and the precision and scale of multi-value Decimal items;
   - the reader's cached `RandomAccess` handle, its synchronous file handle and inline page reads on thread-pool threads;
   - Access object-name validation, and scaffolder output that compiles for any table and column names;
   - the CI, publishing and versioning work, the dead-code removal and the missing benchmarks.

   For these, see the last entries of "Fixed since 6eab703". Still to land: the foreign-key check on updates that don't change the key, seen on Northwind (northwind-fk), and the relationship cache and the AutoNumber seed scan (perf-followups).
2. **Make every write atomic and crash-safe (wave 2).** Without a transaction, update and delete on a wide table written by an earlier build apply their row changes and then throw. A cascade update to two child tables can stop after the first (wide-table and OLE entries), and an update whose re-insert fails loses the row. This comes with the transactions design flaw:
   - statement-level savepoints;
   - a sidecar rollback journal, on by default for path-opened files, so a crash during commit can be rolled back;
   - recovery when the writer opens the file.
3. **Close the remaining design flaws (wave 2).** The plans for the twelve open rows of the table above are merged into one ordered roadmap. It starts with splitting `DatabaseFile` and a real pager, which also writes REFERENCE usage maps for large tables and large indexes, then write atomicity, the schema model, the write pipeline, read composition, encryption as a page layer, typed failures, the format profile and the LINQ query plan.

The per-claim results, with current file:line evidence and fix notes for all 14 flaws, are in `scratchpad\recheck.json` and `scratchpad\recheck-digest.md`.
