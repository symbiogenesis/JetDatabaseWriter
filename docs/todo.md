None of the bugs from my earlier report is fixed at `HEAD` (6eab703). The five commits fixed the code's structure, not its behaviour. I re-ran my four repros against a fresh build of `HEAD` and all four still fail. Re-checking the code also turned up nine more data-loss or corruption bugs, which I ran myself. The test suite passes (3,832 passed, 29 DAO tests skipped, as usual), but no test covers any of these bugs.

## What the five commits fixed
- **The service-locator problem is gone.** Nothing outside the facades takes `AccessWriter`, `AccessReader` or `AccessBase` any more. `WriterServices` and `ReaderServices` now wire everything explicitly, the two dependency cycles are removed, and `ServiceGraphTests` guards this.
- **Duplicate code was merged:**
  - one `TableCatalog` replaces the two `GetUserTablesAsync` copies;
  - the shared index-descriptor helpers live on `IndexCatalogReader`;
  - the row primitives exist only in `TableRowStore`;
  - `AccessWriter` no longer has its own snapshot copies.
- **The row decoders no longer depend on the reader facade.** `RowDecoder` and `LongValueDecoder` now take `DatabaseFile`, and `ReaderPageCache` reads straight through to pending transaction writes when one is active. That makes the main fix below cheap.
- **The concurrency doc now gives the correct `UseTransactionalWrites` default.**
- **No new defects, apart from one small one, now fixed.** A before/after comparison over all 92 test databases found identical results. The only change was that the "Total rows scanned" diagnostic also counted catalog rows it couldn't decode (25 became 28 on one fixture). It affected only the diagnostic text; see "Fixed since 6eab703".

## Fixed since 6eab703
- **Bug 1: a large MEMO dropped the rows after it on the same data page.** One ~1.4 MB MEMO row plus 29 small rows made `Rows()` return 1 of 30 rows. `ReaderPageCache` gave evicted pages back to the shared pool while a scan still read them, so the next page read overwrote the scan's data page. It now leaves evicted pages to the GC, and `LruCache` no longer has an eviction callback. `AccessReaderCacheTests.Rows_WhenLongValueChainEvictsCurrentDataPage_ReturnsEveryRow` covers it.
  - Follow-up: the read-ahead guards in `TableReader.ShouldReadAheadTablePages` (a cache of at least 3 pages, and no MEMO, OLE or complex columns) worked around this bug. They can probably be relaxed now, after benchmarking.
- **Bug 3: any commit on a Jet4 `.mdb` made it reopen as ACCDB.** `TransactionLifecycle.CommitTransactionAsync` incremented page-0 offset `0x14` after every commit, treating it as a "commit lock byte". That byte is the format version (0 = Jet3, 1 = Jet4, 2 or more = ACE), so two commits turned a Jet3 or Jet4 file into ACCDB, and every ACCDB commit changed its ACE version. `BumpCommitLockByteAsync` is gone, along with the tests that asserted the bump. The cooperative commit-lock byte-range sentinel is unchanged. `JetTransactionTests.Commit_PreservesPageZeroFormatVersionByte` covers Jet3, Jet4 and ACCDB.
- **Bug 9: a cancelled `InsertRowsAsync` left its rows on disk without index entries.** `TableDataWriter.InsertPreparedBatchAsync` ran its cleanup on the cancelled token, so the cleanup threw on its first page read and the rows written so far stayed live. A cancel could also land inside a single row's writes, after the data page and before the TDEF row count, leaving a row the cleanup never recorded. Cancellation is now checked only between rows. Each row write and the index maintenance after the loop run to completion once started, and the cleanup runs without a token. It now also swallows I/O failures, as its doc comment always claimed. `AccessWriterTests.InsertRows_CancelledWhileWritingRows_RollsBackBatch` and `InsertRows_CancelledDuringIndexMaintenance_CompletesBatch` cover it.
- **Bug 12: `ReadTableAsync<T>` returned no rows when `T` bound an Attachment or multi-value column.** `TableReader.ReadTableAsync<T>` had its own two scan loops (full map and projected). Neither resolves complex columns, so it skipped both whenever `T` bound one, then fell through to the linked-table lookup, which returns nothing for a native table. It now collects from `EnumerateMappedRowsAsync`, the same decoder choice `Rows<T>` streams from, and honours `maxRows`. The two private loops are gone. Separately, `Rows<T>` threw `InvalidCastException` ("Object must implement IConvertible") when an `object` property was bound to a `byte[]` or complex cell. `RowMapper.CoerceToTarget` now passes through any value the property can already hold, as `RuntimeRowMapper` does. `ReadSurfaceConsistencyTests.ReadTableGeneric_BoundAttachmentColumn_*` and `ReadTableGeneric_BoundMultiValueColumn_ReturnsSameRowsAsRowsGeneric` cover it.
  - Side effect: for a table with complex columns, `ReadTableAsync<T>` now loads the complex data and decodes every column even when `T` binds no complex column, as `Rows<T>` already did. The deleted projected loop skipped that work.
- **Drift between the `TableReader` read loops: counts, calculated columns and `maxRows` disagreed across APIs.**
  - `GetRealRowCountAsync` walked the raw row-offset table. It counted rows that every read skips because their layout doesn't parse, such as a row with a column count of 0, and `Query<T>().Count()` uses the same count. It also threw `ArgumentOutOfRangeException` on a data page whose row count runs past the page. It now uses the shared page enumerator and the cached live-row bounds, and counts only rows that the new `RowDecodePlan.CanDecodeRow` accepts, which is the same check the typed, string and direct decoders apply. This also fixes a real overcount in Access-produced files: delTestV2000.mdb and delTestV2003.mdb counted 2 rows where every read returns 1.
  - `ReadFirstTableAsStringsAsync` skipped the catalog's calculated-column result types, so a calculated Double read as `4.117213714E-315` instead of `83333.3333`. It now delegates to `ReadTableAsStringsAsync`.
  - `ReadTableAsStringsAsync` now also goes through `EnumerateTableScanPagesAsync`, and reports progress when it stops at `maxRows`.
  - `maxRows: 0` returned one row from every bounded read, native and linked text. It now returns none, and DataTables keep their columns.
  - `ReadSurfaceConsistencyTests` covers this on Jet3, Jet4 and ACCDB: `ReadApis_RowWithZeroColumnCount_AllSkipItAndAgreeOnCount` reads a zero-column-count row through all 10 APIs with read-ahead on and off, `ReadApis_DataPageRowCountPastPageCapacity_AgreeOnCount` uses an overfull row count, `ReadApis_MaxRowsZero_ReturnNoRows` checks `maxRows: 0`, and `ReadFirstTableAsStrings_CalculatedColumns_MatchesReadTableAsStrings` uses the calculated-column fixture. Two `LinkedTextTableTests` gain `maxRows: 0` checks.
- **"Total rows scanned" in `LastDiagnostics` counted catalog rows it could not decode.** `TableCatalog.ScanAsync` reported `rows.Count` from `CatalogRowReader.GetCatalogRowsAsync`, which returns a `CatalogRow` for every live `MSysObjects` slot, including rows too short or malformed to decode. `CatalogScanSummary` documents the value as the rows decoded. So indexTestV2003.mdb printed 28 instead of 25, and unsupportedFieldsTestV2007.accdb printed 38 instead of 35. `CatalogRow` now has an `IsDecoded` flag. `CatalogRowReader` sets it with the same skip rules as `RowDecodePlan.CanDecodeRow`: the row is shorter than the column-count field, has a column count of 0, or has a layout that does not parse. The scan counts only decoded rows, and also stops looking for user tables in undecodable ones, as the reader did before 60403d1. The user table list is unchanged on all 92 fixtures. Undecodable rows stay in the list, so `CatalogWriter`, `DataPageInserter` and `ComplexColumnManager` still see every live slot. `CatalogDiagnosticsTests.ListTables_Diagnostics_CountsOnlyDecodableCatalogRows` pins 25 and 35 on those fixtures, and `ListTables_Diagnostics_RowsScannedMatchesMSysObjectsRowCount` checks that the count equals the `MSysObjects` row count from the table reader on Jet3, Jet4 and ACE fixtures.
  - Follow-up: on Jet3 and Jet4 databases the writer creates, `ReadDataTableAsync("MSysObjects")` returns an empty table with no columns, because `MSysObjects` can't be found by name there. This predates the fix, and it is why the second test uses only Access-authored fixtures.
- **`Rows()` lost attachments and multi-value items, and attachments stayed compressed.** `ComplexColumnReader` read each flat child table as strings and joined it on the flat table's own AutoNumber key (`<table>_<column>`) instead of the `_<column>` back-reference to the parent's complex slot. Each parent got at most one attachment, chosen by AutoNumber rather than by owner, so a parent with two attachments showed one, rows with no attachments showed someone else's, and Access's zlib-compressed `FileData` came back still compressed. Multi-value and version-history cells were always DBNull. `GetAttachmentsAsync` had two bugs of its own. It read `FileData` through the OLE decoder, whose signature sniffing cuts off everything before a file magic it finds, for example `FF D8 FF` inside a raw jpg. And `AttachmentWrapper` only inflated raw deflate, so compressed attachments written by Access came back still compressed. Flat tables are now read through one typed path in `ComplexColumnReader` that returns OLE bytes as stored (`RowDecoder.EnumerateRawOleTypedRowsForTdefAsync`), and joined on the `_<column>` column. That column is matched by exact name first; the old "first Long starting with `_`" fallback now skips the flat table's AutoNumber, which also starts with `_` when the parent table's name does. The `Get*Async` APIs and the row cells share this path. A complex cell is still `byte[]`, and it now holds every attachment (decoded data, name, type, URL, timestamp) or every value of the parent row. The new public `ComplexCellValue.ReadAttachments` / `ReadMultiValueItems` decode it. A row with no items reads as DBNull, and `RowsAsStrings` / `ReadTableAsStringsAsync` return the cell as a base64 data URI instead of `__CX:N__`. `AttachmentWrapper.TryDecode` now accepts zlib bodies. A damaged `MSysComplexColumns` or `MSysObjects` is still traced rather than failing the read, and the scan falls back to finding the flat table by name. `ComplexColumnsRowReadTests` covers writer-created attachments, including a raw jpg containing a JPEG signature, and int and text multi-values, read through `Rows()`, `ReadTableAsync`, `Rows<T>`, `Rows<T>(predicate)` and the string paths. The same class tests the Access-authored complexDataTest, ComplexFields and Northwind fixtures. `ComplexColumnsRowApiTests.AttachmentWrapper_TryDecode_AcceptsAccessZlibWrappedBody` covers the zlib decode.
  - Follow-up: `ColumnMetadata.TypeName` still reports "Attachment" for every complex column, including multi-value and version-history columns. A version-history cell carries only the history text, not the flat table's `Modified` timestamp. The writer stores attachments as raw deflate with `dataLen` set to the compressed length, while Access writes zlib with the uncompressed length; whether Access reads the writer's attachments is unchecked.
  - Follow-up: a multi-value Decimal written as 12.34 reads back as 12 from both `GetMultiValueItemsAsync` and the cell, so the precision is lost in the write or decode path, not in the row read.
- **Opening a database read the whole file, and the writer opened flat-Agile files it could not write.** `EncryptionManager.TryDecryptAgileCompoundFileAsync` loaded the entire file into memory on every `AccessReader` open, only to look for a flat-Agile descriptor in page 0. A 3.17 MB file read 3.17 MB per open, a path-based writer open paid it again through its password check, and one `UpdateRowsAsync` read about 5× the file. The writer never checked for flat Agile, so it opened such a file, appended unencrypted pages to the AES-CBC encrypted file, and then failed with misleading errors. The probe now reads only page 0, through a shared `ReadHeaderPageAsync` that `DetectEncryptionFormatAsync` and the new `IsFlatAgileEncryptedAsync` also use, and reads the whole file only after it finds a flat-Agile header. A reader open of a 3.17 MB ACE file now reads 4,228 bytes, and one `UpdateRowsAsync` reads about 2× the file; the rest is `TableSnapshotReader` re-opening and scanning the file (see suggested step 1). `OfficeCryptoAgile.TryGetFlatEncryptionInfo` now checks the descriptor length against the end of page 0, so a length that runs past page 0 returns false instead of throwing `ArgumentException`. Both `AccessWriter.OpenAsync` overloads throw `NotSupportedException` for flat Agile before checking the password, taking a lock-file slot or writing anything; the message points at `DecryptAsync` / `EncryptAsync` and `AccdbAgileCfb`. The README and the `AccessEncryptionFormat.AccdbAgile` doc no longer call flat Agile a writer target, and say that `EncryptAsync`'s default `.accdb` target is this format. `EncryptionOpenProbeTests` covers it: `ReaderOpen_ReadsOnlyTheFirstPages` and `WriterOpen_ReadsOnlyTheFirstPages` count the bytes read on Jet3, Jet4 and ACE files (unencrypted, RC4, ACCDB legacy password and AES-CFB wrapped) and allow at most four pages; `IsFlatAgileEncrypted_RecognisesPageZeroAlone` and `IsFlatAgileEncrypted_DescriptorLengthPastPageZero_ReturnsFalse` cover the page-0 probe; and the `WriterOpen_FlatAgilePath_*` and `WriterOpen_FlatAgileStream_*` tests open flat Agile with the right, wrong or no password and check that the bytes, the stream and the lock file are unchanged.
  - Follow-up: `AccessWriter.DetectEncryptionFormatAsync` reports `Jet4Rc4` for an unencrypted Jet4 `.mdb` the writer created, so `EncryptAsync` on such a file throws "already encrypted (Jet4Rc4)". `EncryptionConverter.DetectFlatFormat` tests bit 0x02 of header byte 0x62 before unmasking it. Access-authored Jet4 files are unaffected, which is why the RC4 cases use AdventureWorks. This predates the fix.
  - Follow-up: the path overload of `AccessWriter.OpenAsync` reads page 0 three times: in `ThrowIfFlatAgileAsync`, in the password check's `AccessReader` open, and in the stream overload. Each read is 4 KB.
- **Updating an unrelated column stripped a leading prefix from an OLE value.** `UpdateRowsAsync`, cascade updates and `AddColumnAsync`/`DropColumnAsync`/`RenameColumnAsync` delete each row and insert it again from the writer's snapshot. `TableReader.ReadDataTableForSchemaRewriteAsync` decoded that snapshot with the public read rules, so OLE cells went through `OleObjectDecoder.DecodeOleValueBytes`. An OLE 1.0 package was replaced by its embedded file, and a value with a file signature after a prefix (`00 01 42 4D ...`, `%PDF` after a header) lost the prefix. A MEMO whose LVAL data could not be read decoded to `(memo on LVAL page)` or `(memo chain error: ...)`, and that text was written back as data. The snapshot now uses `RowDecodePlan.CreateTypedForWriteBack`, which reads OLE as the stored bytes, inline and from LVAL rows and chains (`LongValueDecoder.ReadLongValueBytesExactAsync`), and types the MEMO and OLE columns as `object`. The public read API still unwraps packages and slices at signatures. A MEMO or OLE value that cannot be read becomes an `UnreadableLongValue`. An update, a schema rewrite and `IndexMaintainer.RewriteSystemTableRowsAsync` then throw `InvalidDataException` before any row of the table changes, and a cascade update checks each child table before rewriting that table's rows. Assigning a new value to the unreadable column, or dropping it, still works, and inserts and deletes on the table are unaffected. `TableRowStore` refuses to write an `UnreadableLongValue` as a backstop. `LongValueWriteBackTests` covers inline, single-page and chained OLE on Jet3 (inline only), Jet4 and ACCDB. It runs the update, all three column operations, committed and rolled-back transactions, `UseTransactionalWrites`, rows on several data pages and a cascade update (ACCDB). `UpdateRowsAsync_UnreadableMemo_RefusesRowAndLeavesItUntouched`, `UpdateRowsAsync_ReplacingUnreadableMemo_Succeeds` and `AddColumnAsync_UnreadableMemo_RefusesRewriteBeforeChangingSchema` cover the refusal.
  - Follow-up: `RelationshipEnforcer.EnforceFkOnPrimaryUpdateAsync` is not atomic across relationships. When a parent update cascades to two child tables and the second holds an unreadable MEMO, the first child already has the new key while the parent row keeps the old one. The existing "cascade-update is not enabled" error has the same gap. Only `UseTransactionalWrites` or an explicit transaction rolls it back.

## Open: reproduced by the re-check agents (I didn't run these myself)
- **Wide tables skip unique checks.** On a table whose definition spans more than one page (200 columns, 30 indexes), a duplicate insert into a UNIQUE index is accepted. [UniqueIndexChecker.cs:37-46](JetDatabaseWriter/Indexes/UniqueIndexChecker.cs#L37-L46) reads only the first page.
- **RenameColumn changes types and loses foreign-key indexes.**
  - NUMERIC(10,2) becomes (18,0), so 12.34 is stored as 12.
  - On a child table, the foreign-key index is dropped and the parent's link still points to the freed page.
  - The code is at [TableSchemaEditor.cs:237-258](JetDatabaseWriter/Tables/TableSchemaEditor.cs#L237-L258).
- **Jet3 table headers are corrupted.**
  - The row count is written into the AutoNumber slot ([TDefPageBuilder.cs:486-488](JetDatabaseWriter/Schema/TDefPageBuilder.cs#L486-L488)).
  - The AutoNumber writer overwrites the table-type byte, which went from 0x4E to 0xBC after 700 inserts ([AutoNumberMaintainer.cs:71-78](JetDatabaseWriter/Schema/AutoNumberMaintainer.cs#L71-L78)).
- **Jet3 long values the library writes can't be read back.** `LongValueStore.WriteLvalPageHeader` always writes the Jet4 data-page header (row count at offset 12, row offsets from 14), but Jet3 data pages keep them at 8 and 10. A Jet3 MEMO over about 1 KB or OLE value over 256 bytes written by the library reads back as `(memo on LVAL page)` or an empty `byte[]`. An update or schema rewrite of such a row used to store that placeholder for good; it now throws `InvalidDataException` and leaves the row alone. This is why the Jet3 cases in `LongValueWriteBackTests` use only inline payloads.
- **Constraints:**
  - Rolling back an AddColumn or DropColumn switches off every check on that table, so NULL gets into AutoNumber and Required columns.
  - AutoNumber IDs are reused across sessions ([ConstraintRegistry.cs:382-424](JetDatabaseWriter/Schema/ConstraintRegistry.cs#L382-L424)).
  - Validation rules and default values stored in the file are never enforced.
  - Rules declared in code are lost when the writer is reopened.
  - Calculated expressions follow Excel precedence: `-2^2` = 4, and `5%` is accepted as 0.05.
- **LINQ mapping:** `[Column]` is ignored. Inserting an entity with a renamed property writes DBNull, and `Where(p => p.LastName == "Smith")` matches nothing.

## Design flaw status
| Flaw | Status | What changed |
|---|---|---|
| Facade is the engine / service locator | **Partly resolved** | Locator and cycles are gone. `DatabaseFile` (1,420 lines, used by about 33 types) is the new catch-all: pager, transaction journal, encryption and table-definition parsing in one class. |
| Reader and writer are separate engines | Open, critical | Moved into `TableSnapshotReader`. The reusable decoder now exists but the writer doesn't use it. |
| No pager or buffer manager | Open, critical | The cache moved into `ReaderPageCache`, and its eviction bug (bug 1) is now fixed. There are still several end-of-file definitions, and the writer still has no cache. |
| Transactions not atomic | Open, critical | Changes were mechanical, and the docs still claim before-image journaling. Rollback is now shown to break the writer (bugs 10–11). The format-byte bump is fixed (bug 3). |
| Schema isn't a model | Open | Three duplicate parsers merged, the rest unchanged |
| No write pipeline or real B-tree | Open | Moved into `TableDataWriter` with the same algorithms |
| Constraints live in the process, not the file | Open | No change |
| Lossy value model | Open | Complex-column cells are no longer lossy: `Rows()` and the other row reads return every attachment, decoded, and every multi-value item (see "Fixed since 6eab703"). Updates, cascades and schema rewrites no longer lose data either: the writer's snapshot carries OLE bytes exactly and refuses a MEMO or OLE value it cannot read instead of storing placeholder text. The OLE signature heuristic on the normal read path is unchanged, and a multi-value Decimal still loses its scale. |
| Format knowledge scattered | Open | No change. Files importing `JetTypeInfo` went from 35 to 40. |
| Read API doesn't compose | Open | Moved into `TableReader`. The read loops now agree on which rows they return, on `maxRows` and on calculated-column types (bug 12 and the drift fix above), but they are still separate loops with no shared scan primitive. `IndexRowReader` still returns nothing for linked tables (`ListIndexesAsync`, `EnumerateIndexRowsAsync`), `CatalogReader.ResolveTableAsync` still re-reads the TDEF uncached and rescans MSysObjects, and unknown tables still read as empty, unlike the writer. |
| Encryption isn't a page layer | Open | Opening a file now reads only page 0 to detect flat Agile, and the writer refuses flat Agile instead of corrupting it. Flat Agile and the CFB Office Crypto formats are still decrypted whole into memory, and the writer still has no page cipher for flat Agile. |
| Failures aren't modeled | Open | `LastDiagnostics` is now built from a typed record internally |
| No CI; untested netstandard2.1 build | Open | No change. A Release build also fails on 155 analyzer errors in the test project. |
| LINQ layer has no mapping model | Open | It now depends on reader services instead of the facade, which makes a package split easier |

## Suggested next steps
1. **Make the writer's reads see the transaction.** This is now small: build `TableSnapshotReader` from a `ReaderServices` over the writer's own `DatabaseFile`, with a capacity-0 `ReaderPageCache`. That should fix bugs 5–8, and likely bug 2 as well. Pairing rows to locations by position stays fragile until a cursor returns each row with its location. Remove the allow-list entry and the doc's "deliberate exception" at the same time. The new snapshot must still decode with `RowDecodePlan.CreateTypedForWriteBack` (or call `ReadDataTableForSchemaRewriteAsync`), or updates start stripping OLE prefixes again.
2. **Rollback should reset writer state.** Inject `TableCatalog`, `DataPageInserter` and `ConstraintRegistry` into `TransactionLifecycle`, and invalidate or restore them on rollback (fixes bugs 10–11 and the disabled-constraints problem).
3. **One-line and small fixes:**
   - run the full constraint pass on update (bug 4);
   - keep every column property in RenameColumn.
4. **Add CI** that runs the tests on every PR. Each repro above should become a failing test first; the programs are in `scratchpad\recheck\*` and `scratchpad\repro2`/`repro3`.

The per-claim results, with current file:line evidence and fix notes for all 14 flaws, are in `scratchpad\recheck.json` and `scratchpad\recheck-digest.md`.
