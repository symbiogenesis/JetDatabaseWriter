## Data loss and broken referential integrity

- **Without a transaction, a failed update can lose rows or leave their indexes and counts inconsistent.**
  - `TableDataWriter.UpdateRowsAsync` rewrites each matching row with `TableRowStore.MarkRowDeletedAsync` and then `InsertRowDataLocAsync`, and `RelationshipEnforcer.ApplyCascadeUpdatesAsync`, which runs before that loop, rewrites the cascaded child rows the same way. Every new version is encoded and measured before the call's first logical page write, so an encoder refusal or an oversized row is refused before mutation.
  - A default write scope coalesces repeated changes to a page and drains pages in page-number order at the end of the call, spilling earlier when its dirty-page threshold is reached. It does not undo a failed call: scope disposal drains pending changes even when the operation throws, and a failed drain can leave a prefix of the changed pages on disk. A read or corrupt-page failure between a tombstone and its replacement can therefore persist the deletion; an I/O failure during a spill or final drain can persist only part of a multi-page rewrite.
  - The remaining failure points include the re-insert's LVAL work, owned-page discovery and allocation, and, with `SecureEraseMode.DeletedRowsAndFreedPages`, release of the old row's LVAL rows after its slot is flagged. Index maintenance runs after the row loop and the re-insert suppresses the TDEF row-count adjustment, so a partial update can leave stale index entries or a row count above the live rows. Cancellation is ignored once the call starts logical page writes. The README's "Transaction durability" limitations document the gap.
  - Repro target for the statement-atomicity fault sweep: a multi-page table with a primary key and large Memo values, updated without a transaction, with a stream fault at each physical spill or final-drain write and with a corrupt page reached after the first tombstone. Check row values, index results, TDEF counts and file bytes against the pre-call image. Include `SecureEraseMode.DeletedRowsAndFreedPages` and calls large enough to cross the dirty-page threshold.
  - Planned in wave 2: atomicity-b makes every call statement-atomic.
- **Earlier builds leave damaged TDEF index descriptors that no repair API fixes.** Builds before f68a131 put spilled `used_pages` row bytes 8 or 16 bytes early, inside `col_map`, in wide Jet4 and ACCDB tables. A 200-column, 30-index table can have 15 indexes naming col_num 0x02FF and up; a hit at a page boundary damages a continuation-page header and cuts the definition short. Repro: `LegacyDamageInjector.InjectStrayUsedPagesByteAsync` on that schema. Planned in wave 2: legacy-repair adds explicit detection and `AccessWriter.RepairAsync`; it must refuse lost index settings without changing the file.
- **Cascade updates stop at the first level, so a grandchild keeps the old key as an orphan.** `RelationshipEnforcer.PlanCascadeUpdatesAsync` plans the rewrites of each cascading relationship's dependent rows, on the seek and the snapshot paths, but never plans again with the child table as the primary table; deletes recurse through `PlanCascadeDeletesAsync`. Repro (ACCDB): A (`Id` primary key), B (`AId` primary key) and C (`Id` primary key, `BAId`), related A.Id <- B.AId and B.AId <- C.BAId, both cascading updates, with rows A [1], B [1] and C [1, 1]. Updating A.Id to 5 leaves C.BAId at 1. Planned in wave 2: write-pipeline-a1's cascade plan recurses through updates as deletes already do.

## Values stored or read wrong without an error

- **Text outside the code page is stored as its best-fit match or `?` in Jet3 `LvProp` strings.**
  - Jet3 `LvProp`: `ColumnPropertyBlockBuilder.ToBytes`, `ColumnPropertyTargetBuilder.AddText` and `AddMemoText`, `LinkedOdbcLvPropBuilder.BuildNameMap` and `ColumnPropertyTarget.GetTextValue` take their encoding from `JetFormat.PropertyTextEncodingOf`, which gives Windows-1252 for every Jet3 file, and `ColumnPropertyBlock.Parse` hard-codes 1252 too. So a Description, ValidationText, DefaultValue or ValidationRule expression, or an ODBC source column name outside Windows-1252 is stored lossily without an error, and on a Jet3 file with another code page the `LvProp` target names can differ from the TDEF column names. Names and Text or Memo values are refused instead (`AccessObjectName.ThrowIfNotStorable` and `TableDataWriter.ThrowIfTextNotStorable` through `JetFormat.DescribeUnstorableCharacter`, with `JetFormat.EncodeAnsiText` as the backstop). Repro: on a new Jet3 file, `CreateTableAsync("T", [new ColumnDefinition("Name", typeof(string), 50) { Description = "中文 Łódź", ValidationText = "中文" }])`; after reopening, `GetColumnMetadataAsync` returns the Description "?? Lódz" and the ValidationText "??".
  - Wave 2's format-profile-b #1 encodes LvProp text with the database's code page, which fixes Jet3 files with another code page; whether a character the code page lacks is then refused, as it is in names and values, or stored as '?' is left to that package.
- **Earlier builds leave General Legacy keys in General and General 97 indexes.** Files changed by earlier builds retain keys encoded with the wrong collation. Repro: modify a General or General 97 text index with a pre-collation build, then compare its stored keys with its descriptor-selected encoder. A full index rebuild would repair the keys; no public repair operation does so. Not planned yet: deferred from wave 2; consider an explicit repair mode alongside legacy-repair.
- **Fixed-length Text columns read as Null.** `ColumnInfo.IsFixed` treats every Text column as variable-length (`JetTypeInfo.IsAlwaysVariableLength`), whatever its descriptor's FLAG_FIXED says, so `users.c_flag_` reads as Null in both rows of all four fixedTextTest fixtures (V2000, V2003, V2007 and V2010). The stored values have not been checked, and no fixture shows how Access pads such a value on write. Wave 2's write-pipeline-c stops an update from writing those Nulls back, but the read stays wrong. Not planned yet: deferred from wave 2.
- **An `LvProp` blob that cannot be read gives no properties, without an error, and a schema rewrite then replaces it with only the modelled properties.** `ColumnPropertyReader.ReadLvPropForTableAsync` gets the blob from the typed decode, where `LongValueDecoder.ReadLongValueRawBytesAsync` returns an empty array for an LVAL row or chain it cannot read, and `ColumnPropertyBlock.Parse` returns null for under 4 bytes or an unknown magic. So `GetColumnMetadataAsync` shows no description, default, rule or calculated result type, `ConstraintRegistry` enforces no stored default or rule, and nothing is traced. From the code, not run: AddColumn, DropColumn and RenameColumn then call `PersistedPropertyProjector.ProjectForRewrite(null, ...)`, which builds a blob from what `JetExpressionConverter.ApplyColumn` emits for the columns, and that blob replaces the stored one on the rebuilt table's catalog row, so Caption, Format, the table-level Filter and the rest are lost. A row value in the same state is refused (`UnreadableLongValue`, `InvalidDataException`). Planned in wave 2: failure-model-b1 reports such a blob as unreadable, and constraints-b refuses a schema rewrite over it.
- **An unreadable MEMO reads as placeholder text, and an unreadable OLE value as an empty array, on every public read API.** `LongValueDecoder.ReadLongValueAsync` returns "(memo)" or "(OLE)" for a descriptor shorter than its 12-byte header, "(memo on LVAL page)" or "(OLE)" when the LVAL row cannot be located or is empty, and "(memo chain error: <reason>)" or "(OLE chain error: <reason>)" when a chain breaks. `RowDecoder` and `RowDecodePlan` return that text as the cell, so `Rows`, `ReadTableAsync`, `Rows<T>`, `ReadTableAsync<T>` and the string APIs show it as stored data. OLE cells go through `ReadLongValueRawBytesAsync`, which returns an empty array for any unreadable value, and calculated long values behave the same. Nothing reaches `Trace` or `LastDiagnostics`, and neither the README nor `IAccessReader` documents it. The writer's snapshot is not affected: `RowDecodePlan.CreateTypedForWriteBack` reads through `ReadLongValueBytesExactAsync`, and updates and rewrites refuse the resulting `UnreadableLongValue` with `InvalidDataException`. Planned in wave 2: failure-model-b1 (one decode-fault policy for every read path, with no placeholder values).
- **A damaged complex-column catalog makes every Attachment and multi-value cell read as Null with no error.** `ComplexColumnReader.TryGetComplexColumnsAsync` and `LoadColumnCellsAsync` catch `InvalidDataException`, `IndexOutOfRangeException`, `IOException` and `OverflowException` from a damaged parent TDEF, `MSysComplexColumns`, `MSysObjects` or flat table, trace them only when diagnostics are enabled (`TraceBestEffortFallback`), and return no descriptors or no cells. Planned in wave 2: failure-model-b1 #2 stops catching `IOException` there and makes reads under `StrictParsing` throw `CorruptComplexColumn`; lenient reads still give Null.

## Writes refused that Access allows

- **A unique index that is not the primary key refuses a second Null key, so every insert into NorthwindTraders' Employees fails.** Access allows any number of Null keys in such an index: Employees has 10 rows with a Null `WindowsUserName` under its unique index 'WindowsUserName'. `UniqueIndexChecker` encodes Null like any other value and compares encoded keys, and `IndexMaintainer`'s bulk rebuild throws on equal encoded keys. Repro: on a copy of NorthwindTraders.accdb, `InsertRowAsync("Employees", new RowValues { ["FirstName"] = "Ada", ["LastName"] = "Lead", ["WindowsUserName"] = "ada.lead" })` throws "Unique index violation on table 'Employees': duplicate key detected after row mutation". Planned in wave 2: write-pipeline-b lets a unique index that is not the primary key hold several all-Null keys.
- **`AccessWriter` cannot open Access-native flat Agile ACCDB files, the format `EncryptAsync` writes by default for `.accdb`.** Both `AccessWriter.OpenAsync` overloads throw `NotSupportedException` for `AccessEncryptionFormat.AccdbAgile` before checking the password, taking a lock-file slot or writing anything, because the writer has no AES-256-CBC page cipher for that layout; the reader decrypts such a file whole into memory. So a file the library encrypts with default options cannot then be edited by it. The README gives the workarounds: decrypt, edit and encrypt again, or re-encrypt as `AccdbAgileCfb`, which the writer opens. Planned in wave 2: encryption-flat-agile.
- **AddColumn, DropColumn and RenameColumn throw `NotSupportedException` on every Access-authored table with an Attachment or multi-value column.** The rewrite (`TableSchemaEditor`, through `IndexHelpers.ProjectIndexes`) forwards every Normal or PrimaryKey index whose key columns survive, including Access's unique, Required complex-column index (`<column>_<32 hex>`), and `CatalogArtifactWriter.CreateCatalogTableArtifactAsync` then calls `IndexHelpers.ResolveIndexes`, which refuses a Complex or Attachment key ("Microsoft Access does not permit indexes on this column type"). Nothing is written. Affected: NorthwindTraders.accdb ProductCategories, ComplexFields.accdb Documents and complexDataTest Table1 (all three operations checked there). As a result, the rewrite's carry of the TDEF complex AutoNumber (TDEF@28) and its per-row reference assignment are tested only on tables the writer created. Fix idea: rebuild a projected complex-column index as the same unique, Required index instead of treating it as a user declaration; the rebuilt `LvProp` keeps the properties the writer does not model, such as memo-data's `AppendOnly`. Then test a rewrite on complexDataTest, where TDEF@28 (7 in V2007, 8 in V2010) is above the largest live reference (4). Not planned yet.
- **`CreateRelationshipAsync` refuses Jet3, Jet4 and slim-catalog ACCDB files the writer created, because `CreateDatabaseAsync` writes none of Access's standard system objects there.**
  - `AccessWriter.InitializeFreshDatabaseAsync` calls `ComplexColumnManager.ScaffoldSystemTablesAsync`, which returns early unless the format is ACCDB with `WriteFullCatalogSchema`. So those files have no `MSysObjects` row naming `MSysObjects`, no Tables, Databases or Relationships containers, no `MSysDb`, and no `MSysACEs`, `MSysQueries` or `MSysRelationships` tables. Reads do not need them (`CatalogRowReader.FindSystemTableTdefPageAsync` resolves `MSysObjects` to TDEF page 2), but with no `MSysRelationships`, `RelationshipManager.CreateRelationshipAsync` throws `NotSupportedException`, as the README's "Foreign-key relationships" section says.
  - `TDefPageBuilder.WriteJet3HeaderDefaults` and `WriteJet4AceHeaderDefaults` also write Access's defaults 3, 4 and 5 into the header's `MSysACEs`, `MSysQueries` and `MSysRelationships` TDEF fields (the i32 values at 0x24, 0x28 and 0x2C), and only the full-catalog ACCDB path patches them (`PatchHeaderSystemTablePagesAsync`), so on these formats the fields name pages that hold other things. Repro: `CreateDatabaseAsync(Jet4Mdb)`, then `CreateTableAsync("T")`; unmasked, the fields read 3, 4 and 5, and pages 3, 4 and 5 have page types 04, 04 and 01. On Jet3, page 3 is T's TDEF. The slim-ACCDB case is from the code, not run.
  - Either create the tables or stop naming pages that do not hold them. Not planned yet: deferred from wave 2, because whether Access needs those rows needs a DAO run.
- **Attachments and multi-value items can be added but not removed or replaced one at a time.** The writer changes them only through `AddAttachmentAsync` and `AddMultiValueItemAsync`; their rows in the hidden flat table go only with the parent row, the table or the column. Planned in wave 2: value-model-b adds item ids and removes and replaces items.
- **`BeginTransactionAsync` inside an open transaction throws, and there are no public savepoints.** `TransactionLifecycle.BeginTransactionAsync` refuses a second transaction with `InvalidOperationException` ("A transaction is already active on this writer. Only one concurrent transaction per AccessWriter is supported."), where DAO's `BeginTrans` nests up to five levels (from memory, not checked). The internal statement savepoint frames could support a public API. Not planned yet: deferred from wave 2.

## Partial writes and pages left allocated

- **`CreateTableAsync` and `InsertRowsAsync` can fail after their first page write and leave what they wrote.** Wave 2's atomicity-b rolls such a call back.
  - Not reproduced: `CatalogArtifactWriter.CreateCatalogTableArtifactAsync` reserves the TDEF pages, allocates an empty leaf per index and a usage-map page before it inserts the `MSysObjects` and `MSysACEs` rows, with no path that releases them, so any later failure without `UseTransactionalWrites` would leave those pages allocated with no catalog row naming them. Repro to try: fail the `MSysObjects` row write with `WriteFaultStream`, then look for TDEF and leaf pages no catalog row reaches.
  - Every `InsertRowsAsync` overload writes its rows one at a time (`TableDataWriter.InsertPreparedBatchAsync`, which every overload reaches through `InsertMappedRowsAfterValidationAsync`), so when row N fails, for example with `JetLimitationException` because it is larger than a data page, or with a foreign-key refusal, which is checked just before each row is written, rows 1 to N-1 are already on data pages. `RollbackInsertedRowsAsync` marks them deleted and rewinds the TDEF row count, so no row stays live, but the deleted slots and any data pages appended for them remain. A single-row insert leaves the file unchanged, because the row is measured before any page is written. Fix idea: serialize and size-check every row of the batch before writing the first.
- **`AddAttachmentAsync` and `AddMultiValueItemAsync` rebuild every index of the hidden flat table on each call, so adding items one at a time grows quadratically in time and file size.**
  - `ComplexColumnManager.AddComplexItemCoreAsync` inserts the flat row and then calls `MaintainIndexesAsync`, which decodes every live flat row and builds every flat-table index again. The replaced trees are never freed, because `RebuildIndexesAsync` frees replaced index pages only for tables without long-value or complex columns, and never for flat tables.
  - Measured on 2026-10-03 with a Release build on a shared Arm64 machine: an ACCDB table `Docs` (`Id` primary key, `Files` attachment) with 800 rows, one 1 KB attachment added to each row, no transaction. Calls averaged 9.2 ms over the first 100 and 183 ms over the last 100, and the file grew from 196 KB to 23 MB, with 5,015 of its 5,860 pages index pages. The same 800 values inserted into an indexed table, one `InsertRowAsync` each, took 1.4-2.8 ms per call throughout and left a 3.3 MB file with 14 index pages.
  - Fix: insert through `InsertRowDataLocAsync`, pass the row and its location to `TryMaintainIndexesIncrementalAsync` as `TableDataWriter`'s inserts do, and rebuild only when that bails. Planned in wave 2: write-pipeline-a2 #3 routes complex-column writes through the one write path and maintains the flat-table indexes incrementally (at most 6 index page writes per item over 300 items).
- **Replaced index trees stay allocated and unreachable until Compact & Repair.**
  - `IndexMaintainer.TryMaintainIndexesIncrementalAsync` never frees the tree that an incremental multi-level rebuild (`IndexBTreeEditor.TryPlaceTreeAsync`) replaces, or the root leaf it grows into a tree, and `IndexBTreeEditor.TryRebuildCatalogIndexTreeAsync` does the same for catalog indexes. Repro: 3,000 random single inserts into a table with a primary key, then count the 0x03/0x04 pages owned by its TDEF that no `first_dp` reaches (`PageAudit.FindUnreachableIndexPagesAsync`): 7 on Jet4 and ACCDB, 12 on Jet3. Root-leaf growth is also unchecked against DAO Compact & Repair (catalog-index-maintenance-notes.md).
  - The full rebuild (`RebuildIndexesAsync`) frees the trees it replaces only on tables that have no Memo, OLE or complex columns and are neither flat tables nor `MSys*` tables. On Jet3 it finds the old trees by walking them from `first_dp` (`CollectJet3ReplacedTreePagesAsync`), and only for indexes whose `used_pages` is 0, as every writer-created one is; an Access-authored Jet3 index names a usage-map row the writer cannot rewrite, so its old tree stays. A table with an FK entry takes the full rebuild on every write, so an Access-authored Jet3 table in a relationship, and any table with Memo, OLE or complex columns in one, grows with every insert, update and delete. Repro: in a copy of indexTestV1997.mdb, insert 1,500 rows into Table1 (`[i, i % 3, 10 + i % 4, "d", 0]` for i from 100), then make 10 single inserts: 360 of Table1's index pages are unreachable, 36 per insert.
  - FK entries that `DropTableAsync` (`RelationshipManager.RemovePartnerLinksAsync`) or `DropRelationshipAsync` removes leave their index leaves allocated, and `TryReclaimTrailingRealIdxAsync` reclaims only trailing unreferenced real-idx slots, so a slot in the middle of the array stays in the partner's TDEF. Reclaiming it means renumbering `index_num2` and every cross-TDEF `rel_idx_num` that points at it (index-and-relationship-format-notes.md §9, W14).
  - Planned in wave 2 for the first bullet only: write-pipeline-b #3 and #4 replace the incremental and catalog tree rebuilds with in-place B-tree edits, which free emptied index pages on user tables. The full rebuild's exclusions and the FK-entry leaves that `DropTableAsync` and `DropRelationshipAsync` leave are not planned yet.
- **The LVAL pages the writer allocates go into none of their long-value column's usage maps.** `LongValueEncoder` allocates each LVAL page through `PageAllocator.AllocatePageAsync` and records it in neither the column's own owned-pages map nor its free-space map, where Access lists its LVAL pages (calcFieldTestV2010 Table1's AllNames: rows 2 and 3 of usage-map page 0x57). The table's owned-pages map leaves them out, as Access's do (data-page-row-format-notes.md, "Usage-map rows"). Drops and rewrites free the writer's LVAL pages through each row's Memo and OLE headers (`ReclaimTableStoragePagesAsync`), but anything that finds a column's LVAL pages through its usage maps misses them. Not planned yet.
- **A crash during `EncryptAsync`, `DecryptAsync` or `ChangePasswordAsync` by path leaves `<db>.reenc-<guid>.tmp` beside the database, and nothing removes it; on Linux and macOS the rename is not durable.** `EncryptionManager.ReplaceFileAtomicAsync` creates the temp file, flushes it and calls `ReplaceFileWithTemp`, and deletes it only when the temp write fails or is cancelled, or when both renames are refused. A crash between creating it and the rename leaves it (the database holds the old or the new contents), and nothing looks for a stale `*.reenc-*.tmp`. On Linux and macOS the directory entry the rename changes is not flushed, so a power loss just after the call returns can still show the old file; the wave-2 crash journal has the same gap. Fix idea: sweep stale `<db>.reenc-*.tmp` files before a path re-encryption, and flush the directory after the rename on Unix. Not planned yet; encryption-containers #3, which rewrites path re-encryption, is where it belongs.
- **A writer over a caller stream that is not a `FileStream` gets no crash recovery from the rollback journal.** Nothing makes a write-back crash-safe today (**Transactions have no crash recovery**, under "Design flaws"), and wave 2's crash-journal journals only files opened by path or as a `FileStream`: any other caller stream keeps an in-process undo only, so a process crash or power loss during a write-back can leave its bytes torn. A caller-supplied journal stream would cover it. Not planned yet: deferred from wave 2.
- Minor:
  - **The surgical index split paths append their pages outside `PageAllocator` (not reproduced).** `IndexBTreeEditor.TryAppendContiguousAsync`, which `TrySurgicalMultiLevelMaintainAsync` and `TrySurgicalCrossLeafMaintainAsync` use, appends through `Pager.AppendPageAsync`, so the splits never reuse free pages, and an append that fails or lands out of sequence leaves the pages already appended unlinked. Repro to try: make a surgical split append two pages with `WriteFaultStream` failing the second, then look for the first with `PageAudit.FindUnreachableIndexPagesAsync`. Fix idea: reserve the run through `PageAllocator.ReserveContiguousPagesAsync` and a `ReservedPageRuns`, as `TryPlaceTreeAsync` does. Planned in wave 2: write-pipeline-b #4 deletes these paths with `IndexBTreeEditor`, and #2's `IndexPageStore` allocates through `PageAllocator`.

## Values that differ from Access or between writers

- **The writer does not enforce every constraint stored in the file.** The README's "Column defaults and validation rules" limitation documents the first two.
  - Table-level (record) validation rules: a table's `ValidationRule` and `ValidationText` are in the table-level target of its `MSysObjects.LvProp` blob, the block with an empty name, which can come anywhere among the blocks. `ConstraintRegistry` loads only column targets, and no production code calls `ColumnPropertyBlock.FindTableTarget`, so inserts and updates never evaluate a table rule, including rules Access wrote. `TableSchemaEditor.RewriteTableAsync` passes the projected blob to the rebuilt table through `CatalogTableArtifact.PersistedProperties`, where enforcement can register the rule.
  - A stored default or rule the expression engine cannot parse or evaluate is skipped. `ColumnValidationRule.Compile` returns `Unsupported`, `Accepts` returns true for an unsupported rule and for one whose evaluation throws `ArgumentException`, `NotSupportedException`, `InvalidOperationException`, `FormatException`, `InvalidCastException`, `ArithmeticException` or `IndexOutOfRangeException`, and when `ColumnDefaultValue.TryEvaluate` fails, an omitted column stays DBNull, which stores Null or, on a Required column, throws "... is marked NOT NULL and no value was supplied". Examples: `GenGUID()`, `CurrentUser()`, `DLookUp`. So the writer refuses an insert that leaves out a Required ReplicationID column whose default is `GenGUID()`, which Access fills, and never checks a rule that uses `DLookUp`.
  - `ConstraintRegistry.ApplyAsync` (insert) and `ApplyUpdateAsync` (update) skip every check (NOT NULL, AutoNumber generation, defaults, rules and calculated-column recomputation) when the cached constraint list's count differs from the TDEF column count or from the row's length. No trigger is known apart from a positional row of the wrong length, which `TableRowStore` then refuses with `ArgumentException` ("Expected N values for table row but received M") after the earlier rows of a batch are written, but nothing checks that the list matches the columns by name. Fix idea: rebuild the list from the `TableDef`, matching names per position, or throw.
  - Planned in wave 2: constraints-a enforces table rules, evaluates `GenGUID()` and `CurrentUser()` and refuses a write whose default or rule it cannot evaluate, and rebuilds a stale constraint list from the file instead of skipping the checks.
  - Once constraints-a refuses instead of skipping, a table whose stored default or rule uses a function the expression engine lacks (`DLookUp` and the other domain aggregates, `Eval`, or any function it does not implement) refuses every insert, and every update the rule covers, where today the check is skipped. No fixture holds such an expression. Not planned yet: deferred from wave 2; record each function users report, and constraints-a moves this bullet to its own item when it deletes this one.
- **`GeneralLegacyTextIndexEncoder` encodes 1 of the 8 keys of the `Unicode` index on testUnicodeCompV2003.mdb's table `Table` differently from the leaf Access wrote.** A wave-2 probe re-encoded the text index leaves of the Access-authored fixtures (about 1.07M keys in 94 files) with the encoder for each sort order; every other key matched, apart from fixedTextTest*'s `Users2_8_idx`, whose column reads as Null (**Fixed-length Text columns read as Null**). Which character differs is not recorded; `TextSortOrderFixtureTests` skips this index. Not planned yet: deferred from wave 2.
- **The public API cannot choose a database or column sort order.** `CreateDatabaseAsync`, `CreateTableAsync`, `AddColumnAsync` and `ColumnDefinition` expose no sort-order option. New databases use General Legacy for Jet4 and ACCDB and General 97 for Jet3. New text columns inherit their database header's default, and schema rewrites preserve surviving column descriptors, but callers cannot request a different supported order. Repro: creating a new ACCDB offers no way to select General version 1. Not planned yet: deferred from wave 2.
- **Defaults.** Not planned yet.
  - `ConstraintRegistry.HydrateFromTableDef` and `ToConstraint` keep a `ValidationRule` property on an AutoNumber column, so a rule another tool stored there is checked against generated values, where Jackcess ignores every property on an AutoNumber column. From the code, not run; what Access does is unchecked.
- **Expressions.** Calculated columns, defaults and validation rules share one engine. Not planned yet.
  - Custom `Format` date codes are .NET's: `CalculatedExpressionFormattingFunctions` passes an unrecognised format to `DateTime.ToString(format, CultureInfo.InvariantCulture)`, so `Format(#2020-01-31 06:00#, "mm/dd/yyyy")` gives `00/31/2020` where VBA gives `01/31/2020`. Translate VBA's codes first: `m` and `mm` are the month unless they follow an `h` or precede an `s`, `n` and `nn` are minutes, and `ttttt`, `AM/PM`, `w`, `ww`, `q` and `y` have VBA meanings.
  - The named date formats use .NET's invariant patterns: `Format(d, "Long Date" | "Short Date" | "Long Time" | "Short Time")` and `FormatDateTime(d, 1..4)` use `D`, `d`, `T` and `t`, so `FormatDateTime(DateSerial(2025, 2, 3), 2)` gives `02/03/2025` and `Format(#2020-01-31#, "Short Date")` gives `01/31/2020`, where VBA en-US gives `2/3/2025` and `1/31/2020`; Short Time and Long Date differ too. The numeric named formats also use the invariant culture (`"Currency"` gives the `¤` symbol) and have not been compared with VBA.
  - Intermediate numbers are Decimal or Double rather than VBA's Variant subtypes: number literals parse as `double` (`CalculatedExpressionAstFactory.NumberValue`), radix literals become plain decimal numbers, and `AccessVariantOperators` keeps arithmetic on two non-date operands in `decimal`. So `CStr(1/3)` has 28 digits (VBA: 15), `TypeName(&H10)` is `Double` (VBA: `Integer`) and `VarType(&HFFFF)` is 14 (VBA: 2). Fix: carry Integer, Long, Double, Currency and Decimal through literals and operators.
  - A table-qualified field reference is not evaluated, and the error names an internal placeholder. `CalculatedExpressionNormalizer` replaces each bracketed name with its own `__JdwCalcCol<n>` placeholder, and `CalculatedExpressionEvaluationContext.GetNameValue` maps only single placeholders back. Repro: on ACCDB, `CreateTableAsync("T", [Price double, Calc double calculated "[T].[Price]*2"])` succeeds, and an insert that leaves Calc Null throws `InvalidOperationException` "references unknown name '__JdwCalcCol0.__JdwCalcCol1'"; `T.Price*2` fails with unknown name 'T.Price', and `[T]![Price]*2` with a syntax error. A validation rule written that way is never enforced, because a rule whose evaluation fails accepts the value. `IAccessSchema.RenameColumnAsync`, the README and calculated-columns-format-notes.md say the engine does not evaluate table-qualified references. Fix: resolve the table's own qualifier, or reject it when the column is declared, and name the reference as written.
- **Complex columns.** Not planned yet.
  - A multi-value `string` column with no `MaxLength` gets a Memo `Value` column and reports "Multi-value Memo", though Access has no multi-value Memo. `ComplexColumnManager.BuildFlatTableSchema` gives `Value` the parent's `MaxLength`, and `JetTypeInfo.TypeCodeFromDefinition` maps a string whose `MaxLength` is outside 1..255 to Memo, while `ResolveComplexTypeTemplateName` points the `MSysComplexColumns` row at `MSysComplexType_Text` (TEXT(255)). Fix: give the `Value` column Text(255) when `MaxLength` is 0, and refuse a `MaxLength` over 255.
  - `InsertRowAsync<T>` with a POCO whose `byte[]` property holds a complex cell read back through `Rows<T>` throws `InvalidCastException` ("Unable to cast object of type 'System.Byte[]' to type 'System.IConvertible'"). `ConstraintRegistry` (`SuppliedComplexReference`, `TryGetComplexReference`) accepts only a `ComplexIdRef` or an integer as a supplied reference, so the `byte[]` stays in the row and `RowEncoder` calls `Convert.ToInt32` on it. Whether to ignore such a cell, giving the row a fresh reference as for null (Jackcess ignores a value given for a complex column by default), or to reject it with an `ArgumentException` naming the column is the user's call (under "Decisions left to the user").
  - Complex columns on tables the writer creates get no complex-column index. Access gives each one a unique, Required index on the parent row's 4-byte per-row reference, named `<column>_<32 hex>` truncated to 64 characters (for example `Attachments_CFC7F98A63064F2DBDB6822D653AB763` in ComplexFields.accdb), with Long Integer keys (`7F` and a big-endian int with the sign bit flipped). `BuildFlatTableSchema` emits only the flat table's indexes (`MSysComplexPKIndex`, the FK index and, for attachments, `IdxFKPrimaryScalar`), and `IndexHelpers.ResolveIndexes` refuses a declared index on an Attachment or Complex column. `IndexKeyEncoder` encodes such keys, and index maintenance and `ComplexColumnManager.HasComplexColumnIndexAsync` keep them current on Access tables. Fix: emit the index in `CreateTableAsync` and in `AddColumnAsync` of a complex column, together with lifting the schema-rewrite refusal under "Writes refused".
  - Updating an append-only Memo column (column property `AppendOnly`) adds no version-history row, as Access does. The version-history flat table has `_VersionHistory_<GUID>` (the per-row reference), `<memo column name>` (Memo), `Modified_<GUID>` (DateTime) and the AutoNumber key `<table>_VersionHistory_<GUID>`; complexDataTest*.accdb Table1 holds five versions. The read side supports it (`ComplexColumnReader`, `MultiValueItem.Modified`, the 'V' cell kind in `ComplexCellValue`), but no write path appends a row. complex-columns-format-notes.md §2.4.3 states the limitation.

Repro, from the code and not run: on ACCDB, `CreateTableAsync("A", [Id, new ColumnDefinition(new string('c', 64), typeof(byte[])) { IsAttachment = true }])` gives a 99-character flat-table name and flat column names of 65 and 66 characters.

## Performance

- **The reader's system-table lookups rescan and decode all of `MSysObjects` on every call.** `CatalogRowReader.FindTableTdefPageAsync` takes the `MSysObjects` TDEF from the reader's TDEF memo, which reads it once per reader, and calls `GetCatalogRowsAsync`, which reads every `MSysObjects` data page through `OwnedDataPages.ForEachLiveTableRowAsync`, not the reader's `ReaderPageCache`, and decodes the Id, ParentId, Name, Type and Flags of every catalog row before it matches one; nothing but that TDEF and the reader's list of `MSysObjects` data pages is cached between calls. The reader uses it in `CatalogReader.ResolveTableAsync` for any name that is not a user table, in `ComplexColumnReader`'s `MSysComplexColumns` lookup on every complex-column read and every metadata read of a table with complex columns, and in its flat-table lookup when the column's `FlatTableID` names no table definition. The linked-table listing and the complex-column object-name lookup also rescan `MSysObjects` on every call, though they decode only the columns they use. Measured with a counting stream on NorthwindTraders.accdb before the reader memoized TDEF bytes, so the counts include TDEF reads it no longer repeats (not re-measured since then, or since the catalog scans began decoding only the columns they use): each repeated `GetColumnMetadataAsync("Employees")` (a table with an attachment column) read 217,088 bytes, and each repeated `GetColumnMetadataAsync("MSysObjects")` or `GetColumnMetadataAsync("MSysRelationships")` 208,896, where a cached lookup that stops at the first match reads 20,480 and 12,288. With the page cache off, on NorthwindTraders.accdb `ListLinkedTablesAsync` reads 200,704 bytes over 9 pages and `GetComplexColumnsAsync("Employees")` 430,080 bytes over 13; on odbcLinkerTestV2007.accdb the listing reads 110,592 bytes over 6. Fix idea: cache the decoded catalog rows in `TableCatalog` and drop them whenever the writer changes the catalog, after an audit of the writer's cache invalidation. Planned in wave 2: read-composition-a caches the reader's table resolution and complex-column descriptors, so repeated metadata calls read nothing after warm-up; the linked-table listing's rescan is not planned yet.
- **Reading a table's persisted properties decodes the `LvProp` of every catalog row before the table's own, LVAL pages included, on every call.** `ColumnPropertyReader.ReadLvPropForTableAsync` enumerates `MSysObjects` through `RowDecoder.EnumerateTypedRowsForTdefAsync` with `Id` and `LvProp` wanted, until the row whose `Id` equals the TDEF page, and caches nothing. Column metadata (`SchemaReader`, `HydrateCalculatedResultTypesAsync`), a writer's constraint load (`TableSnapshotReader.ReadLvPropBlockAsync`) and every AddColumn, DropColumn and RenameColumn pay it, so a table late in the catalog reads the property blobs of every object before it. From the code, not measured. Smaller interim fix: scan with only `Id` wanted, then decode the matching row's `LvProp`. Planned in wave 2: read-composition-a reads only the table's own catalog row.
- **Every insert, update and delete on a table in a relationship rebuilds all of the table's indexes from a full decode of its rows.** `IndexMaintainer.TryMaintainIndexesIncrementalAsync` bails (C1c, "foreign-key logical index present") whenever the table's TDEF holds an FK logical index, which the writer emits on both sides of every relationship, because Access Compact & Repair rejected incrementally maintained relationship-backed indexes in probe validation. The bulk rebuild (`MaintainIndexesAsync`) decodes every live row through `TableSnapshotReader.ReadRowsAsync`, re-encodes every key and rebuilds every tree, so each write costs time in proportion to the table's size, and on some tables the replaced trees stay allocated (above). index-and-relationship-format-notes.md documents that FK tables take the bulk rebuild. Not planned yet: wave 2 defers removing the C1c bail until the DAO run (under "Before 4.0.0 ships") passes.
- **A delete that a relationship without cascading deletes refuses reads every row of the child table when the child has a MEMO, OLE, Attachment or multi-value column.** `RelationshipEnforcer.PlanCascadeDeletesAsync` calls `FindDependentRowsAsync` before it looks at `CascadeDeletes`. That seeks the child's foreign-key index and then reads every column of each row found (`TryReadAllRowsTypedAsync`), which `PartialColumnReader.TryReadColumnValuesTypedAsync` cannot do for a non-null MEMO or OLE value or a complex column's reference, so it falls back to `TableSnapshotReader.ReadRowsAsync` over the whole child table, long values included, only to count the rows for the refusal. A key update refuses from the seek's row locations (`CountDependentRowsOfKeyChangeAsync`). Repro, run as a scratch test on Jet4 and ACCDB: the setup of `ForeignKeyCascadeUpdateTests.Update_RefusedBySeekableRelationshipWithoutCascade_ReadsNoOtherChildPage` (M with 200 rows and a MEMO column over 7 data pages, one row under P.Id 1, FK_M_P not cascading), with `DeleteRowsAsync("P", RowCriteria.Where("Id", 1))` in place of the update, reads all 7 of M's data pages before it refuses. Fix: when the relationship does not cascade deletes, count the seek's locations, leaving out the rows in `cascaded`, and read the rows only on the scan fallback. Not planned yet; it belongs with write-pipeline-a1's cascade plan.
- **`Rows<T>(predicate)` compiles its predicate and lists the table's indexes on every call, and a collection `Include` costs 5-6 times a reference include.**
  - `IndexRowReader.Rows<T>(tableName, predicate, ...)` calls `predicate.Compile()` and `IndexPredicateTranslator.ExtractPushableCriteria` on every call, and `RowsInferredAsync` lists the indexes again through `TryPlanIndexReadAsync`. With `PublicSeekBenchmarks` on Relational_1000_10000_v1.accdb (10,000 Orders; not re-measured since captured operands stopped compiling and materializers were cached), 1,000 `Rows<T>(o => o.OrderId == key)` lookups took 525 ms and 58 MB, against 38.7 ms through `SeekRowsAsync`, 31.9 ms through `FromIndex(...).WhereEquals` and 2.9 ms for one `Rows<T>()` scan keeping the same keys. read-performance-bottlenecks.md records the numbers and advises explicit seeks in loops.
  - `IncludeLoader.LoadCollectionAsync` loads every child row for all the parents' keys (`BuildChildGroupsAsync`) and only then applies the include's Where, OrderBy, Skip and Take to each parent's list (`ApplyOperations`). With `QueryIncludeBenchmarks` over 1,000 customers and 10,000 orders, a collection include took 52.7 ms and 18 MB, the same include filtered, ordered and capped at five orders per customer 51.9 ms, and a reference include (each order's customer) 9.3 ms and 4 MB.
  - Captured operands are read without compiling, but the predicate still compiles on every call; planned with wave 2's LINQ plan cache (linq-plan-cache). Profile the `Include` cost before changing it.
- **Index inference scans for a bound its key cannot hold exactly**: a fractional bound on an integral key, or a Currency, Decimal or Single bound with more precision than the key keeps. `IndexSeekFilter` leaves such a comparison to the residual filter, which reads it from the rows the remaining comparisons seek or from a scan, so `r.Id > 1.5` scans. The Date/Time direction rule, which keeps a key that moved away from the matches, could cover these types too and seek `r.Id > 1.5` as `Id >= 2`. Not planned yet; linq-plan-cache edits `IndexRowReader`, where the filter runs.
- **`AccessReader.OpenAsync` reads the 0x80-byte header and then page 0 again: 4,228 bytes in two or more reads.** The stream overload reads the header with `PageFile.ReadHeaderAsync`, `EncryptionManager.TryDecryptAgileCompoundFileAsync` then reads page 0, and with `ValidateOnOpen` (the default) `ValidateDatabaseFormat` reads the 4-byte JET magic once more. The writer reads page 0 once, through `EncryptionManager.ReadOpenHeaderPageAsync`, which the reader could share. Repro: the `CountingStream` in `EncryptionOpenProbeTests.ReaderOpen_ReadsOnlyTheFirstPages` counts 4,228 bytes on an unencrypted ACE file. Not planned yet; encryption-flat-agile #1, which makes `PageFile.ReadHeaderAsync` return the whole 4,096-byte page, may close it.
- **Concurrent scans on a shared reader in `PageReadOptimizationMode.Disabled` run 12-36% slower than in `Auto`, because every page read the cache misses waits for the reader's I/O gate.** `PageFile.ReadPageAsync` reads positionally through `RandomAccess` only after `EnableRandomAccessPageReadsIfSupported`, which only a path-opened reader in `Auto` or `Enabled` on the net10.0 build calls; otherwise `StreamPageStore` takes its seek gate and reads the shared stream. That covers `Disabled`, every mode of the netstandard2.1 build, and every read through the writer's `Pager`. With `AccessReaderConcurrentScanBenchmarks` on the 25,000-row numeric table (405 data pages, more than the default 256-page cache), `Disabled` was 12-36% slower than `Auto` at 4 and 8 simultaneous scans (8 scans: 23-25 ms against 20-21 ms) and 3-9% slower at one, while separate readers took 34-37 ms for 8 scans in either mode. This is not a bug; if `Disabled` matters under concurrency, positional reads on its `FileStream` would take the gate out of page reads. Not planned yet: re-measure concurrent scans after changes to `StreamPageStore`.
- **The writer opens its file with an overlapped handle and the `RandomAccess` hint.** `AccessWriter.CreateStream` uses `FileOptions.Asynchronous | FileOptions.RandomAccess`, and the writer does not set `PageFile.ReadsInlineOnThreadPool`, so its page reads are always offloaded. On Windows an overlapped read completes through the I/O completion port and a thread-pool callback even when the OS cache holds the page; for path-opened readers that cost 14.8-19.1 µs per warm 4 KB read, against 3.8-4.9 µs on a synchronous handle (read-performance-bottlenecks.md §7). Moving the writer to `FileOptions.None`, and possibly to inline reads, needs insert, update and delete A/B measurements with no transaction, with `UseTransactionalWrites` and in an explicit transaction. Not planned yet: deferred from wave 2.
- **Table scans of tables with Attachment or multi-value columns never read ahead, and that exclusion was never measured.** `TableReader.ShouldReadAheadTablePages` refuses read-ahead when `HasLongValueOrComplexColumns` is true (Memo, OLE, Complex and Attachment columns). For MEMO and OLE the exclusion is measured: in `AccessReaderReadAheadEligibilityBenchmarks`, read-ahead moved warm `Auto` scans of a 5,000-row MEMO table and a 2,000-row OLE table by less than the run-to-run noise at cache sizes 0, 2 and 256, because each row's long-value reads dwarf the one data page the prefetch overlaps, while it took the 25,000-row numeric table from 9.9-10.5 ms to 8.6-8.9 ms at cache sizes 0 and 2. A complex column's cell in the main table is a 4-byte reference, so its cost per row depends on the flat-table reading a scan does. Add an Attachment or multi-value table, with and without items, to that benchmark, and drop ComplexType and AttachmentType from the exclusion if read-ahead gains on them. Not planned yet.
- **Why `FileOptions.SequentialScan` on a synchronous handle defeats the OS read-ahead is not understood.** In the page-I/O investigation, 9,800 sequential 4 KB page reads of a copy the OS had not cached took 47 ms with `FileOptions.None` and 654 ms with `SequentialScan` on a synchronous handle (584 ms with `RandomAccess`, 965-1,040 ms on overlapped handles). Repro: make an uncached copy as `AccessReaderColdScanBenchmarks` does (Windows only: `FILE_FLAG_NO_BUFFERING` and write-through), then time the same sequential reads through a `FileStream` opened with each option. read-performance-bottlenecks.md records it as not understood. Not planned yet.
- **Why core-split-a slowed the 40-column table's warm first row, while one page read per call was handed to the pool, is not known.** `AccessReaderTableScanReadAheadBenchmarks.FirstRow` with `Shape=Wide` and `Temperature=WarmRepeatScan` read the table's TDEF page raw on every call both at 8288373d, before core-split-a, and at bb191440, after it, and BenchmarkDotNet's main thread, which is not a pool thread, hands that read to the pool and waits to be woken. Run back to back on one runner, in both orders, `Enabled` took 28.9 and 32.2 µs per call at 8288373d against 35.4 and 59.4 µs at bb191440, `Auto` 34.3 and 46.0 µs against 34.8 and 58.9 µs, and `Disabled` 35.0 and 58.6 µs against 35.5 and 59.8 µs; an earlier run had every mode 3-6 µs slower at bb191440. The per-call costs that a read of the code found the split adding on that path are sub-microsecond (page-read delegates bound to `IPageSource.ReadPageAsync`, a virtual `CanReadPositionally`, format reads through the profile); the cause was not investigated. The reader's TDEF and owned-page memos take every read off that warm call, so the benchmark no longer shows it, but a cost the split added per hand-off would stay on every read that is still handed off, such as a page-cache miss or a cold read on a thread that cannot read inline. Repro: that benchmark at 8288373d against bb191440 in both run orders (`scripts/ci-gate.ps1 -Benchmarks "*AccessReaderTableScanReadAheadBenchmarks.FirstRow*"` with `-Sha` and `-Baseline` swapped between the two runs), then one offloaded `PageFile.ReadPageAsync` per call from a thread that is not a pool thread, at 8288373d against the current code. Not planned yet.
- **AddColumn, DropColumn and RenameColumn copy every row into a new table.** `TableSchemaEditor.RewriteTableAsync` reads every row into a `DataTable` snapshot, writes them into a new `~tmp_<13 hex digits>` table, and drops the original and renames the copy (or, when the table has complex columns and the edit drops or renames none of them, moves the copy onto the original's TDEF page with `TransplantTempTableToOriginalAsync`), so even a rename costs time and space in proportion to the table. Jackcess's `TableUpdater` adds a column by editing the TDEF in place. Not planned yet: deferred from wave 2, as a separate design that changes the bytes a schema edit leaves.
- **`MinAsync` and `MaxAsync` read every row even when an index orders the column.** They fold every row the query returns as the read streams it, although the first or last entry of an index on the column would answer them; `IndexCursor.TryReadLastEntryAsync`, which `AutoNumberMaintainer` uses, already reads a last entry. Not planned yet: deferred from wave 2.
- **Creating an encrypted database writes it in plaintext first and then re-encrypts the whole file.** `CreateDatabaseAsync` takes no encryption settings, so an encrypted file is created unencrypted and then passed to `EncryptAsync`, which writes the whole file again to `<db>.reenc-<guid>.tmp` and renames it over the original. A `CreateDatabaseAsync` overload that writes the encryption descriptor up front is cheap once wave 2's encryption-flat-agile adds the flat Agile page codec. Not planned yet: deferred from wave 2.

## Design flaws

Each of these needs structural work rather than a local fix; the bugs above are many of their symptoms.

- **The pager still lacks page leases.** Callers own page copies instead of pinned leases. Planned in wave 2: pager-c adds page leases and reader cache integration.
- **Transactions have no crash recovery.** Commit captures raw before-images in memory and restores the original bytes and length after a stream write or flush fails; if restoration fails too, the writer becomes faulted. There is no persistent rollback journal or recovery on open, so a process crash or power loss during replay can still leave a partial transaction in the file. Calls without a transaction are not statement-atomic (the data-loss and partial-write items above). The README's "Transaction durability" limitation describes these gaps. Planned in wave 2: atomicity-b makes every call statement-atomic; crash-journal adds a sidecar rollback journal, on by default for files opened by path or as a `FileStream` that are not CFB containers, with recovery on open.
- **The schema is not a model.** Each column edit (AddColumn, DropColumn, RenameColumn) re-parses the TDEF and `LvProp`, rebuilds `ColumnDefinition`s and `IndexDefinition`s, and writes a new table. Column, index, foreign-key and property projection are separate helpers (`ColumnDefinition.WithName`, `IndexHelpers.ProjectIndexes`, `PersistedPropertyProjector`, and `RelationshipManager`'s capture and relink) rather than edits to one in-process model. Planned in wave 2: schema-model-core and schema-model-c.
- **No write pipeline or real B-tree.** Insert, update, delete, cascades, complex-item adds and schema rewrites each wire the insert, tombstone and index-maintenance primitives by hand, and an update is a delete plus a re-insert. The B-tree has no real insert, delete or merge: index maintenance splices the leaves a write touches in place (up to 64 per index), rebuilds a multi-level tree from its leaves, or rebuilds every index from a snapshot; tables with an FK index always take the full rebuild, and emptied pages are not freed. Planned in wave 2: write-pipeline-a1 (the cascade plan), write-pipeline-a2 (one write path), write-pipeline-b (a real B-tree) and write-pipeline-c (in-place updates).
- **Constraints live in the process, not the file.** Each writer session builds its own constraint registry from the file and its own declarations; a CLR `ValidationRule` delegate cannot be stored, so it binds only the declaring writer (documented, with `ValidationRuleExpression` as the stored alternative). What the writer does not enforce is under "Values that differ" ("The writer does not enforce every constraint stored in the file"). Planned in wave 2: constraints-a and constraints-b.
- **Lossy value model.** Unreadable MEMO and OLE values read as placeholder text or empty arrays, and an unreadable `LvProp` blob as no properties (items above). Planned in wave 2: failure-model-b1.
- **Format knowledge is scattered.** 47 library files import `JetTypeInfo` with `using static`, and its per-type answers (fixed sizes, variable storage, CLR mappings, display names) are spread over separate switches. The immutable `JetFormat` profile answers the per-format layouts, the text codecs and the capability flags, and `FormatKnowledgeTests` keeps `DatabaseFormat` comparisons in JetFormat.cs, Enums/, Encryption/ and the facades, but Jet3 `LvProp` text hard-codes Windows-1252 (above). Planned in wave 2: format-profile-b.
- **The read API does not compose.** `TableReader`'s read loops agree on results but share no scan primitive. `IndexRowReader` returns nothing for linked tables (`ListIndexesAsync`, `EnumerateIndexRowsAsync`). `CatalogReader.ResolveTableAsync` rescans `MSysObjects` for a system table (above). An unknown table reads as empty in the reader, while the writer throws. Planned in wave 2: read-composition-a and read-composition-b.
- **Encryption is not a page layer.** Flat Agile and the CFB Office Crypto formats (Agile CFB and Standard) are decrypted whole into memory on open rather than page by page, and the writer has no page cipher for flat Agile (above). Planned in wave 2: encryption-flat-agile makes flat Agile a page layer, and encryption-containers makes the CFB containers durable and atomic. The CFB containers stay decrypted whole into memory: a segment-addressable reader for them is deferred, not planned in wave 2.
- **Failures are not modeled.** Encryption, corruption and limitation paths still lack complete structured failures, and `LastDiagnostics` is typed only internally. Constraint, lookup, schema, lock and transaction-state refusals already carry error codes, but their coverage does not extend to every deliberate throw. Planned in wave 2: encryption-flat-agile, failure-model-b1 and failure-model-b2.
- **The LINQ layer has no query plan.** Predicates and query plans are compiled per call (the performance item above), and nothing is annotated for AOT or trimming: there is no `DynamicallyAccessedMembers`, `RequiresUnreferencedCode`, `RequiresDynamicCode` or `IsAotCompatible` in the repository. Planned in wave 2: linq-plan-cache and linq-aot.

## Unchecked against Access

Microsoft Access is not installed on any machine the suite has run on, so none of the skip-guarded DAO tests has run. Wave 2 asks for one full DAO run on a host with Microsoft Access before 4.0.0 ships; who provides the host is the one wave-2 decision left to the user. Each item below waits on that run unless it says otherwise, and the Jet3 items need a DAO engine that opens Access 97 files, which the hosts used so far lack.

- **The library's Jet4 RC4 and ACCDB legacy-password schemes may not be what Access writes.** No fixture is a file Access encrypted, so the library's encrypted formats are checked only against themselves. Jet4 RC4 (`AccessEncryptionFormat.Jet4Rc4`) uses flag 0x02 or 0x03 in raw header byte 0x62 plus a header password, and per-page RC4 keyed with `MD5(dbKey ‖ pageNumber)`; mdbtools and Jackcess describe Jet RC4 differently (the encoding key at 0x3E from the unmasked header, XORed with the page number, and no flag at 0x62). The ACCDB legacy password (`AccdbLegacyPassword`) uses flag 0x07 plus a header password, and `AccdbLegacyPasswordMask` is AesEncrypted.accdb's empty-password pattern XOR "secret", but that fixture holds no password: it is a DAO `CompactDatabase` output and a compacted copy of NorthwindTraders.accdb. ACCDB AES-128 in a CFB wrapper is the library's own layout too. Whether Access opens the library's files, or the library opens Access's, is unchecked. The README's Encryption Support section, its feature table and the `AccessEncryptionFormat` docs say so. It needs Access-authored encrypted fixtures or a DAO run.

## Decisions left to the user

- **Who provides a host with Microsoft Access for the DAO run** (under "Before 4.0.0 ships"). It is the one wave-2 decision left to the user.
- **Whether a plain `typeof(decimal)` column on a Jet3 `.mdb` becomes Currency instead of throwing `NotSupportedException`.** `ColumnDefinition.NumericPrecision` defaults to 18 and `NumericScale` to 0, so an undeclared decimal column is Decimal(18,0). On Jet3, `JetTypeInfo.ResolveStorageType` creates a decimal column as Currency and refuses a declaration Currency cannot hold, a scale above 4 or more than `CurrencyIntegerDigits` (14) integer digits, so the default is refused with a message that suggests a declaration that fits, `IsCurrency`, or a double; the same declaration works on Jet4 and ACCDB. Creating Currency anyway needs `NumericPrecision` to tell an undeclared precision from a declared 18, so it would have to become nullable or gain a flag.
- **Whether the scaffolder qualifies its type names with `global::`.** `EntityEmitter.Emit` puts its using directives above a file-scoped namespace and names `DateTime`, `DateTimeOffset`, `TimeSpan`, `DateOnly`, `TimeOnly`, `Guid`, `Hyperlink`, `[Column]` and `[Table]` by their simple names, and C# looks a simple name up in the generated namespace and each enclosing one before those usings. `ScaffoldNames.FindTypeHidingSegment` refuses a `--namespace` segment with one of those names, but the tool cannot see the user's project: with a `MyApp.Hyperlink` class, scaffolding into `MyApp.Data` binds every Hyperlink property to it, and a `MyApp.ColumnAttribute` class or a `MyApp.Guid` namespace gives CS0616 or CS0118. The README's scaffolding section documents this. `global::`-qualified property and attribute types, or `using global::...;` directives inside the namespace, would remove it, but either reverses the decision to keep the usings above the namespace, which stops a segment such as `System` from capturing them.
- **Whether `InsertRowAsync<T>` ignores or rejects a complex cell** read back through `Rows<T>` (the complex-columns item under "Values that differ").

#### Shared names and contracts

- On main since core-split-a, and assumed by every package: `JetFormat` (internal sealed, the one format profile) as `DatabaseFile.Format`, extended later (capability flags, `DefaultTextSortOrder`, `TDefFormat`, `HeaderLayout`, `CodePageSource`, `PropertyTextEncoding`); `Pages/Paging/{IPageSource,PageBuffers,PageFile,Pager}`; `Schema/TableDefReader`; `Pages/{OwnedDataPages,DataPageRows}`; `Tests/Infrastructure/WriteModes.cs`; `EmptyDatabaseBootstrapGoldenTests`.
- Paging: one `IPageSource`; `PageFile` reads, `Pager : PageFile` writes, and the reader never holds a `Pager`. Storage and encryption use `IPageStore`, `StoreCapabilities` and `IPageCodec`. `OwnedPageIndex` tracks data-page owners. Later: `OverlayPageStore` (crash-journal), `ContainerImageStore` (encryption-containers), `PageLease` (pager-c).
- `TableSchema` (`Schema/Models/*`, parsed by `TDefCodec`, cached in `TDefImageCache`, written by `TDefWriter`) is the one per-table model; `ResolvedTable` becomes `(Entry, Schema)`; the reader resolves through `Catalog/TableRegistry`, the writer through `Mutations/WriteTarget`. `TableDef` stays the column layout; nothing is named `TableHandle`.
- `IPageWriteObserver`: `OnPageWritten(long pageNumber, ReadOnlySpan<byte> before, ReadOnlySpan<byte> after)` on every logical page write, in plaintext, `before` empty past the old end; `OnInvalidateAll()` on every rollback, savepoint rollback, statement discard, failed commit, truncate and shrink. Observers take only leaf locks, never call the pager or throw, and register with `Pager.AddWriteObserver` (copy-on-write, called in order).
- `WriterState`, which every rollback restores: the `DataPageInserter` hint, the owned-map policy's sets, the `ConstraintRegistry` snapshot with AutoNumber counters, the `PageAllocator` free set, the catalog (`TableCatalog.Invalidate()` bumps `Generation`) and the observers. New writer-side caches join it.
- After atomicity-b and crash-journal, every public mutation runs in a savepoint frame or a statement transaction whose pages stay in the pager until write-back, so a failure before it, cancellation included, leaves the file byte-identical and an explicit transaction usable. The one write-back, `Pager.CommitAsync`, journals before-images to `<db>-journal` on a journaled file and fsyncs, writes the pages, flushes, then invalidates the journal; a failed undo faults the writer {WriterFaulted}. Statements spill past max(64, PageCacheSize/2) frames and stay atomic. No compensation code: byte-identical fault and crash sweeps prove the failure paths.
- Test infrastructure: `WriteModes`, `CountingStream`, `WriteFaultStream` (FailOnWrite, CancelAfterWrites and CancelAfterReads today; atomicity-b adds ThrowOnceBeforePageWrite, ThrowAlwaysFromPageWrite, ThrowOnFlushCall), `PageAudit`, `LegacyDamageInjector`, `EmptyDatabaseBootstrapGoldenTests` (change a hash only on purpose, naming the bytes).

#### Decisions already made

- Writes: `UseTransactionalWrites` (default false) means durable per call; no statement-journal option; public `PageCacheSize` (default 256); `MaxTransactionPageBudget` limits only explicit transactions.
- Journal: `<db file>-journal`; `UseRollbackJournal` (default true) on path and `FileStream` files that are not containers; one that cannot be created fails the write; a reader of a hot journal gets a pre-crash overlay, or {HotJournalConflict} with nothing changed; a second writer gets {DatabaseInUse} at once; `CreateDatabaseAsync` deletes a stale journal only after `CreateNew`.
- Schema: the reader caches TDEFs for its lifetime, unbounded; VerifyOnHit runs in CI; rewrites keep un-modelled bytes.
- Pipeline: free emptied index pages on user tables only; update in place, keeping unchanged long values; carry unreadable, unassigned MEMO and OLE values raw; a unique non-PK index takes several all-Null keys, which IgnoreNulls omits; cascade updates recurse, and every cascaded row is validated before writing.
- Constraints: an unevaluable default or rule refuses the write {UnsupportedExpression}, with no opt-out; `CurrentUser()` is "Admin"; Guid AutoNumbers get flags 0x43 and `GenGUID()`; malformed declarations throw `ArgumentException`; table rules check the whole post-update row, get a public API and block dropping a column they name.

#### Risks

1. Base drift across 17 mostly serial stages: rebase at the start and find code by symbol.
2. A write that bypasses the pager's scope (the CFB rewrap, Shrink's truncate, direct stream writes) breaks atomicity; keep the fault and crash sweeps green.
3. Stale caches corrupt indexes: one invalidation contract, VerifyOnHit, no reader caches over a writable `PageFile`.
4. Format changes only a DAO run can confirm need Access-fixture or Jackcess evidence and a skip-guarded DAO test.
5. `Assert.Throws<T>` is exact-type: migrate assertions in the commit that changes the type.
6. Two fsyncs per default call on a file (about +2.8 ms on NVMe) and an O(file) container rewrap per call: keep to the benchmark gates, and keep tests off fsyncing temp files where durability is not under test.
7. Access ignores `<db>-journal`, and Unix cannot fsync the journal's directory entry; document both.
8. Wave-1 behaviour must survive: overflow rows, Jet3 LVAL headers and jump tables, explicit-Null inserts, the FK update scope, the DropTable refusal, expression rename rewrites, AutoNumber seeding.
