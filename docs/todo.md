At `6eab703`, none of the bugs from my earlier report was fixed. ## What the five commits fixed
- **The service-locator problem is gone.** Nothing outside the facades takes `AccessWriter`, `AccessReader` or `AccessBase` any more. `WriterServices` and `ReaderServices` now wire everything explicitly, the two dependency cycles are removed, and `ServiceGraphTests` guards this.
- **Duplicate code was merged:**
  - one `TableCatalog` replaces the two `GetUserTablesAsync` copies;
  - the shared index-descriptor helpers live on `IndexCatalogReader`;
  - the row primitives exist only in `TableRowStore`;
  - `AccessWriter` no longer has its own snapshot copies.
- **The row decoders no longer depend on the reader facade.** `RowDecoder` and `LongValueDecoder` now take `DatabaseFile`, and `ReaderPageCache` reads straight through to pending transaction writes when one is active. That makes the main fix below cheap.
- **The concurrency doc now gives the correct `UseTransactionalWrites` default.**
- **No new defects, apart from one small one, now fixed.** A before/after comparison over all 92 test databases found identical results. The only change was that the "Total rows scanned" diagnostic also counted catalog rows it couldn't decode (25 became 28 on one fixture). It affected only the diagnostic text; see "Fixed since 6eab703". The 28 later turned out to be right; see the row-bound entry.

## Fixed since 6eab703
- **Bug 1: a large MEMO dropped the rows after it on the same data page.** One ~1.4 MB MEMO row plus 29 small rows made `Rows()` return 1 of 30 rows. `ReaderPageCache` gave evicted pages back to the shared pool while a scan still read them, so the next page read overwrote the scan's data page. It now leaves evicted pages to the GC, and `LruCache` no longer has an eviction callback. `AccessReaderCacheTests.Rows_WhenLongValueChainEvictsCurrentDataPage_ReturnsEveryRow` covers it. The read-ahead guards that worked around this bug have since been re-evaluated; see the read-ahead entry at the end of this section.
- **Bug 3: any commit on a Jet4 `.mdb` made it reopen as ACCDB.** `TransactionLifecycle.CommitTransactionAsync` incremented page-0 offset `0x14` after every commit, treating it as a "commit lock byte". That byte is the format version (0 = Jet3, 1 = Jet4, 2 or more = ACE), so two commits turned a Jet3 or Jet4 file into ACCDB, and every ACCDB commit changed its ACE version. `BumpCommitLockByteAsync` is gone, along with the tests that asserted the bump. The cooperative commit-lock byte-range sentinel is unchanged. `JetTransactionTests.Commit_PreservesPageZeroFormatVersionByte` covers Jet3, Jet4 and ACCDB.
- **Bug 9: a cancelled `InsertRowsAsync` left its rows on disk without index entries.** `TableDataWriter.InsertPreparedBatchAsync` ran its cleanup on the cancelled token, so the cleanup threw on its first page read and the rows written so far stayed live. A cancel could also land inside a single row's writes, after the data page and before the TDEF row count, leaving a row the cleanup never recorded. Cancellation is now checked only between rows. Each row write and the index maintenance after the loop run to completion once started, and the cleanup runs without a token. It now also swallows I/O failures, as its doc comment always claimed. `AccessWriterTests.InsertRows_CancelledWhileWritingRows_RollsBackBatch` and `InsertRows_CancelledDuringIndexMaintenance_CompletesBatch` cover it.
- **Bug 12: `ReadTableAsync<T>` returned no rows when `T` bound an Attachment or multi-value column.** `TableReader.ReadTableAsync<T>` had its own two scan loops (full map and projected). Neither resolves complex columns, so it skipped both whenever `T` bound one, then fell through to the linked-table lookup, which returns nothing for a native table. It now collects from `EnumerateMappedRowsAsync`, the same decoder choice `Rows<T>` streams from, and honours `maxRows`. The two private loops are gone. Separately, `Rows<T>` threw `InvalidCastException` ("Object must implement IConvertible") when an `object` property was bound to a `byte[]` or complex cell. `RowMapper.CoerceToTarget` now passes through any value the property can already hold, as `RuntimeRowMapper` does. `ReadSurfaceConsistencyTests.ReadTableGeneric_BoundAttachmentColumn_*` and `ReadTableGeneric_BoundMultiValueColumn_ReturnsSameRowsAsRowsGeneric` cover it.

- **Transactions not atomic (partly fixed): cancellation could tear a commit, a torn commit was reported as rolled back, and the docs claimed atomic before-image journaling.** `CommitTransactionAsync` checked the caller's token before every replayed page. A cancel during the commit therefore left part of the transaction in the file and marked it rolled back, and I/O failures after replay started were reported the same way. A token that was already cancelled threw before the journal was detached and left the transaction active. Cancellation is now honoured only until the first page write starts; after that, the replay and the flush run with `CancellationToken.None`. A token that is already cancelled now ends the transaction as a rollback, so a caller can no longer retry `CommitAsync` on the same transaction. A failure before the first page write starts is a clean rollback: `IsRolledBack` is true and the writer state is restored as for a rollback. A failure after it leaves both `IsCommitted` and `IsRolledBack` false, makes `RollbackAsync` throw, and drops the writer's catalog and insert-hint caches; the constraint registry is kept, so AutoNumber counters never move back over IDs that may be on disk. No public API was added. The `PageJournal` budget message no longer claims the transaction was rolled back. The XML docs, the README, `library-structure.md` and `concurrency-and-lock-ordering.md` now describe what happens: after-images are buffered in memory and written in place, which is not crash-atomic. `JetTransactionTests.Commit_WhenCancelledAfterReplayStarts_CompletesReplay` (ACCDB, Jet4, AES-CFB wrapped ACCDB) and `Commit_WithCancelledToken_RollsBackWithoutWritingPages` cover it. `Commit_WhenReplayWriteFails_LeavesSuccessfulReplayPrefixOnDisk` and `Commit_WhenDurableFlushFails_IsNeitherCommittedNorRolledBack` (renamed from `..._MarksRolledBackAfterReplay`) used to pin the "rolled back" report and now assert that `IsRolledBack` is false.

There are no savepoints, so a failed operation inside an explicit transaction stays half-applied in its journal. Writer reads inside a transaction now see the journal (bugs 2 and 5–8, below).

- **Bugs 2, 5, 6, 7 and 8: the writer's reads inside a transaction did not see the transaction's own writes.** Every workflow that reads a table before changing it (update, delete, cascades, full index rebuilds, AddColumn/DropColumn/RenameColumn, AutoNumber seeding, unique checks and relationship enforcement) decoded rows through `TableSnapshotReader`. That class opened a separate uncached `AccessReader` with no journal, and the writer paired its rows by position with row locations read through the journal. So a delete then an update in one transaction rewrote the wrong row, AddColumn dropped the rows inserted earlier in the transaction, a relationship created in the transaction was not enforced, and a cascade delete under `UseTransactionalWrites` left the child's primary-key and foreign-key indexes pointing at the wrong rows. The same cause hid the rows of a bulk insert in a transaction from the index rebuild that runs after the batch, so a seek on a secondary index found none of them (the re-check agents' "bulk insert inside a transaction" entry, now removed). Double and Single columns now parse their own literal exactly.
  - One default in every writer. The declaring writer applied the CLR object, while a reopened writer applied its persisted literal, so they differed whenever the literal did not round-trip: 0.1f on a Double column, 1e-30, or a DateTime with milliseconds. The declaring writer now applies what the literal reads back as, and NaN or infinite defaults are rejected.
  - Tests. `InsertDefaultSemanticsTests` covers every insert shape on Jet3, Jet4 and ACCDB, with a persisted and a CLR default, in the declaring and a reopened writer: explicit nulls stored as NULL, omitted columns and `DbDefault.Value` getting the default, NOT NULL rejection, AutoNumber and calculated columns, and updates rejecting `DbDefault.Value`. `ColumnConstraintTests` covers the rejected defaults on generated columns, a DBNull default, the same CLR default in both writers on all three formats, and non-finite defaults; `AutoNumberTests.AutoIncrement_StrayDefaultValueProperty_IsIgnoredAfterSchemaRewrite` runs on all three formats in every write mode; `ConstraintRegistryTests` checks exact Double and Single defaults over 5,000 random values.
- **Dropping a table in a relationship left its partners pointing at a freed page.**
  - The bug. `DropTableAsync` never looked at relationships. It deleted the table's `MSysObjects` rows and freed every page, TDEF included, while the `MSysRelationships` rows stayed and every partner's FK entry kept naming the freed page. After dropping a parent, every child insert or update with a non-null key was rejected because the parent could not be found; after dropping a child, parent deletes and key updates threw "Table ... was not found". Once a new table reused the page, the stale entries named that unrelated table, and a later schema rewrite re-emitted them, as a bogus self-reference when the copy landed on the page. `DropRelationshipAsync` could not clean up afterwards, because it skips a relationship whose table is missing. This held on Jet3, Jet4 and ACCDB, including Access-authored files (NorthwindTraders Companies, indexTestV2000 Table1, indexTestV1997 Table2, nwind Orders).
  - The fix. Access refuses such a drop: DAO `TableDefs.Delete` and `DROP TABLE` fail with error 3303, "currently participates in one or more relationships". `DropTableAsync` now throws `InvalidOperationException` naming every relationship, before anything is written, whenever any `MSysRelationships` row names the table, including relationships without referential integrity and self-relationships. The caller drops the relationships first. A table can still hold FK entries that no `MSysRelationships` row names, left by earlier builds or a hand-edited catalog. Dropping it now removes every partner entry that names its page before the page is freed (`RelationshipManager.RemovePartnerLinksAsync`); an entry on a page that now holds an unrelated table is left alone.
  - Schema rewrites. Files that earlier builds wrote can still hold FK entries naming a freed page, or the unrelated table that took it. AddColumn, DropColumn and RenameColumn re-emitted every FK entry of the rewritten table unchanged, so such an entry kept naming the freed page, and became a bogus self-reference when the copy took that page, as it usually does. The public API had no way to remove it. `RelationshipManager.CaptureForRewriteAsync` now keeps only entries whose partner links back (`PartnerLinksBackAsync`), and drops the rest; the `MSysRelationships` rows stay, so the relationship is still listed and enforced. A rewrite of the partner then drops its one-sided entry in turn.
  - Tests. `DropTableRelationshipTests` checks that the refusal leaves the file byte for byte unchanged for parent and child, keeps an explicit transaction usable, covers self-referencing, non-enforced and same-transaction relationships and the Access-authored tables above, and that after `DropRelationshipAsync` the drop succeeds in every write mode with no FK entry naming the freed page, even once a new table takes it. Orphan FK entries are unlinked on Jet3, Jet4 and ACCDB, and a rolled-back drop restores them. The new `ForeignKeyLinks` helper checks that every link in a file is reciprocal. `RelationshipSchemaRewriteTests.SchemaRewrite_OfTableWithDanglingForeignKeyEntry_DropsTheEntry` (Jet4, ACCDB) and its Jet3 counterpart on indexTestV1997.mdb check that a dangling entry is dropped while the valid links are re-linked. `DaoRelationshipDropTests` records what DAO does with the same drops; it skips without Microsoft Access.
  - Follow-up: the removed entries' index leaves stay allocated until Compact & Repair, as after `DropRelationshipAsync`.

## Open: found while fixing
The Jet3 long-value bug and the UTF-8 text of new Jet3 databases, which were listed here, are fixed; see "Fixed since 6eab703". These were found while the follow-ups were investigated or fixed. Each says whether its fix is in progress, planned or waiting on evidence:
- **An update whose re-insert fails loses the row.** An update deletes the row and then inserts its new version, and if the insert throws, the delete stays. One way to hit it is an update that grows a row past one data page, which now throws `JetLimitationException`; the README says to use `UseTransactionalWrites` or a transaction for such updates. Planned with the write-atomicity work (wave 2).
- **The library's Jet4 RC4 and ACCDB legacy-password schemes may not be what Access writes.** No Access-authored encrypted Jet4 or legacy-password file is among the fixtures: AesEncrypted.accdb, which the legacy-password scheme was built from, turned out to hold no password (see the header-password entry), and mdbtools and Jackcess describe Jet RC4 differently. The writer reads and writes these schemes consistently, but whether Access opens its files, or the writer opens Access's, is unchecked. It needs Access-authored encrypted fixtures or a DAO run.
- **A full index rebuild of a large index throws `NotSupportedException`.** `UsageMap.WriteInlineRow` writes an index's `used_pages` map only in the inline form, and throws "REFERENCE usage maps for index pages are not yet supported" when the rebuilt B-tree's pages span more than one inline bitmap window. The tooling benchmarks hit it twice: `CreateRelationshipAsync` over 20,000 Orders rows that already have two indexes, and the 338th `AddAttachmentAsync` on an 800-row table. Any table with a foreign-key index takes the full rebuild on every write, so a large child table can reach it. b2d6b49 fails the same way. Planned with the owned usage-map work (wave 2, pager-b).

## Design flaw status
| Flaw | Status | What changed |
|---|---|---|
| Facade is the engine / service locator | **Partly resolved** | Locator and cycles are gone. `DatabaseFile` (about 1,470 lines, injected into about 35 types) is the new catch-all: pager, transaction journal, encryption and table-definition parsing in one class. |
| Reader and writer are separate engines | **Resolved** | The writer no longer opens a second `AccessReader` over its own file. `TableSnapshotReader` decodes through the shared `RowDecoder`, `LongValueDecoder` and `CatalogReader` over the writer's own `DatabaseFile`, so its reads see the transaction journal (bugs 2 and 5–8 fixed). Each decoded row comes back with its location (`LocatedRow`), so nothing pairs rows and locations by position any more. |
| No pager or buffer manager | Open, critical | The cache moved into `ReaderPageCache`, and its eviction bug (bug 1) is now fixed, so table-scan read-ahead no longer needs a cache of at least three pages. There is now one journal-aware end of file, `DatabaseFile.PageCount`, used by every page-number bound and every caller that numbers new pages (see the end-of-file entry above). The writer still has no page cache, and there are no page leases or pins. |
| Transactions not atomic | Open, critical | Rollback no longer breaks the writer: it restores the cached catalog, insert hint and constraint registry (bugs 10–11 fixed). Cancellation can no longer tear a commit, a commit that fails after it started writing pages is no longer reported as rolled back, and the docs now say commit writes in-memory after-images in place, which is not crash-atomic. The format-byte bump is fixed (bug 3). The writer's own reads inside a transaction now see its pending writes (bugs 2 and 5–8). Still no WAL or before-image, so a crash or I/O failure during replay tears the file, and no savepoints. |
| Schema isn't a model | Open | Three duplicate parsers merged. The index paths now read the whole TDEF chain and share `IndexCatalogReader.LocateRealIdxDescStart` instead of their own column-name walks, and in-place TDEF patches go through `LogicalTDefChain.WriteInPlaceAsync` (the wide-table fixes above). Schema rewrites now copy each column whole (`ColumnDefinition.WithName`), project indexes through one `IndexHelpers.ProjectIndexes` that keeps every flag, and carry the table's foreign-key indexes and partner links. There is still no in-process schema model, and DropTable and RenameColumn still miss relationships and calculated expressions respectively (follow-ups above). |
| No write pipeline or real B-tree | Open | Moved into `TableDataWriter`. Update and delete now change exactly the rows they decoded (`LocatedRow`), and updates run the NOT NULL, AutoNumber and rule checks on the columns they assign. Each operation still wires the insert, tombstone and index-maintenance primitives by hand, an update is still a delete plus re-insert, and the B-tree algorithms are unchanged apart from the multi-level rebuild reserving its pages through `PageAllocator` (end-of-file entry). |
| Constraints live in the process, not the file | **Partly resolved** | Every writer now loads the column `DefaultValue`, `ValidationRule` and `ValidationText` from `MSysObjects.LvProp` and enforces them, including those Access wrote, and a CLR `DefaultValue` applies after reopen. Updates run the NOT NULL, AutoNumber and rule checks on the columns they assign (bug 4). A rollback restores the registry (bugs 10–11). AutoNumber seeding now reads the TDEF counter, so IDs are no longer reused across sessions or schema rewrites. Still open: a CLR `ValidationRule` delegate binds only the writer that declared it; expressions the calculated-column engine can't evaluate and table-level rules are skipped; and the registry still skips every check on a table whose constraint list doesn't line up with the TDEF column count. |
| Lossy value model | Open | Complex-column cells are no longer lossy: `Rows()` and the other row reads return every attachment, decoded, and every multi-value item (see "Fixed since 6eab703"). Updates, cascades and schema rewrites no longer lose data either: the writer's snapshot carries OLE bytes exactly and refuses a MEMO or OLE value it cannot read instead of storing placeholder text. The OLE signature heuristic on the normal read path is unchanged, and a multi-value Decimal still loses its scale. |
| Format knowledge scattered | Open | The TDEF header offsets (row count, AutoNumber counter, table type, column and index counts, usage-map pointers, and now the complex AutoNumber) live per format in `TDefHeaderLayout`, and the Jet4-only constants that corrupted Jet3 headers are gone. LVAL pages follow a per-format `LvalPageLayout`, which fixed Jet3 long values. Elsewhere no change: files importing `JetTypeInfo` went from 35 to 40 in the five commits and are 41 now. |
| Read API doesn't compose | Open | Moved into `TableReader`. The read loops now agree on which rows they return, on `maxRows` and on calculated-column types (bug 12 and the drift fix above), but they are still separate loops with no shared scan primitive. `IndexRowReader` still returns nothing for linked tables (`ListIndexesAsync`, `EnumerateIndexRowsAsync`), `CatalogReader.ResolveTableAsync` still re-reads the TDEF uncached and rescans MSysObjects, and unknown tables still read as empty, unlike the writer. |
| Encryption isn't a page layer | Open | Opening a file now reads only page 0 to detect flat Agile, and the writer refuses flat Agile instead of corrupting it. The cached AES page transforms now run under their own lock, so concurrent page reads on an AES file no longer fail. Flat Agile and the CFB Office Crypto formats are still decrypted whole into memory, and the writer still has no page cipher for flat Agile. |
| Failures aren't modeled | Open | `LastDiagnostics` is now built from a typed record internally. Index paths that silently skipped an index they could not parse now throw `JetLimitationException`, a MEMO or OLE value the writer cannot read refuses the write (`InvalidDataException`) instead of storing placeholder text, and a commit that fails after it starts writing is reported as neither committed nor rolled back. `JetLimitationException` is still the only custom exception type. |
| No CI; untested netstandard2.1 build | **Resolved** | `ci.yml` builds the solution in Release with every analyzer as an error and runs the suite on net10.0 and on net8.0, which loads the netstandard2.1 build, on every push to main and every pull request. A release tag publishes the package that run built and tested, versioned from the tag by MinVer, with package validation (CI parts 1–4). CI runs on Windows only. |
| LINQ layer has no mapping model | **Partly resolved** | It depends on reader services instead of the facade, which makes a package split easier. `EntityMap` is now the one mapping model: every typed path maps properties to columns through it, honouring `[Column]`, `[NotMapped]` and `[Table]`. There is still no query plan: reads compile materializers per call, `RowMapper` and `RuntimeRowMapper` coerce values differently, the IQueryable surface runs sync-over-async, the index walk builds a `List` instead of streaming, and nothing is annotated for AOT. |

## Suggested next steps
1. **Finish the follow-up fixes (wave 1, in progress).** Every follow-up was reproduced and given a fix plan, and the fixes are being made in sixteen groups. Each group lands with regression tests, as described in the intro. Already on main:
   - the Jet3 long values, the row-bound bug, overflow rows, the system-table lookup, reading and writing Jet3 rows longer than 256 bytes, and the one-page row-size limit;
   - encryption detection from the unmasked header password, the header `DecryptAsync` leaves, one open per `AccessWriter.OpenAsync(path)`, and the Jet3 header and code page of new databases;
   - `RenameColumnAsync` rewriting the expressions that name the column, `DropColumnAsync` refusing a column an expression names, and the check order of `CreateTableAsync` and `AddColumnAsync`;
   - `DropTableAsync` refusing a table in a relationship, as Access does, and schema rewrites dropping dangling FK entries;
   - defaults: an explicit NULL stores NULL and `DbDefault.Value` asks for the default, floating-point defaults are exact and the same in every writer, and generated columns take no default;
   - complex columns: index keys, references, the ComplexID counter, Access's attachment format, type names and version-history timestamps;
   - calculated-column result types and the expression semantics;
   - the index page-run release, the ACCDB 302-table limit and Jet3 foreign-key entries;
   - the CI, publishing and versioning work, the dead-code removal and the missing benchmarks.

   For these, see the last entries of "Fixed since 6eab703". Still to land, with the data-loss and corruption bugs first:
   - A Jet3 decimal and a multi-value Decimal both store 12.34 as 12 (RenameColumn and complex-cell entries). A decimal on Jet3 will become Currency (decimal-scale).
   - The rest: Access object-name validation and scaffolder name collisions (names-scaffold); the foreign-key check on updates that don't change the key, seen on Northwind (northwind-fk); relationship caching and the AutoNumber seed scan (perf-followups); and `RandomAccess` page reads (randomaccess-perf).
2. **Make every write atomic and crash-safe (wave 2).** Without a transaction, update and delete on a wide table written by an earlier build apply their row changes and then throw. A cascade update to two child tables can stop after the first (wide-table and OLE entries), and an update whose re-insert fails loses the row. This comes with the transactions design flaw:
   - statement-level savepoints;
   - a sidecar rollback journal, on by default for path-opened files, so a crash during commit can be rolled back;
   - recovery when the writer opens the file.
3. **Close the remaining design flaws (wave 2).** The plans for the twelve open rows of the table above are merged into one ordered roadmap. It starts with splitting `DatabaseFile` and a real pager, which also writes REFERENCE usage maps for large tables and large indexes, then write atomicity, the schema model, the write pipeline, read composition, encryption as a page layer, typed failures, the format profile and the LINQ query plan.

The per-claim results, with current file:line evidence and fix notes for all 14 flaws, are in `scratchpad\recheck.json` and `scratchpad\recheck-digest.md`.
