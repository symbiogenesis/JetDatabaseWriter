None of the bugs from my earlier report is fixed at `HEAD` (6eab703). The five commits fixed the code's structure, not its behaviour. I re-ran my four repros against a fresh build of `HEAD` and all four still fail. Re-checking the code also turned up nine more data-loss or corruption bugs, which I ran myself. The test suite passes (3,832 passed, 29 DAO tests skipped, as usual), but no test covers any of these bugs.

## What the five commits fixed
- **The service-locator problem is gone.** Nothing outside the facades takes `AccessWriter`, `AccessReader` or `AccessBase` any more. `WriterServices` and `ReaderServices` now wire everything explicitly, the two dependency cycles are removed, and `ServiceGraphTests` guards this.
- **Duplicate code was merged:**
  - one `TableCatalog` replaces the two `GetUserTablesAsync` copies;
  - the shared index-descriptor helpers live on `IndexCatalogReader`;
  - the row primitives exist only in `TableRowStore`;
  - `AccessWriter` no longer has its own snapshot copies.
- **The row decoders no longer depend on the reader facade.** `RowDecoder` and `LongValueDecoder` now take `DatabaseFile`, and `ReaderPageCache` reads straight through to pending transaction writes when one is active. That makes the main fix below cheap.
- **The concurrency doc now gives the correct `UseTransactionalWrites` default.**
- **No new defects, apart from one small one, now fixed.** A before/after comparison over all 92 test databases found identical results. The only change was that the "Total rows scanned" diagnostic also counted catalog rows it couldn't decode (25 became 28 on one fixture). It affected only the diagnostic text; see "Fixed since 6eab703".

## Fixed since 6eab703
- **Bug 1: a large MEMO dropped the rows after it on the same data page.** One ~1.4 MB MEMO row plus 29 small rows made `Rows()` return 1 of 30 rows. `ReaderPageCache` gave evicted pages back to the shared pool while a scan still read them, so the next page read overwrote the scan's data page. It now leaves evicted pages to the GC, and `LruCache` no longer has an eviction callback. `AccessReaderCacheTests.Rows_WhenLongValueChainEvictsCurrentDataPage_ReturnsEveryRow` covers it.
  - Follow-up: the read-ahead guards in `TableReader.ShouldReadAheadTablePages` (a cache of at least 3 pages, and no MEMO, OLE or complex columns) worked around this bug. They can probably be relaxed now, after benchmarking.
- **Bug 3: any commit on a Jet4 `.mdb` made it reopen as ACCDB.** `TransactionLifecycle.CommitTransactionAsync` incremented page-0 offset `0x14` after every commit, treating it as a "commit lock byte". That byte is the format version (0 = Jet3, 1 = Jet4, 2 or more = ACE), so two commits turned a Jet3 or Jet4 file into ACCDB, and every ACCDB commit changed its ACE version. `BumpCommitLockByteAsync` is gone, along with the tests that asserted the bump. The cooperative commit-lock byte-range sentinel is unchanged. `JetTransactionTests.Commit_PreservesPageZeroFormatVersionByte` covers Jet3, Jet4 and ACCDB.
- **Bug 9: a cancelled `InsertRowsAsync` left its rows on disk without index entries.** `TableDataWriter.InsertPreparedBatchAsync` ran its cleanup on the cancelled token, so the cleanup threw on its first page read and the rows written so far stayed live. A cancel could also land inside a single row's writes, after the data page and before the TDEF row count, leaving a row the cleanup never recorded. Cancellation is now checked only between rows. Each row write and the index maintenance after the loop run to completion once started, and the cleanup runs without a token. It now also swallows I/O failures, as its doc comment always claimed. `AccessWriterTests.InsertRows_CancelledWhileWritingRows_RollsBackBatch` and `InsertRows_CancelledDuringIndexMaintenance_CompletesBatch` cover it.
- **Bug 12: `ReadTableAsync<T>` returned no rows when `T` bound an Attachment or multi-value column.** `TableReader.ReadTableAsync<T>` had its own two scan loops (full map and projected). Neither resolves complex columns, so it skipped both whenever `T` bound one, then fell through to the linked-table lookup, which returns nothing for a native table. It now collects from `EnumerateMappedRowsAsync`, the same decoder choice `Rows<T>` streams from, and honours `maxRows`. The two private loops are gone. Separately, `Rows<T>` threw `InvalidCastException` ("Object must implement IConvertible") when an `object` property was bound to a `byte[]` or complex cell. `RowMapper.CoerceToTarget` now passes through any value the property can already hold, as `RuntimeRowMapper` does. `ReadSurfaceConsistencyTests.ReadTableGeneric_BoundAttachmentColumn_*` and `ReadTableGeneric_BoundMultiValueColumn_ReturnsSameRowsAsRowsGeneric` cover it.
  - Side effect: for a table with complex columns, `ReadTableAsync<T>` now loads the complex data and decodes every column even when `T` binds no complex column, as `Rows<T>` already did. The deleted projected loop skipped that work.
- **Drift between the `TableReader` read loops: counts, calculated columns and `maxRows` disagreed across APIs.**
  - `GetRealRowCountAsync` walked the raw row-offset table. It counted rows that every read skips because their layout doesn't parse, such as a row with a column count of 0, and `Query<T>().Count()` uses the same count. It also threw `ArgumentOutOfRangeException` on a data page whose row count runs past the page. It now uses the shared page enumerator and the cached live-row bounds, and counts only rows that the new `RowDecodePlan.CanDecodeRow` accepts, which is the same check the typed, string and direct decoders apply. This also fixes a real overcount in Access-produced files: delTestV2000.mdb and delTestV2003.mdb counted 2 rows where every read returns 1.
  - `ReadFirstTableAsStringsAsync` skipped the catalog's calculated-column result types, so a calculated Double read as `4.117213714E-315` instead of `83333.3333`. It now delegates to `ReadTableAsStringsAsync`.
  - `ReadTableAsStringsAsync` now also goes through `EnumerateTableScanPagesAsync`, and reports progress when it stops at `maxRows`.
  - `maxRows: 0` returned one row from every bounded read, native and linked text. It now returns none, and DataTables keep their columns.
  - `ReadSurfaceConsistencyTests` covers this on Jet3, Jet4 and ACCDB: `ReadApis_RowWithZeroColumnCount_AllSkipItAndAgreeOnCount` reads a zero-column-count row through all 10 APIs with read-ahead on and off, `ReadApis_DataPageRowCountPastPageCapacity_AgreeOnCount` uses an overfull row count, `ReadApis_MaxRowsZero_ReturnNoRows` checks `maxRows: 0`, and `ReadFirstTableAsStrings_CalculatedColumns_MatchesReadTableAsStrings` uses the calculated-column fixture. Two `LinkedTextTableTests` gain `maxRows: 0` checks.
- **"Total rows scanned" in `LastDiagnostics` counted catalog rows it could not decode.** `TableCatalog.ScanAsync` reported `rows.Count` from `CatalogRowReader.GetCatalogRowsAsync`, which returns a `CatalogRow` for every live `MSysObjects` slot, including rows too short or malformed to decode. `CatalogScanSummary` documents the value as the rows decoded. So indexTestV2003.mdb printed 28 instead of 25, and unsupportedFieldsTestV2007.accdb printed 38 instead of 35. `CatalogRow` now has an `IsDecoded` flag. `CatalogRowReader` sets it with the same skip rules as `RowDecodePlan.CanDecodeRow`: the row is shorter than the column-count field, has a column count of 0, or has a layout that does not parse. The scan counts only decoded rows, and also stops looking for user tables in undecodable ones, as the reader did before 60403d1. The user table list is unchanged on all 92 fixtures. Undecodable rows stay in the list, so `CatalogWriter`, `DataPageInserter` and `ComplexColumnManager` still see every live slot. `CatalogDiagnosticsTests.ListTables_Diagnostics_CountsOnlyDecodableCatalogRows` pins 25 and 35 on those fixtures, and `ListTables_Diagnostics_RowsScannedMatchesMSysObjectsRowCount` checks that the count equals the `MSysObjects` row count from the table reader on Jet3, Jet4 and ACE fixtures.
  - Follow-up: on Jet3 and Jet4 databases the writer creates, `ReadDataTableAsync("MSysObjects")` returns an empty table with no columns, because `MSysObjects` can't be found by name there. This predates the fix, and it is why the second test uses only Access-authored fixtures.
- **`Rows()` lost attachments and multi-value items, and attachments stayed compressed.** `ComplexColumnReader` read each flat child table as strings and joined it on the flat table's own AutoNumber key (`<table>_<column>`) instead of the `_<column>` back-reference to the parent's complex slot. Each parent got at most one attachment, chosen by AutoNumber rather than by owner, so a parent with two attachments showed one, rows with no attachments showed someone else's, and Access's zlib-compressed `FileData` came back still compressed. Multi-value and version-history cells were always DBNull. `GetAttachmentsAsync` had two bugs of its own. It read `FileData` through the OLE decoder, whose signature sniffing cuts off everything before a file magic it finds, for example `FF D8 FF` inside a raw jpg. And `AttachmentWrapper` only inflated raw deflate, so compressed attachments written by Access came back still compressed. Flat tables are now read through one typed path in `ComplexColumnReader` that returns OLE bytes as stored (`RowDecoder.EnumerateRawOleTypedRowsForTdefAsync`), and joined on the `_<column>` column. That column is matched by exact name first; the old "first Long starting with `_`" fallback now skips the flat table's AutoNumber, which also starts with `_` when the parent table's name does. The `Get*Async` APIs and the row cells share this path. A complex cell is still `byte[]`, and it now holds every attachment (decoded data, name, type, URL, timestamp) or every value of the parent row. The new public `ComplexCellValue.ReadAttachments` / `ReadMultiValueItems` decode it. A row with no items reads as DBNull, and `RowsAsStrings` / `ReadTableAsStringsAsync` return the cell as a base64 data URI instead of `__CX:N__`. `AttachmentWrapper.TryDecode` now accepts zlib bodies. A damaged `MSysComplexColumns` or `MSysObjects` is still traced rather than failing the read, and the scan falls back to finding the flat table by name. `ComplexColumnsRowReadTests` covers writer-created attachments, including a raw jpg containing a JPEG signature, and int and text multi-values, read through `Rows()`, `ReadTableAsync`, `Rows<T>`, `Rows<T>(predicate)` and the string paths. The same class tests the Access-authored complexDataTest, ComplexFields and Northwind fixtures. `ComplexColumnsRowApiTests.AttachmentWrapper_TryDecode_AcceptsAccessZlibWrappedBody` covers the zlib decode.
  - Follow-up: `ColumnMetadata.TypeName` still reports "Attachment" for every complex column, including multi-value and version-history columns. A version-history cell carries only the history text, not the flat table's `Modified` timestamp. The writer stores attachments as raw deflate with `dataLen` set to the compressed length, while Access writes zlib with the uncompressed length; whether Access reads the writer's attachments is unchecked.
  - Follow-up: a multi-value Decimal written as 12.34 reads back as 12 from both `GetMultiValueItemsAsync` and the cell, so the precision is lost in the write or decode path, not in the row read.
- **Opening a database read the whole file, and the writer opened flat-Agile files it could not write.** `EncryptionManager.TryDecryptAgileCompoundFileAsync` loaded the entire file into memory on every `AccessReader` open, only to look for a flat-Agile descriptor in page 0. A 3.17 MB file read 3.17 MB per open, a path-based writer open paid it again through its password check, and one `UpdateRowsAsync` read about 5× the file. The writer never checked for flat Agile, so it opened such a file, appended unencrypted pages to the AES-CBC encrypted file, and then failed with misleading errors. The probe now reads only page 0, through a shared `ReadHeaderPageAsync` that `DetectEncryptionFormatAsync` and the new `IsFlatAgileEncryptedAsync` also use, and reads the whole file only after it finds a flat-Agile header. A reader open of a 3.17 MB ACE file now reads 4,228 bytes, and one `UpdateRowsAsync` reads about 2× the file; the rest was `TableSnapshotReader` re-opening and scanning the file, which the fix for bugs 2 and 5–8 below removed. `OfficeCryptoAgile.TryGetFlatEncryptionInfo` now checks the descriptor length against the end of page 0, so a length that runs past page 0 returns false instead of throwing `ArgumentException`. Both `AccessWriter.OpenAsync` overloads throw `NotSupportedException` for flat Agile before checking the password, taking a lock-file slot or writing anything; the message points at `DecryptAsync` / `EncryptAsync` and `AccdbAgileCfb`. The README and the `AccessEncryptionFormat.AccdbAgile` doc no longer call flat Agile a writer target, and say that `EncryptAsync`'s default `.accdb` target is this format. `EncryptionOpenProbeTests` covers it: `ReaderOpen_ReadsOnlyTheFirstPages` and `WriterOpen_ReadsOnlyTheFirstPages` count the bytes read on Jet3, Jet4 and ACE files (unencrypted, RC4, ACCDB legacy password and AES-CFB wrapped) and allow at most four pages; `IsFlatAgileEncrypted_RecognisesPageZeroAlone` and `IsFlatAgileEncrypted_DescriptorLengthPastPageZero_ReturnsFalse` cover the page-0 probe; and the `WriterOpen_FlatAgilePath_*` and `WriterOpen_FlatAgileStream_*` tests open flat Agile with the right, wrong or no password and check that the bytes, the stream and the lock file are unchanged.
  - Follow-up: `AccessWriter.DetectEncryptionFormatAsync` reports `Jet4Rc4` for an unencrypted Jet4 `.mdb` the writer created, so `EncryptAsync` on such a file throws "already encrypted (Jet4Rc4)". `EncryptionConverter.DetectFlatFormat` tests bit 0x02 of header byte 0x62 before unmasking it. Access-authored Jet4 files are unaffected, which is why the RC4 cases use AdventureWorks. This predates the fix.
  - Follow-up: the path overload of `AccessWriter.OpenAsync` reads page 0 three times: in `ThrowIfFlatAgileAsync`, in the password check's `AccessReader` open, and in the stream overload. Each read is 4 KB.
- **Updating an unrelated column stripped a leading prefix from an OLE value.** `UpdateRowsAsync`, cascade updates and `AddColumnAsync`/`DropColumnAsync`/`RenameColumnAsync` delete each row and insert it again from the writer's snapshot. `TableReader.ReadDataTableForSchemaRewriteAsync` decoded that snapshot with the public read rules, so OLE cells went through `OleObjectDecoder.DecodeOleValueBytes`. An OLE 1.0 package was replaced by its embedded file, and a value with a file signature after a prefix (`00 01 42 4D ...`, `%PDF` after a header) lost the prefix. A MEMO whose LVAL data could not be read decoded to `(memo on LVAL page)` or `(memo chain error: ...)`, and that text was written back as data. The snapshot now uses `RowDecodePlan.CreateTypedForWriteBack`, which reads OLE as the stored bytes, inline and from LVAL rows and chains (`LongValueDecoder.ReadLongValueBytesExactAsync`), and types the MEMO and OLE columns as `object`. The public read API still unwraps packages and slices at signatures. A MEMO or OLE value that cannot be read becomes an `UnreadableLongValue`. An update, a schema rewrite and `IndexMaintainer.RewriteSystemTableRowsAsync` then throw `InvalidDataException` before any row of the table changes, and a cascade update checks each child table before rewriting that table's rows. Assigning a new value to the unreadable column, or dropping it, still works, and inserts and deletes on the table are unaffected. `TableRowStore` refuses to write an `UnreadableLongValue` as a backstop. `LongValueWriteBackTests` covers inline, single-page and chained OLE on Jet3 (inline only), Jet4 and ACCDB. It runs the update, all three column operations, committed and rolled-back transactions, `UseTransactionalWrites`, rows on several data pages and a cascade update (ACCDB). `UpdateRowsAsync_UnreadableMemo_RefusesRowAndLeavesItUntouched`, `UpdateRowsAsync_ReplacingUnreadableMemo_Succeeds` and `AddColumnAsync_UnreadableMemo_RefusesRewriteBeforeChangingSchema` cover the refusal.
  - Follow-up: `RelationshipEnforcer.EnforceFkOnPrimaryUpdateAsync` is not atomic across relationships. When a parent update cascades to two child tables and the second holds an unreadable MEMO, the first child already has the new key while the parent row keeps the old one. The existing "cascade-update is not enabled" error has the same gap. Only `UseTransactionalWrites` or an explicit transaction rolls it back.
- **LINQ and POCO mapping ignored `[Column]`.** Three separate rules decided which column a property maps to: `RowMapper` and `RuntimeRowMapper` matched property names to column names, and `IndexPredicateTranslator`, `OrderStage` and `IncludeLoader` used `property.Name` directly. None of them read `[Column]`, so `InsertRowAsync<T>` wrote DBNull to a `Last Name` column, `Rows<T>` and `ReadTableAsync<T>` left `LastName` null, and `Query<T>().Where(p => p.LastName == "Smith")` matched nothing. The scaffolder emitted renamed properties with no attributes, so its own output lost data the same way. A new cached `EntityMap` (`JetDatabaseWriter/Mapping/`) is now the only mapping model. It maps each public settable, non-indexer property to its `[Column]` name or else its own name, skips `[NotMapped]`, and takes `TableName` from `[Table]` or the type name. Typed inserts, `Rows<T>`, `ReadTableAsync<T>`, `FromIndex<T>`, the direct page decoder, `Include` join keys and target-table lookup, `Where` index inference and index-ordered `OrderBy` all go through it. An explicit `[Column("X")]` beats a property that is only named `X`, and two `[Column]` attributes naming the same column throw `InvalidOperationException`. A property with no getter is written as DBNull, and a `[NotMapped]` or setter-less property in a predicate is filtered client-side instead of driving index inference. The scaffolder now emits `[Column("...")]` and `[Table("...")]`, with the `DataAnnotations.Schema` using, wherever a generated name differs from the Access name by more than case. `[Table]` affects only how `Include` resolves a navigation's table; every read, write and query call still names its table. `EntityColumnMappingTests` covers Jet3, Jet4 and ACCDB: inserts, `Rows<T>`, `ReadTableAsync<T>` (full and projected), `Where`/`OrderBy`, `Rows<T>(predicate)`, `FromIndex<T>`, `Include` over renamed key columns, `[NotMapped]`, rule precedence and the duplicate-column error. `ScaffoldedEntityColumnMappingTests` checks the emitted attributes and compiles scaffolded source, inserts through it and reads it back.
  - Follow-up: the scaffolder emits code that does not compile when the generated class is named `ColumnAttribute` or `TableAttribute` (for example from a table named "Column Attribute"), because the short attribute name then binds to the enclosing class. `EntityEmitter.NameAttribute` could emit the `global::`-qualified name.
  - Follow-up: still separate work from the same design flaw: one value coercer for `RowMapper` and `RuntimeRowMapper`, read materializers cached per `TableDef`, no `Compile()` in `IndexPredicateTranslator.EvaluateValue`, AOT annotations, a streaming `IndexCursor`, the namespace moves and `Expression`-based aggregate overloads.
- **Bugs 10 and 11, and checks switched off after a rolled-back AddColumn or DropColumn: rollback left the writer's caches describing the discarded transaction.** `TransactionLifecycle.RollbackTransactionAsync` only detached the page journal. The insert-page hint still pointed at a data page the transaction had appended past the end of the file, so the next insert into a table that was empty before the transaction threw `EndOfStreamException`. A table created in the transaction stayed in the cached catalog, so inserting into it threw `EndOfStreamException` and re-creating it said it already existed. The constraint registry kept the rewritten table's entries: after a rolled-back AddColumn or DropColumn the column count no longer matched, so every check on the table was skipped and NULL reached AutoNumber and Required columns. A rolled-back DropTable, DropColumn or RenameColumn lost the in-code `DefaultValue` and `ValidationRule`. `TransactionLifecycle` now takes `TableCatalog`, `DataPageInserter` and `ConstraintRegistry`. `BeginTransactionAsync` captures the insert hint, the writable owned-map set and the registry, including AutoNumber counters. A rollback, a failed `UseTransactionalWrites` call and a failed commit restore them and invalidate the catalog. AutoNumber values a rolled-back transaction used are handed out again, matching the TDEF counter the rollback also discards. A commit-lock timeout used to escape before the transaction was marked, leaving it neither committed nor rolled back; it now ends the transaction as a rollback. `TransactionRollbackStateTests` covers Jet3, Jet4 and ACCDB: `InsertRow_AfterRolledBackInsert_Succeeds` (an empty table and a 300-row multi-page batch), `CreateTable_RolledBack_TableIsGoneAndCanBeRecreated`, `DropTable_RolledBack_TableAndRulesRemain`, `Constraints_AfterRolledBackSchemaChange_StillApply` and `ClrRules_AfterRolledBackSchemaChange_AreRestored` (AddColumn, DropColumn, RenameColumn), `AutoNumber_AfterRolledBackInserts_ContinuesFromCommittedRows`, `InsertRow_AfterFailedAutoCommitBatch_Succeeds` (an auto-commit batch over the journal page budget) and `Commit_WhenCommitLockTimesOut_RollsBackAndResetsWriter`.
- **Transactions not atomic (partly fixed): cancellation could tear a commit, a torn commit was reported as rolled back, and the docs claimed atomic before-image journaling.** `CommitTransactionAsync` checked the caller's token before every replayed page. A cancel during the commit therefore left part of the transaction in the file and marked it rolled back, and I/O failures after replay started were reported the same way. A token that was already cancelled threw before the journal was detached and left the transaction active. Cancellation is now honoured only until the first page write starts; after that, the replay and the flush run with `CancellationToken.None`. A token that is already cancelled now ends the transaction as a rollback, so a caller can no longer retry `CommitAsync` on the same transaction. A failure before the first page write starts is a clean rollback: `IsRolledBack` is true and the writer state is restored as for a rollback. A failure after it leaves both `IsCommitted` and `IsRolledBack` false, makes `RollbackAsync` throw, and drops the writer's catalog and insert-hint caches; the constraint registry is kept, so AutoNumber counters never move back over IDs that may be on disk. No public API was added. The `PageJournal` budget message no longer claims the transaction was rolled back. The XML docs, the README, `library-structure.md` and `concurrency-and-lock-ordering.md` now describe what happens: after-images are buffered in memory and written in place, which is not crash-atomic. `JetTransactionTests.Commit_WhenCancelledAfterReplayStarts_CompletesReplay` (ACCDB, Jet4, AES-CFB wrapped ACCDB) and `Commit_WithCancelledToken_RollsBackWithoutWritingPages` cover it. `Commit_WhenReplayWriteFails_LeavesSuccessfulReplayPrefixOnDisk` and `Commit_WhenDurableFlushFails_IsNeitherCommittedNorRolledBack` (renamed from `..._MarksRolledBackAfterReplay`) used to pin the "rolled back" report and now assert that `IsRolledBack` is false.
  - Still open: there is no WAL or before-image, so a crash or I/O failure during replay still leaves part of the transaction in the file. There are no savepoints, so a failed operation inside an explicit transaction stays half-applied in its journal. Writer reads inside a transaction now see the journal (bugs 2 and 5–8, below).
- **Wide tables were created with a phantom key column in half their indexes.** When `CatalogArtifactWriter` created a table, it split each real index's logical `used_pages` offset into a page and an offset by plain division by the page size. That ignores the 8-byte header on TDEF continuation pages. On a 200-column, 30-index Jet4 or ACCDB table, the usage-map row byte therefore landed 8 or 16 bytes early, inside the descriptor's `col_map`, and the real `used_pages` row byte stayed 0. As a result, 15 of the 30 indexes read back as two-column indexes on a column that does not exist (col_num 0x02FF and up). `ListIndexesAsync` reported them that way, and the writer's unique check and index maintenance skipped them because the extra column did not resolve. The new `TDefPageBuilder.WriteLogicalUsedPagesPointer` maps every byte of the pointer through `LogicalToPhysicalTDefOffset`, and both table creation and the fresh `MSysObjects` catalog setup use it. `IndexWriterTests.CreateTable_TDefChainSpansMultiplePages_RoundTrips` now checks that each index keeps exactly its declared key column and, on Jet4 and ACCDB, that each `used_pages` pointer names row realIdx + 2 of the table's usage map.
  - Not repaired: tables written by earlier builds keep the stray `col_map` byte. Writes to them now throw; see the next entry.
- **Wide tables skipped unique checks and left their indexes stale.** This hit tables whose definition spans several TDEF pages: 200 columns and 30 indexes on Jet4 or ACCDB, or 50 columns on Jet3. A duplicate insert or update into a UNIQUE index was accepted, and inserts, updates and deletes left the indexes empty or stale. `UniqueIndexChecker`, the bulk, incremental and catalog-splice paths of `IndexMaintainer`, `SystemTableHasMaintainableIndexesAsync` and `RelationshipSeekPlanner` read only the first TDEF page. The column-name walk ran off that page and each path returned without doing its work. They now read the whole chain. Patches to `first_dp` and `used_pages` are written back to the physical page that holds them through the new `LogicalTDefChain.WriteInPlaceAsync`, called via `DatabaseFile.WriteTDefChainInPlaceAsync` and `WriteTDefInt32Async`; `IndexBTreeEditor`'s root patches use the same path. If an index section still cannot be parsed, or an index names a column the table does not have, the unique check and the bulk rebuild now throw `JetLimitationException` instead of skipping it, and the README's error-handling list says so. The index paths throw `InvalidDataException` when the TDEF page passed to them is not a TDEF. The inline column-name walks in `UniqueIndexChecker`, `IndexMaintainer` and `IndexCatalogReader.ReadMetadata` now call `IndexCatalogReader.LocateRealIdxDescStart`. `MultiPageTDefIndexMaintenanceTests` covers Jet3, Jet4 and ACCDB: `DuplicateInsert_IntoUniqueIndex_IsRejectedBeforeWrite` and `DuplicateUpdate_IntoUniqueIndex_IsRejected` reject duplicates, and the other tests match every index B-tree entry by entry against the live rows after inserts, updates and deletes (`InsertUpdateDelete_KeepsEveryIndexInStep`), multi-level trees (`ManyRows_MultiLevelIndexes_StayInStep`), an explicit commit and a rollback, `UseTransactionalWrites`, AddColumn, relationships with the wide table on both sides, and an AES-encrypted ACCDB.
  - Follow-up: on a wide table written before the previous fix, an index carrying the phantom column makes writes throw `JetLimitationException`. An insert is rolled back first, but without `UseTransactionalWrites` (the default) `UpdateRowsAsync` and `DeleteRowsAsync` change the rows before index maintenance throws, so the caller sees a failure for a write that was applied and the indexes are stale. The unique pre-check throws before any change only when the phantom column is in a unique index. Checking that every index resolves before mutating rows would close this.
  - Follow-up: found while testing, not fixed. A Jet3 row longer than 255 bytes, such as a Jet3 table with 200 Long columns, throws `OverflowException` in `RowEncoder.SerializeRow`, because `JetTypeInfo.WriteField` writes the 1-byte EOD and variable-offset fields with a checked `(byte)` cast; this is why the Jet3 cases use 50 columns. The transaction-visibility bugs (a duplicate update not rejected, and a delete hitting the wrong row, after an earlier update in the same transaction) also show up on wide tables but are not specific to them; they are bug 2's cause and are fixed with it (next entry).
- **Bugs 2, 5, 6, 7 and 8: the writer's reads inside a transaction did not see the transaction's own writes.** Every workflow that reads a table before changing it (update, delete, cascades, full index rebuilds, AddColumn/DropColumn/RenameColumn, AutoNumber seeding, unique checks and relationship enforcement) decoded rows through `TableSnapshotReader`. That class opened a separate uncached `AccessReader` with no journal, and the writer paired its rows by position with row locations read through the journal. So a delete then an update in one transaction rewrote the wrong row, AddColumn dropped the rows inserted earlier in the transaction, a relationship created in the transaction was not enforced, and a cascade delete under `UseTransactionalWrites` left the child's primary-key and foreign-key indexes pointing at the wrong rows. The same cause hid the rows of a bulk insert in a transaction from the index rebuild that runs after the batch, so a seek on a secondary index found none of them (the re-check agents' "bulk insert inside a transaction" entry, now removed). Owned-page discovery also stopped at the physical end of the file, so it missed tables and data pages appended inside the transaction. `TableSnapshotReader` now decodes through the writer's own `DatabaseFile`. `WriterServices` builds it from a `RowDecoder` over a capacity-0 `ReaderPageCache` and a `CatalogReader` over the writer's `TableCatalog`, so it caches nothing, reuses the writer's page keys and takes no lock-file slot. It still decodes with `RowDecodePlan.CreateTypedForWriteBack` and types MEMO and OLE columns as `object`, so the OLE fix above keeps working. Owned-page discovery is now bounded by `LogicalPageCount`. `AccessReader.OpenUncachedAsync`, `ReadDataTableForSchemaRewriteAsync` and `ReadLvPropForTableAsync` are gone, along with the write-back mode of `TableReader` and `LinkedTableReader`, the `ServiceGraphTests` allow-list entry and the "deliberate exception" text in `library-structure.md`. `UpdateRowsAsync` and `DeleteRowsAsync` no longer open and scan the file a second time. `TransactionReadVisibilityTests` covers each bug with no transaction, with `UseTransactionalWrites` and in an explicit committed transaction, on Jet3, Jet4 and ACCDB (relationship and index-seek cases on Jet4 and ACCDB); `BulkInsert_ThenIndexSeek_FindsEveryInsertedRow` covers the bulk insert. It also covers a rollback, and an explicit transaction on Jet4 RC4, ACCDB password, AES, Standard and Agile CFB files. `LongValueWriteBackTests` now reads its snapshots through the writer's own `TableSnapshotReader`.
  - Follow-up: every insert, update and delete still calls `GetEnforcedRelationshipsAsync`, which scans `MSysObjects` twice and decodes `MSysRelationships`. Most of the bytes one `UpdateRowsAsync` still reads come from there; caching it per writer session would remove them.
- **The writer paired decoded rows with row locations by position.** `UpdateRowsAsync`, `DeleteRowsAsync`, the full index rebuild and the cascade-delete and cascade-update snapshot fallbacks decoded rows into one list and row locations into another, then zipped them under `Math.Min`. A live row the decoder skips (too short, or a column count of 0) shifted every later pair. With one such row at the front of a table, deleting Id=3 deleted row 2, and updating Id=4 deleted row 3 and left the old row 4 beside the updated copy, with or without a transaction; a full index rebuild pointed each key at its neighbour's row. `TableSnapshotReader.ReadRowsAsync` now returns each decoded row together with the location it came from (`LocatedRow`), still decoded with `CreateTypedForWriteBack`. All of these paths, plus `UniqueIndexChecker`'s pre-update check and its pre-insert snapshot path, mutate and index exactly that location, and `IndexMaintainer.MaintainIndexesAsync` no longer resolves the table by name. The cascade-update fallback still builds every rewritten child row, and refuses an unreadable MEMO or OLE value, before it deletes any child row. `TransactionReadVisibilityTests.DeleteAndUpdate_PastARowTheDecoderSkips_ChangeOnlyTheMatchingRows` covers it on Jet3, Jet4 and ACCDB in every write mode, including primary-key seeks.
  - Follow-up: `DatabaseFile.GetLiveRowLocationsAsync` has no production callers left; only `ForeignKeyEnforcementTests`, `MultiPageTDefIndexMaintenanceTests` and `TransactionReadVisibilityTests` use it. Its doc comment now warns against pairing it with decoded rows, but moving those tests to `ForEachLiveTableRowAsync` and deleting it would stop anyone reintroducing positional pairing.
- **Bug 4: an update could set a NOT NULL column to null.** `TableDataWriter.UpdateRowsAsync` passed each staged row only to `ConstraintRegistry.ApplyCalculatedAsync`, which recomputes calculated columns and nothing else. Null was written into NOT NULL and AutoNumber columns, in the declaring writer and in a reopened one, and a CLR `ValidationRule` never saw updated values. The new `ConstraintRegistry.ApplyUpdateAsync` checks each column the update assigns the way insert checks a supplied value: null in a NOT NULL or AutoNumber column throws `InvalidOperationException`, and `ValidationRule` runs on non-null values and throws `ArgumentException`. Calculated columns are then recomputed as before. The checks run while rows are staged, so a rejected update writes nothing. Update doesn't substitute defaults or recheck columns it doesn't assign, so a row that already holds null in a NOT NULL column can still have its other columns updated. An explicit AutoNumber value on update now raises the TDEF high-water through `AutoNumberMaintainer`, as on insert. The `ColumnDefinition`, `IAccessWriter.UpdateRowsAsync` and README docs describe the update behaviour; the README's `IsNullable` row now names the LvProp `Required` property as where it is stored. `ColumnConstraintTests` covers it: `Update_NullIntoNotNullColumn_IsRejected` (Jet3, Jet4 and ACCDB, same and reopened writer), `Update_NullIntoNotNullColumn_LeavesEveryRowUnchanged` (multi-page table, `UseTransactionalWrites`, committed and rolled-back transactions), `Update_NullIntoAutoNumberColumn_IsRejected`, `Update_ValidationRule_RejectsAssignedValue`, `Update_OtherColumn_DoesNotRecheckUnassignedNotNullColumn` and `Update_ExplicitAutoNumberValue_RaisesTdefHighWater`.

## Open: reproduced by the re-check agents (I didn't run these myself)
- **RenameColumn changes types and loses foreign-key indexes.**
  - NUMERIC(10,2) becomes (18,0), so 12.34 is stored as 12.
  - On a child table, the foreign-key index is dropped and the parent's link still points to the freed page.
  - The code is at [TableSchemaEditor.cs:237-258](JetDatabaseWriter/Tables/TableSchemaEditor.cs#L237-L258).
- **Jet3 table headers are corrupted.**
  - The row count is written into the AutoNumber slot ([TDefPageBuilder.cs:505-507](JetDatabaseWriter/Schema/TDefPageBuilder.cs#L505-L507)).
  - The AutoNumber writer overwrites the table-type byte, which went from 0x4E to 0xBC after 700 inserts ([AutoNumberMaintainer.cs:71-78](JetDatabaseWriter/Schema/AutoNumberMaintainer.cs#L71-L78)).
- **Jet3 long values the library writes can't be read back.** `LongValueStore.WriteLvalPageHeader` always writes the Jet4 data-page header (row count at offset 12, row offsets from 14), but Jet3 data pages keep them at 8 and 10. A Jet3 MEMO over about 1 KB or OLE value over 256 bytes written by the library reads back as `(memo on LVAL page)` or an empty `byte[]`. An update or schema rewrite of such a row used to store that placeholder for good; it now throws `InvalidDataException` and leaves the row alone. This is why the Jet3 cases in `LongValueWriteBackTests` use only inline payloads.
- **Constraints:**
  - AutoNumber IDs are reused across sessions ([ConstraintRegistry.cs:491-533](JetDatabaseWriter/Schema/ConstraintRegistry.cs#L491-L533)).
  - Validation rules and default values stored in the file are never enforced.
  - Rules declared in code are lost when the writer is reopened.
  - Calculated expressions follow Excel precedence: `-2^2` = 4, and `5%` is accepted as 0.05.

## Design flaw status
| Flaw | Status | What changed |
|---|---|---|
| Facade is the engine / service locator | **Partly resolved** | Locator and cycles are gone. `DatabaseFile` (1,420 lines, used by about 33 types) is the new catch-all: pager, transaction journal, encryption and table-definition parsing in one class. |
| Reader and writer are separate engines | **Resolved** | The writer no longer opens a second `AccessReader` over its own file. `TableSnapshotReader` decodes through the shared `RowDecoder`, `LongValueDecoder` and `CatalogReader` over the writer's own `DatabaseFile`, so its reads see the transaction journal (bugs 2 and 5–8 fixed). Each decoded row comes back with its location (`LocatedRow`), so nothing pairs rows and locations by position any more. |
| No pager or buffer manager | Open, critical | The cache moved into `ReaderPageCache`, and its eviction bug (bug 1) is now fixed. Owned-page discovery now uses `LogicalPageCount` instead of the stream length, but there are still several end-of-file definitions, and the writer still has no cache. |
| Transactions not atomic | Open, critical | Rollback no longer breaks the writer: it restores the cached catalog, insert hint and constraint registry (bugs 10–11 fixed). Cancellation can no longer tear a commit, a commit that fails after it started writing pages is no longer reported as rolled back, and the docs now say commit writes in-memory after-images in place, which is not crash-atomic. The format-byte bump is fixed (bug 3). The writer's own reads inside a transaction now see its pending writes (bugs 2 and 5–8). Still no WAL or before-image, so a crash or I/O failure during replay tears the file, and no savepoints. |
| Schema isn't a model | Open | Three duplicate parsers merged. The index paths now read the whole TDEF chain and share `IndexCatalogReader.LocateRealIdxDescStart` instead of their own column-name walks, and in-place TDEF patches go through `LogicalTDefChain.WriteInPlaceAsync` (the wide-table fixes above). The rest unchanged |
| No write pipeline or real B-tree | Open | Moved into `TableDataWriter` with the same algorithms |
| Constraints live in the process, not the file | Open | No change |
| Lossy value model | Open | Complex-column cells are no longer lossy: `Rows()` and the other row reads return every attachment, decoded, and every multi-value item (see "Fixed since 6eab703"). Updates, cascades and schema rewrites no longer lose data either: the writer's snapshot carries OLE bytes exactly and refuses a MEMO or OLE value it cannot read instead of storing placeholder text. The OLE signature heuristic on the normal read path is unchanged, and a multi-value Decimal still loses its scale. |
| Format knowledge scattered | Open | No change. Files importing `JetTypeInfo` went from 35 to 40. |
| Read API doesn't compose | Open | Moved into `TableReader`. The read loops now agree on which rows they return, on `maxRows` and on calculated-column types (bug 12 and the drift fix above), but they are still separate loops with no shared scan primitive. `IndexRowReader` still returns nothing for linked tables (`ListIndexesAsync`, `EnumerateIndexRowsAsync`), `CatalogReader.ResolveTableAsync` still re-reads the TDEF uncached and rescans MSysObjects, and unknown tables still read as empty, unlike the writer. |
| Encryption isn't a page layer | Open | Opening a file now reads only page 0 to detect flat Agile, and the writer refuses flat Agile instead of corrupting it. Flat Agile and the CFB Office Crypto formats are still decrypted whole into memory, and the writer still has no page cipher for flat Agile. |
| Failures aren't modeled | Open | `LastDiagnostics` is now built from a typed record internally |
| No CI; untested netstandard2.1 build | Open | No change. A Release build also fails on 155 analyzer errors in the test project. |
| LINQ layer has no mapping model | **Partly resolved** | It depends on reader services instead of the facade, which makes a package split easier. `EntityMap` is now the one mapping model: every typed path maps properties to columns through it, honouring `[Column]`, `[NotMapped]` and `[Table]`. There is still no query plan: reads compile materializers per call, `RowMapper` and `RuntimeRowMapper` coerce values differently, the IQueryable surface runs sync-over-async, the index walk builds a `List` instead of streaming, and nothing is annotated for AOT. |
