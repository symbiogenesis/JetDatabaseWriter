## Data loss and broken referential integrity

- **Without a transaction, an I/O error or a damaged page after an update deletes a row loses the row.**
  - `TableDataWriter.UpdateRowsAsync` rewrites each matching row with `TableRowStore.MarkRowDeletedAsync` and then `InsertRowDataLocAsync`, and `RelationshipEnforcer.ApplyCascadeUpdatesAsync`, which runs before that loop, rewrites the cascaded child rows the same way. Every new version is encoded and measured first, with no I/O (`TableRowStore.EncodeRow`), before the call's first write: the table's own rows as `UpdateRowsAsync` stages them, and at the end of `RelationshipEnforcer.PlanCascadeUpdatesAsync` every rewritten child row, with the key changes of every relationship that reaches it, and every own row that took a self-relationship's cascaded key. So a value the encoder refuses, or a row too long for a page, throws before anything is written.
  - What is left is a page failure after a row's delete, an I/O error from the stream or a damaged page: in the re-insert's LVAL page work, in `DataPageInserter.FindInsertTargetAsync`, which reads the data pages and the owned-pages usage map, or in its data-page write; and, for the updated table's own rows under `SecureEraseMode.DeletedRowsAndFreedPages`, in the delete's release of the old row's LVAL rows, which `MarkRowDeletedAsync` runs (`LongValueEncoder.DeallocateLongValueAsync`) after it has flagged the slot. `ApplyCascadeUpdatesAsync` passes `MarkRowDeletedAsync` no `TableDef`, so it releases no long values there.
  - The row is then gone. The indexes still name the old slots of the rows the call had reached, because index maintenance runs after the loop. The TDEF `num_rows` still counts the lost row, because the re-insert passes `updateTDefRowCount: false` and nothing recomputes the count: `GetTableStatsAsync` reports one row too many, and `DatabaseFile.ValidateOwnedDataPagesAsync` rejects the owned-pages map because the live rows fall short of `num_rows`, so a scan that does not have the table's pages cached can fall back to the whole-file owned-page pass. Cancelling the token cannot stop the call there, because the call ignores it once it has written its first page. The README's "Transaction durability" limitations document the gap.
  - Repro, run as a probe: a new Jet3 or ACCDB file over `WriteFaultStream`, with T (`Id` primary key, `Name`) holding [1, 'a'] and [2, 'b']. With no transaction, arm `FailOnWrite(2)` and run `UpdateRowsAsync("T", RowCriteria.Where("Id", 1), { Name = "z" })`: the second page write, the re-insert's, throws `IOException`, and T holds only row 2. From the code, not run: under `SecureEraseMode.DeletedRowsAndFreedPages`, with a MEMO column added to T and a value over 1,024 bytes in it for row 1, the second page write is the release of that value's LVAL row instead, with the same result.
  - Planned in wave 2: atomicity-b makes every call statement-atomic.
- **A cascade into a table with an index the writer cannot maintain, such as a wide table written by an earlier build, deletes or rewrites that table's rows and then throws, while the parent row stays.**
  - An insert, update, delete or column change first checks that the writer can maintain every index of the table it names (the index preflight, `IndexMaintainer.ThrowIfIndexesUnmaintainableAsync`), and otherwise throws `JetLimitationException` ("The indexes of table 'Wide' cannot be maintained: index 'IX_03' names a column the table does not have.") before it changes anything. A cascade reaches other tables unchecked: `RelationshipEnforcer.ApplyCascadeDeletesAsync` and `ApplyCascadeUpdatesAsync` delete or rewrite a child table's rows before that table's index rebuild refuses, so without `UseTransactionalWrites` or a transaction the child rows stay deleted or rewritten under a parent that keeps its key.
  - Such indexes are in wide tables written by builds of this library before f68a131, whose `CatalogArtifactWriter` put each spilled `used_pages` row byte 8 or 16 bytes early, inside `col_map`: 15 of the 30 indexes of a 200-column, 30-index Jet4 or ACCDB table read as two-column indexes on col_num 0x02FF and up, which `ListIndexesAsync` lists with an empty column name. Where the byte's offset is a whole number of pages, it overwrote the type byte of a TDEF continuation page instead, which cuts the table definition short before the index descriptors past it.
  - Repro, run as a scratch test (ACCDB, no transaction): Parent (`Id` primary key) with rows 10000 to 10004, and a 200-column Wide table with 30 indexes and 40 rows, related Parent.Id <- Wide.C001 with cascading deletes. After `LegacyDamageInjector.InjectStrayUsedPagesByteAsync` on Wide, `DeleteRowsAsync("Parent", "Id", 10001)` throws the preflight's message for Wide, Parent keeps all 5 rows, and Wide has lost its 8 rows with C001 = 10001.
  - Planned in wave 2: collation #3 calls the preflight for each cascade child table before anything is written, and atomicity-b makes the whole call statement-atomic.
  - `CreateRelationshipAsync` with such a table on either side writes the relationship and then throws. `RelationshipManager.CreateRelationshipAsync` appends the `MSysRelationships` rows, runs the catalog artifact plan, and adds the foreign-key entries and an empty leaf to both TDEFs before its `MaintainIndexesAsync` of each table refuses. Repro, run as a scratch test (ACCDB): Parent as above and Wide with 40 rows and no relationship. After `InjectStrayUsedPagesByteAsync` on Wide, `CreateRelationshipAsync(new RelationshipDefinition("R", "Parent", "Id", "Wide", "C001"))` throws the preflight's message for Wide, yet `ListRelationshipsAsync` then returns R, Parent has the foreign-key index `.rB`, Wide has 31 indexes, and a second call throws "A relationship named 'R' already exists". The same happens with no transaction and inside an explicit transaction that is then committed. Planned in wave 2: collation #3 calls the preflight from `CreateRelationshipAsync` for both tables, and atomicity-b makes the call statement-atomic.
  - Adding an attachment or multi-value item to a row whose complex slot is null, in such a table with an index on a complex column, changes the table and then throws. `ComplexColumnManager.ReadOrAllocateComplexReferenceAsync` raises the table's complex AutoNumber (`RaiseComplexHighWaterAsync`) and writes the new reference into the row (`PatchNullComplexSlotsAsync`) before its `MaintainIndexesAsync` of the table refuses. Only rows written by earlier builds of this library have a null slot, and tables the writer creates have no complex-column index, so this needs both. From the code, not reproduced. Not planned yet: the check belongs in `AddComplexItemCoreAsync`, before the allocation, with collation #3's other call sites; atomicity-b makes the call statement-atomic.
  - Nothing repairs such a table yet. Planned in wave 2: legacy-repair adds `AccessWriter.RepairAsync`, and the preflight message will then name it.
- **Cascade updates stop at the first level, so a grandchild keeps the old key as an orphan.** `RelationshipEnforcer.PlanCascadeUpdatesAsync` plans the rewrites of each cascading relationship's dependent rows, on the seek and the snapshot paths, but never plans again with the child table as the primary table; deletes recurse through `PlanCascadeDeletesAsync`. Repro (ACCDB): A (`Id` primary key), B (`AId` primary key) and C (`Id` primary key, `BAId`), related A.Id <- B.AId and B.AId <- C.BAId, both cascading updates, with rows A [1], B [1] and C [1, 1]. Updating A.Id to 5 leaves C.BAId at 1. Planned in wave 2: write-pipeline-a1's cascade plan recurses through updates as deletes already do.
- **A delete whose own rows a cascading self-relationship also reaches counts those rows twice, so the TDEF row count and the index row counters end up too low.**
  - `TableDataWriter.DeleteRowsAsync` passes only the matching rows' values to `RelationshipEnforcer.PlanCascadeDeletesAsync`, whose `cascaded` set starts empty, so it leaves out only rows that an earlier cascade of the call deletes. A caller's row that is also a child of another caller's row is deleted by the cascade (`ApplyCascadeDeletesAsync`: tombstone, `AdjustTDefRowCountAsync`, index rebuild) and then again by `DeleteRowsAsync`, which counts it in its own row-count adjustment and passes it to `TryMaintainIndexesIncrementalAsync` as a delete hint. Its attachment and multi-value rows are deleted once, with the cascade, because the statement's `ComplexChildDeletes` groups hold each planned flat row once.
  - Repro, run on Jet4 and ACCDB: Tree (`Id` primary key, `ParentId`) with rows [1, null], [2, 1] and [3, null], and FK_Tree_Self (Tree.Id <- Tree.ParentId) cascading deletes. `DeleteRowsAsync("Tree", RowCriteria.Where(ColumnPredicate.In("Id", 1, 2)))` returns 2 and leaves row 3, but `GetTableStatsAsync` reports a Tree RowCount of 0.
  - Fix: pass the caller's row locations to `PlanCascadeDeletesAsync`, and after the refusal check leave them out of what a cascade deletes and recurses into. Planned in wave 2: write-pipeline-a1 #4's cascade plan folds self-referencing overlaps, and its tests include the repro.
- **A cascaded key that duplicates a key in a unique index of the child table is refused only after the child rows are rewritten, and the child table's index rebuild is abandoned.**
  - `TableDataWriter.UpdateRowsAsync` checks the updated table's unique indexes before anything is written (`UniqueIndexChecker.CheckUniqueIndexesPreUpdateAsync`), but no check covers the rows `RelationshipEnforcer.PlanCascadeUpdatesAsync` plans: `ApplyCascadeUpdatesAsync` rewrites them, and the child's `MaintainIndexesAsync` then throws `InvalidOperationException` ("Unique index violation on table 'C': duplicate key detected after row mutation. The duplicate row has been written but the index B-tree was not rebuilt; ..."). Without a transaction the child rows keep the new key under a parent that keeps the old one. Through a self-relationship, the cascaded rows of the updated table are missing from its own pre-check in the same way.
  - `IndexMaintainer.RebuildIndexesAsync` throws from inside its per-index loop, before it writes the TDEF, and releases the trees it has placed. Of the indexes ahead of the failing one in real-index order, only one whose old root is a single leaf and whose new tree fits on one page is rewritten, in place; the failing index, every index after it, and the earlier indexes whose new tree went to new pages keep their old trees, which point at the rewritten rows' old slots and have no entries for the rewritten rows.
  - The collision needs a child row that already holds the new key with no parent row holding it, since a parent row with that key fails the parent's own check first; `CreateRelationshipAsync` lets such a row in (**`CreateRelationshipAsync` does not check the existing rows**).
  - Repro, run as a scratch test on Jet4 and ACCDB: P (`Id` primary key) with rows 1 and 2, and C (`Id` primary key, `ParentId` with a unique index) with rows [1, 1] and [2, 3], related afterwards by FK_C_P (P.Id <- C.ParentId) cascading updates. `UpdateRowsAsync("P", RowCriteria.Where("Id", 1), { Id = 3 })` throws that message; P keeps rows 1 and 2, and C reads [1, 3] and [2, 3].
  - Fix: check each cascade child table's unique indexes in `PlanCascadeUpdatesAsync`, with the planned rewrites in place of the rows they replace, through a table read or, on the seek path, probes of the child's unique indexes. Not planned yet; atomicity-b's statement atomicity would roll the rewrites back.
- **Setting a referenced column that is not the primary key to Null orphans its dependent rows.** `RelationshipEnforcer.ResolveReferencedKeyChangesAsync`, which `PlanCascadeUpdatesAsync` calls, skips a row whose old or new referenced key is null, so the update is neither refused nor cascaded. Access refuses it with error 3200 when updates do not cascade (from memory, not checked against Access). Repro (ACCDB): P (`Id` primary key, `Name`) and D (`Id` primary key, `PName`) with rows P [2, 'two'] and D [1, 'two'], related P.Name <- D.PName. `UpdateRowsAsync("P", RowCriteria.Where("Id", 2), { Name = null })` returns 1, and D keeps 'two'. The README does not mention it. Not planned yet; it belongs with write-pipeline-a1's cascade plan.
- **`CreateRelationshipAsync` does not check the existing rows, so an enforced relationship can be created over orphaned keys.** `RelationshipManager.CreateRelationshipAsync` checks the name, the tables, the key columns and that no relationship has the same name, then writes the `MSysRelationships` rows, the catalog object and the FK entries without reading the foreign table. Access refuses with "Data in the table violates referential integrity rules" (from memory, not checked). Repro: create P (`Id`) and C (`Id`, `ParentId`), insert C [2, 99] with no P row 99, and `CreateRelationshipAsync` (P.Id <- C.ParentId) succeeds. `ForeignKeyUpdateScopeTests` (for example `Update_UnassignedForeignKey_OnOrphanedRow_IsNotChecked`) plant their orphaned rows this way, so a fix must plant them through `ForeignKeyTestDatabase.PlantRelationshipAsync` instead. Not planned yet; it belongs with write-pipeline-a1's cascade plan.
- **`InsertRowAsync<T>` with a POCO whose AutoNumber property is a non-nullable `int` stores 0, so a second insert duplicates the key.** `RowMapper<T>.BuildToRow` boxes a non-nullable value-type property as it is, and `ConstraintRegistry.ApplyAsync` generates an AutoNumber only for null, `DBNull.Value` or `DbDefault.Value`. Only an `int?` property or a `[NotMapped]` one gets a generated value. Repro: create `A` with `Id` (`int`, `IsAutoIncrement`) and `Name`, and insert `new PocoA { Name = "x" }` twice, where `PocoA` has `int Id` and `string? Name`; both Ids read back as 0. Not planned yet.
- **`UpdateRowsAsync` and `DeleteRowsAsync` compare a `byte[]` criteria value by reference, so an equality matches no row and an inequality matches every row.** `RowCriteriaEvaluator.ValuesEqual` tries `object.Equals` and then an `IComparable` comparison, and `byte[]` has neither, so a `ColumnPredicate.Equal` or `In` on a Binary or OLE value, or the single-column overloads, which build the same criteria, change nothing with no error, while `NotEqual` matches every row, the equal ones included. From the code, not run. Planned in wave 2: value-model-b matches `byte[]` criteria by content.
- Minor, on files whose FK entries are already inconsistent (neither Access nor the writer writes them):
  - **A partner FK entry that names a dropped table, with no entry on the dropped table naming it back, survives `DropTableAsync` and names the freed page.** `RelationshipManager.RemovePartnerLinksAsync` finds partners only through the `rel_tbl_page` of the dropped table's own FK entries, so the stale entry stays until that partner is rewritten, and once a new table takes the page it is a phantom partner. Repro: on a new ACCDB, relate B.Id to A.ParentId and create a table T; point A's FK entry `rel_tbl_page` at T's TDEF page with `WriteTDefInt32Async`, then `DropTableAsync("T")`: T's page (41) is freed and A's entry still names it. An entry whose own `rel_idx_num` is -1 is kept unchecked, but a rewrite of its partner drops the partner's entry, because the -1 entry names no entry back. From the code, not run. Fix idea: treat a target entry whose `rel_idx_num` is -1 but whose `rel_tbl_page` names this table as linking back. Not planned yet.

## Values stored or read wrong without an error

- **Text outside the code page is stored as its best-fit match or `?` in Jet3 `LvProp` strings, and in strings inserted into a Binary column on every format.**
  - Jet3 `LvProp`: `ColumnPropertyBlockBuilder.ToBytes`, `ColumnPropertyTargetBuilder.AddText` and `AddMemoText`, and `LinkedOdbcLvPropBuilder.BuildNameMap` call `Encoding.GetEncoding(1252)`, and the read side (`ColumnPropertyBlock`, `ColumnPropertyTarget`) hard-codes 1252 too. So a Description, ValidationText, DefaultValue or ValidationRule expression, or an ODBC source column name outside Windows-1252 is stored lossily without an error, and on a Jet3 file with another code page the `LvProp` target names can differ from the TDEF column names. Names and Text or Memo values are refused instead (`AccessObjectName.ThrowIfNotStorable`, `DatabaseFile.EncodeAnsiText`). Repro: on a new Jet3 file, `CreateTableAsync("T", [new ColumnDefinition("Name", typeof(string), 50) { Description = "中文 Łódź", ValidationText = "中文" }])`; after reopening, `GetColumnMetadataAsync` returns the Description "?? Lódz" and the ValidationText "??".
  - Binary columns: `RowEncoder.EncodeBinaryValue` converts a value that is not a `byte[]` with `db.AnsiEncoding.GetBytes`, the database's lenient code-page encoder, and `TableDataWriter.ThrowIfTextNotStorable` checks only Text and Memo columns, on Jet3 only. Repro, on ACCDB and Jet3: `CreateTableAsync("T", [new ColumnDefinition("B", typeof(byte[]), 10)])`, then `InsertRowAsync("T", ["中文"])`; the value reads back as 3F 3F. Fix: refuse a string for a Binary column, or encode it strictly.
  - Wave 2's format-profile-b #1 encodes LvProp text with the database's code page, which fixes Jet3 files with another code page; whether a character the code page lacks is then refused, as it is in names and values, or stored as '?' is left to that package. The Binary column is not planned yet.
- **Text index keys are always encoded as General Legacy.** `IndexKeyEncoder.EncodeEntry` sends every Text and Memo key through `GeneralLegacyTextIndexEncoder`, whatever the column's or the database's sort order; `GeneralTextIndexEncoder` and `General97TextIndexEncoder` exist, but only FormatProbe and tests call them. So on tables whose sort order is General (Access 2010 and later) or General 97 (Jet3), the writer's index entries, unique checks and seeks use a key form Access does not, for any character where the two collations differ (index-and-relationship-format-notes.md §9). From the code, not run. Planned in wave 2: collation encodes each text key with its column's sort order and refuses a write that needs an unsupported one.
  - Files this writer has already changed keep the General Legacy keys it put into General and General 97 indexes, and nothing will repair them once collation lands; a full index rebuild (`IndexMaintainer.RebuildIndexesAsync`) would, and legacy-repair's `RepairAsync` could. Not planned yet: deferred from wave 2. collation moves this bullet to its own item when it deletes this one.
- **Cascade updates rewrite child rows without the child table's checks.** `RelationshipEnforcer.PlanCascadeUpdatesAsync` builds the rewritten child rows and `ApplyCascadeUpdatesAsync` writes them with `MarkRowDeletedAsync` and `InsertRowDataAsync`, and neither calls `ConstraintRegistry.ApplyUpdateAsync`, which `UpdateRowsAsync` runs only on the caller's own rows, before the plan. So a child column's validation rule is not checked against the cascaded key, and a child calculated column that names the foreign-key column keeps its old cached value; the same holds for a row of the updated table whose own cascaded key a self-relationship writes into the caller's rewrite. From the code, not run. Planned in wave 2: write-pipeline-a2 validates every cascaded child row before anything is applied, and constraints-a adds the table rule.
- **Fixed-length Text columns read as Null.** `ColumnInfo.IsFixed` treats every Text column as variable-length (`JetTypeInfo.IsAlwaysVariableLength`), whatever its descriptor's FLAG_FIXED says, so `users.c_flag_` reads as Null in both rows of all four fixedTextTest fixtures (V2000, V2003, V2007 and V2010). The stored values have not been checked, and no fixture shows how Access pads such a value on write. Wave 2's write-pipeline-c stops an update from writing those Nulls back, but the read stays wrong. Not planned yet.
- **An `LvProp` blob that cannot be read gives no properties, without an error, and a schema rewrite then replaces it with only the modelled properties.** `ColumnPropertyReader.ReadLvPropForTableAsync` gets the blob from the typed decode, where `LongValueDecoder.ReadLongValueRawBytesAsync` returns an empty array for an LVAL row or chain it cannot read, and `ColumnPropertyBlock.Parse` returns null for under 4 bytes or an unknown magic. So `GetColumnMetadataAsync` shows no description, default, rule or calculated result type, `ConstraintRegistry` enforces no stored default or rule, and nothing is traced. From the code, not run: AddColumn, DropColumn and RenameColumn then call `PersistedPropertyProjector.ProjectForRewrite(null, ...)`, which builds a blob from what `JetExpressionConverter.ApplyColumn` emits for the columns, and that blob replaces the stored one on the rebuilt table's catalog row, so Caption, Format, the table-level Filter and the rest are lost. A row value in the same state is refused (`UnreadableLongValue`, `InvalidDataException`). Planned in wave 2: failure-model-b1 reports such a blob as unreadable, and constraints-b refuses a schema rewrite over it.
- **An unreadable MEMO reads as placeholder text, and an unreadable OLE value as an empty array, on every public read API.** `LongValueDecoder.ReadLongValueAsync` returns "(memo)" or "(OLE)" for a malformed 12-byte descriptor, "(memo on LVAL page)" or "(OLE)" when the LVAL row cannot be located, and "(memo chain error: <reason>)" or "(OLE chain error: <reason>)" when a chain breaks. `RowDecoder` and `RowDecodePlan` return that text as the cell, so `Rows`, `ReadTableAsync`, `Rows<T>`, `ReadTableAsync<T>` and the string APIs show it as stored data. OLE cells go through `ReadLongValueRawBytesAsync`, which returns an empty array for any unreadable value, and calculated long values behave the same. Nothing reaches `Trace` or `LastDiagnostics`, and neither the README nor `IAccessReader` documents it. The writer's snapshot is not affected: `RowDecodePlan.CreateTypedForWriteBack` reads through `ReadLongValueBytesExactAsync`, and updates and rewrites refuse the resulting `UnreadableLongValue` with `InvalidDataException`. Planned in wave 2: failure-model-b1 (one decode-fault policy for every read path, with no placeholder values).
- **A row behind an overflow pointer that cannot be resolved disappears from every read API with no signal.** An overflow header slot (flag 0x4000) starts with the target row index and a 24-bit page number. `DatabaseFile.TryResolveOverflowRowAsync` returns null, without throwing or tracing, when the pointer is shorter than 4 bytes, names page 0 or a page at or past `PageCount`, names a page that is not a data page of the same table or lacks the slot, or needs more than `Constants.DataPage.MaxOverflowHops` (8) hops. `DatabaseFile.ForEachRowOnPageAsync`, the `TableReader` scans, `RowDecoder` and the `IndexRowReader` seek then skip the row. At least trace the skip when `DiagnosticsEnabled` is set. Repro: `OverflowRowTests.CorruptOverflowPointer_SkipsTheRow` with the `OverflowRowLayout.PointerPastEndOfFile` layout. Not planned yet.
- **A damaged complex-column catalog makes every Attachment and multi-value cell read as Null with no error, and the fallback can pick another table's flat table.** `ComplexColumnReader.TryGetComplexColumnsAsync` and `LoadColumnCellsAsync` catch `InvalidDataException`, `IndexOutOfRangeException`, `IOException` and `OverflowException` from a damaged parent TDEF, `MSysComplexColumns`, `MSysObjects` or flat table, trace them only when diagnostics are enabled (`TraceBestEffortFallback`), and return no descriptors or no cells. Without descriptors, `FindFlatTableFallbackAsync` looks for the flat table through `GetComplexFlatTablePageAsync` and then takes the first system table whose name ends with `_<columnName>`, ignoring case, so two tables with a complex column of the same name (Docs.Files and Mail.Files) can resolve to the wrong flat table (from the code, not run). Planned in wave 2 for the error only: failure-model-b1 #2 stops catching `IOException` there and makes reads under `StrictParsing` throw `CorruptComplexColumn`; lenient reads still give Null, and the `_<columnName>` suffix fallback is not planned yet.
- **`Include` joins text keys ignoring case when it seeks and by exact case when it scans**, so whether a child whose foreign key differs from its parent's key only in case is included depends on the plan the loader picks. Access joins text ignoring case. The seek goes through the index's case-insensitive key; the scan matches `IncludeLoader.Normalize`'s keys, which keep text as it is stored, ordinally.
  - Repro, run as a scratch test: P (`Code` Text(10) primary key) and C (`Id` primary key, `PCode` Text(10)), with a relationship from P.Code to C.PCode. P holds 'ABC' and 'XYZ'; C holds [1, 'abc'], which the writer accepts, plus N rows [100+i, 'XYZ']. `Query<PRow>("P").Where(p => p.Code == "ABC").Include(p => p.Cs)` returns the child with N = 20 on Jet4 and ACCDB, which seek, but not with N = 1, where the cost guard scans, and not on Jet3 for either N.
  - Fix: key text in `IncludeLoader.Normalize` by the database's text comparison, or always match through the collation. Not planned yet; collation, which edits `IncludeLoader` and asks that `Include` find the rows a scan finds, is where it belongs, and its tests should include the repro.
- **Deleting a row with attachments or multi-value items leaves the deleted flat rows in the hidden flat table's indexes.** `ComplexColumnManager.ApplyComplexChildDeletesAsync`, which `DeleteRowsAsync` runs for the rows it deletes and `RelationshipEnforcer.ApplyCascadeDeletesAsync` for the rows a cascade deletes, marks each planned flat row deleted and lowers the flat table's row count, but maintains none of the flat table's indexes (`MSysComplexPKIndex`, the FK back-reference index and, for attachments, `IdxFKPrimaryScalar`). Their entries keep pointing at the deleted rows until the next `AddAttachmentAsync` or `AddMultiValueItemAsync` on that column rebuilds every flat-table index. The library reads items by scanning the flat table, so its own reads are unaffected; what Access does with the stale entries is unchecked. Repro, run as a scratch test (ACCDB): `Docs` (`Id` primary key, `Files` attachment) with rows 1 and 2 and one attachment each; after `DeleteRowsAsync("Docs", "Id", 1)` the flat table has 1 live row, and each of its 3 indexes holds 2 entries (`IndexLeafChain.ReadEntriesAsync`). Planned in wave 2: write-pipeline-a1 #3 maintains the flat-table indexes on complex cascades, with the deleted rows as delete hints.

## Writes refused that Access allows

- **A unique index that is not the primary key refuses a second Null key, so every insert into NorthwindTraders' Employees fails.** Access allows any number of Null keys in such an index: Employees has 10 rows with a Null `WindowsUserName` under its unique index 'WindowsUserName'. `UniqueIndexChecker` encodes Null like any other value and compares encoded keys, and `IndexMaintainer`'s bulk rebuild throws on equal encoded keys. Repro: on a copy of NorthwindTraders.accdb, `InsertRowAsync("Employees", new RowValues { ["FirstName"] = "Ada", ["LastName"] = "Lead", ["WindowsUserName"] = "ada.lead" })` throws "Unique index violation on table 'Employees': duplicate key detected after row mutation". Planned in wave 2: write-pipeline-b lets a unique index that is not the primary key hold several all-Null keys.
- **A full index rebuild of a large index throws `NotSupportedException`.** `UsageMap.WriteInlineRow` writes an index's `used_pages` map only in the INLINE form, and throws "REFERENCE usage maps for index pages are not yet supported" when the rebuilt B-tree's pages span more than one inline bitmap window. A table in a relationship takes the full rebuild on every write (under "Performance"), so a large child table can reach it: `CreateRelationshipAsync` over 20,000 Orders rows that already have two indexes throws. So do `AddAttachmentAsync` fills, whose flat-table rebuilds threw at call 256 of a 400-row fill and at call 338 of an 800-row fill, while another 800-row run finished; where it throws depends on where the rebuilt trees land. Planned in wave 2: pager-b writes REFERENCE usage maps for indexes too.
- **`AccessWriter` cannot open Access-native flat Agile ACCDB files, the format `EncryptAsync` writes by default for `.accdb`.** Both `AccessWriter.OpenAsync` overloads throw `NotSupportedException` for `AccessEncryptionFormat.AccdbAgile` before checking the password, taking a lock-file slot or writing anything, because the writer has no AES-256-CBC page cipher for that layout; the reader decrypts such a file whole into memory. So a file the library encrypts with default options cannot then be edited by it. The README gives the workarounds: decrypt, edit and encrypt again, or re-encrypt as `AccdbAgileCfb`, which the writer opens. Planned in wave 2: encryption-flat-agile.
- **AddColumn, DropColumn and RenameColumn throw `NotSupportedException` on every Access-authored table with an Attachment or multi-value column.** The rewrite (`TableSchemaEditor`, through `IndexHelpers.ProjectIndexes`) forwards every Normal or PrimaryKey index whose key columns survive, including Access's unique, Required complex-column index (`<column>_<32 hex>`), and `CatalogArtifactWriter.CreateCatalogTableArtifactAsync` then calls `IndexHelpers.ResolveIndexes`, which refuses a Complex or Attachment key ("Microsoft Access does not permit indexes on this column type"). Nothing is written. Affected: NorthwindTraders.accdb ProductCategories, ComplexFields.accdb Documents and complexDataTest Table1 (all three operations checked there). As a result, the rewrite's carry of the TDEF complex AutoNumber (TDEF@28) and its per-row reference assignment are tested only on tables the writer created. Fix idea: rebuild a projected complex-column index as the same unique, Required index instead of treating it as a user declaration; the rebuilt `LvProp` keeps the properties the writer does not model, such as memo-data's `AppendOnly`. Then test a rewrite on complexDataTest, where TDEF@28 (7 in V2007, 8 in V2010) is above the largest live reference (4). Not planned yet.
- **An insert with a few MEMO or OLE values under the inline caps throws for a row too long, where Access would move some of them to LVAL pages.** `LongValueEncoder.PrepareLongValues` moves a value to LVAL pages only when that one value is over its cap (`Constants.LongValue.MaxInlineMemoBytes`, 1,024 encoded bytes, or `MaxInlineOleBytes`, 256 bytes). The row has no budget, so `RowEncoder.SerializeRow` throws `JetLimitationException` past `DataPageLayout.MaxRowLength` (2,036 bytes on Jet3, 4,080 on Jet4 and ACCDB), before anything is written. Repro: on a Jet3 table of `Id` and three MEMO columns, `InsertRowAsync` with three 1,000-character strings throws "The row is 3058 bytes, which exceeds the 2036-byte maximum"; five such MEMOs on Jet4 or ACCDB give 5,091 bytes. The README's "Table and row size" limitation documents this. An update that grows a row this way throws the same exception before it changes any row. Fix: when the serialized row is too long, move the largest inline MEMO or OLE values to LVAL pages until it fits, still before any page is written. Not planned yet.
- **`CreateRelationshipAsync` refuses Jet3, Jet4 and slim-catalog ACCDB files the writer created, because `CreateDatabaseAsync` writes none of Access's standard system objects there.**
  - `AccessWriter.InitializeFreshDatabaseAsync` calls `ComplexColumnManager.ScaffoldSystemTablesAsync`, which returns early unless the format is ACCDB with `WriteFullCatalogSchema`. So those files have no `MSysObjects` row naming `MSysObjects`, no Tables, Databases or Relationships containers, no `MSysDb`, and no `MSysACEs`, `MSysQueries` or `MSysRelationships` tables. Reads do not need them (`CatalogRowReader.FindSystemTableTdefPageAsync` resolves `MSysObjects` to TDEF page 2), but with no `MSysRelationships`, `RelationshipManager.CreateRelationshipAsync` throws `NotSupportedException`, as the README's "Foreign-key relationships" section says.
  - `TDefPageBuilder.WriteJet3HeaderDefaults` and `WriteJet4AceHeaderDefaults` also write Access's defaults 3, 4 and 5 into the header's `MSysACEs`, `MSysQueries` and `MSysRelationships` TDEF fields (the i32 values at 0x24, 0x28 and 0x2C), and only the full-catalog ACCDB path patches them (`PatchHeaderSystemTablePagesAsync`), so on these formats the fields name pages that hold other things. Repro: `CreateDatabaseAsync(Jet4Mdb)`, then `CreateTableAsync("T")`; unmasked, the fields read 3, 4 and 5, and pages 3, 4 and 5 have page types 04, 04 and 01. On Jet3, page 3 is T's TDEF. The slim-ACCDB case is from the code, not run.
  - Either create the tables or stop naming pages that do not hold them. Not planned yet; whether Access needs those rows needs a DAO run.
- **`RenameColumnAsync` refuses a rename that changes only the letter case.** `TableSchemaEditor.RenameColumnAsync` compares the new name, ignoring case, with every column, the renamed one included, so `RenameColumnAsync("T", "Name", "NAME")` throws `InvalidOperationException` "Column 'NAME' already exists in table 'T'." Leave the renamed column out of the check, and check the case-insensitive `mapColumnName` callback that rewrites expressions, indexes and complex-column names. Access is believed to allow the rename; this is unchecked. Not planned yet.
- **Attachments and multi-value items can be added but not removed or replaced one at a time.** The writer changes them only through `AddAttachmentAsync` and `AddMultiValueItemAsync`; their rows in the hidden flat table go only with the parent row, the table or the column. Planned in wave 2: value-model-b adds item ids and removes and replaces items.
- **`BeginTransactionAsync` inside an open transaction throws, and there are no public savepoints.** `TransactionLifecycle.BeginTransactionAsync` refuses a second transaction with `InvalidOperationException` ("A transaction is already active on this writer. Only one concurrent transaction per AccessWriter is supported."), where DAO's `BeginTrans` nests up to five levels (from memory, not checked). Wave 2's atomicity-a adds internal savepoint frames that a public API could expose. Not planned yet: deferred from wave 2.

## Partial writes and pages left allocated

- **`CreateTableAsync` and `InsertRowsAsync` can fail after their first page write and leave what they wrote.** Wave 2's atomicity-b rolls such a call back. The first two below (`IsAutoIncrement` on `byte` or `long`, and a `byte[]` `DefaultValue`) are refusals that belong with the argument checks, before any I/O; that is not planned yet.
  - `IsAutoIncrement` on a `byte` or `long` column is refused by `ConstraintRegistry.Register` (`NotSupportedException`, "IsAutoIncrement is only supported for Int16 and Int32"), which runs at the end of `CatalogArtifactWriter.CreateCatalogTableArtifactAsync`, after the TDEF, index leaves, usage map, `MSysObjects` row and `MSysACEs` rows are written, so the table stays in the file. Repro, run as a probe: on a new ACCDB, `CreateTableAsync("T", [new("Id", typeof(long)) { IsAutoIncrement = true, IsNullable = false }])` throws, and a reopened reader's `ListTablesAsync` returns `T`; `typeof(byte)` behaves the same. From the code: `IsAutoIncrement` on a non-integer type throws `ArgumentException` from the same place, and `AddColumnAsync`, which builds its `~tmp_<guid>` table through the same path, probably leaves that table behind (not checked). The check belongs with the argument validation in `TableSchemaEditor.CreateDeclaredTableAsync` and `AddColumnAsync`. `AutoNumberTests.AutoIncrement_OnUnsupportedIntegralType_ThrowsNotSupported` asserts only the throw. The `ColumnDefinition.IsAutoIncrement` summary says it is "Only valid for byte, short, int, and long columns", while the README says `byte` and `long` throw, and `IAccessSchema.CreateTableAsync`'s `NotSupportedException` docs omit the case.
  - A `byte[]` `DefaultValue` throws `NotSupportedException` from `JetExpressionConverter.BuildLvPropBlob` (through `ToJetExpression`) after the TDEF, index-leaf and usage-map pages are written, and without `UseTransactionalWrites` those pages stay allocated. Repro: on a fresh ACCDB, `CreateTableAsync("B", [Id int, Bin byte[] with DefaultValue = new byte[] { 1, 2 }])` throws, and the file grows from 131,072 to 139,264 bytes. From the code, any `DefaultValue` type `ToJetExpression` does not handle (it handles string, bool, the integral types, float, double, decimal, `DateTime` and `Guid`), such as `TimeSpan` or `DateTimeOffset`, fails the same way. `AddColumnAsync` does not leak, because `RewriteTableAsync` serializes the properties before it writes anything. Fix: have `TableSchemaEditor.ValidateDeclaredDefault` check that the literal converts.
  - Not reproduced: `CatalogArtifactWriter.CreateCatalogTableArtifactAsync` reserves the TDEF pages, allocates an empty leaf per index and appends a usage-map page before it inserts the `MSysObjects` and `MSysACEs` rows, with no path that releases them, so any later failure without `UseTransactionalWrites` would leave those pages allocated with no catalog row naming them. Repro to try: fail the `MSysObjects` row write with `WriteFaultStream`, then look for TDEF and leaf pages no catalog row reaches.
  - Every `InsertRowsAsync` overload writes its rows one at a time (`TableDataWriter.InsertMappedRowsAfterValidationAsync`), so when row N fails, for example with `JetLimitationException` because it is larger than a data page, or with a foreign-key refusal, which is checked just before each row is written, rows 1 to N-1 are already on data pages. `RollbackInsertedRowsAsync` marks them deleted and rewinds the TDEF row count, so no row stays live, but the deleted slots and any data pages appended for them remain. A single-row insert leaves the file unchanged, because the row is measured before any page is written. Fix idea: serialize and size-check every row of the batch before writing the first.
- **Dropping a table, or a complex column, leaves the hidden flat table's pages allocated.** `ComplexColumnManager.DropComplexChildrenForTableAsync`, which `DropTableAsync` calls, and `DropSingleComplexChildAsync`, which a schema rewrite calls for a dropped Attachment or multi-value column, mark only the `MSysComplexColumns` and `MSysObjects` rows deleted. The flat table's TDEF, data, index and usage-map pages stay allocated until Compact & Repair. Repro: on a new ACCDB, create `Docs` (`Id` primary key, `Files` attachment), insert a row and add one attachment, read the flat table's TDEF page from `GetComplexColumnsAsync("Docs")[0].FlatTableId` (36), then `DropTableAsync("Docs")`: the page keeps type 0x02 and `PageAllocator.IsPageFreeAsync` returns false. `DropSingleComplexChildAsync` was read, not run. Not planned yet.
- **Under `SecureEraseMode.DeletedRowsAndFreedPages`, cascade deletes, cascade updates, the attachment and multi-value rows a parent row's delete removes, and a rolled-back insert batch leave the deleted rows' MEMO and OLE values on their LVAL pages.** They call the `TableRowStore.MarkRowDeletedAsync` overload that takes no `TableDef` (`RelationshipEnforcer.ApplyCascadeDeletesAsync` and `ApplyCascadeUpdatesAsync`, `ComplexColumnManager.ApplyComplexChildDeletesAsync` and `TableDataWriter.RollbackInsertedRowsAsync`), which clears the row's bytes but cannot find its long values, so those are neither scrubbed nor freed. `UpdateRowsAsync` and `DeleteRowsAsync` pass the `TableDef` for the caller's own rows. From the code, not run. Planned in wave 2: write-pipeline-a1 scrubs and frees long values on every delete path.
- **`AddAttachmentAsync` and `AddMultiValueItemAsync` rebuild every index of the hidden flat table on each call, so adding items one at a time grows quadratically in time and file size.**
  - `ComplexColumnManager.AddComplexItemCoreAsync` inserts the flat row and then calls `MaintainIndexesAsync`, which decodes every live flat row and builds every flat-table index again. The replaced trees are never freed, because `RebuildIndexesAsync` frees replaced index pages only for tables without long-value or complex columns, and never for flat tables.
  - Measured on 2026-10-03 with a Release build on a shared Arm64 machine: an ACCDB table `Docs` (`Id` primary key, `Files` attachment) with 800 rows, one 1 KB attachment added to each row, no transaction. Calls averaged 9.2 ms over the first 100 and 183 ms over the last 100, and the file grew from 196 KB to 23 MB, with 5,015 of its 5,860 pages index pages. The same 800 values inserted into an indexed table, one `InsertRowAsync` each, took 1.4-2.8 ms per call throughout and left a 3.3 MB file with 14 index pages.
  - The rebuilt trees are what reach the REFERENCE usage-map `NotSupportedException` under "Writes refused"; REFERENCE maps would remove the throw, but not the rebuilds or the growth.
  - Fix: insert through `InsertRowDataLocAsync`, pass the row and its location to `TryMaintainIndexesIncrementalAsync` as `TableDataWriter`'s inserts do, and rebuild only when that bails. Planned in wave 2: write-pipeline-a2 #3 routes complex-column writes through the one write path and maintains the flat-table indexes incrementally (at most 6 index page writes per item over 300 items).
- **Replaced index trees stay allocated and unreachable until Compact & Repair.**
  - `IndexMaintainer.TryMaintainIndexesIncrementalAsync` never frees the tree that an incremental multi-level rebuild (`IndexBTreeEditor.TryPlaceTreeAsync`) replaces, or the root leaf it grows into a tree, and `IndexBTreeEditor.TryRebuildCatalogIndexTreeAsync` does the same for catalog indexes. Repro: 3,000 random single inserts into a table with a primary key, then count the 0x03/0x04 pages owned by its TDEF that no `first_dp` reaches (`PageAudit.FindUnreachableIndexPagesAsync`): 7 on Jet4 and ACCDB, 12 on Jet3. Root-leaf growth is also unchecked against DAO Compact & Repair (catalog-index-maintenance-notes.md).
  - The full rebuild (`RebuildIndexesAsync`) frees the trees it replaces only on tables that have no Memo, OLE or complex columns and are neither flat tables nor `MSys*` tables. On Jet3 it finds the old trees by walking them from `first_dp` (`CollectJet3ReplacedTreePagesAsync`), and only for indexes whose `used_pages` is 0, as every writer-created one is; an Access-authored Jet3 index names a usage-map row the writer cannot rewrite, so its old tree stays. A table with an FK entry takes the full rebuild on every write, so an Access-authored Jet3 table in a relationship, and any table with Memo, OLE or complex columns in one, grows with every insert, update and delete. Repro: in a copy of indexTestV1997.mdb, insert 1,500 rows into Table1 (`[i, i % 3, 10 + i % 4, "d", 0]` for i from 100), then make 10 single inserts: 360 of Table1's index pages are unreachable, 36 per insert.
  - FK entries that `DropTableAsync` (`RelationshipManager.RemovePartnerLinksAsync`) or `DropRelationshipAsync` removes leave their index leaves allocated, and `TryReclaimTrailingRealIdxAsync` reclaims only trailing unreferenced real-idx slots, so a slot in the middle of the array stays in the partner's TDEF. Reclaiming it means renumbering `index_num2` and every cross-TDEF `rel_idx_num` that points at it (index-and-relationship-format-notes.md §9, W14).
  - Planned in wave 2 for the first bullet only: write-pipeline-b #3 and #4 replace the incremental and catalog tree rebuilds with in-place B-tree edits, which free emptied index pages on user tables. The full rebuild's exclusions and the FK-entry leaves that `DropTableAsync` and `DropRelationshipAsync` leave are not planned yet.
- **The LVAL pages the writer allocates go into no usage map, and a table's INLINE owned-pages map is never promoted to REFERENCE.**
  - `LongValueEncoder` allocates each LVAL page through `PageAllocator.AllocatePageAsync` and records it in neither the table's owned-pages map nor the long-value column's own owned and free-space maps, where Access lists its LVAL pages (calcFieldTestV2010 Table1's AllNames: rows 2 and 3 of usage-map page 0x57). Drops and rewrites free the writer's LVAL pages through each row's Memo and OLE headers (`ReclaimTableStoragePagesAsync`), but anything that finds a table's LVAL pages through usage maps misses them.
  - `DataPageInserter.MarkPageInOwnedMapAsync` marks only the data pages the writer appends, and only in the INLINE form (a 64-byte bitmap covering 512 pages from its `start_page`), so a page outside that window is left out. On Jet3 the writer keeps no table usage maps at all (`CanMaintainOwnedMapAsync`).
  - The cost: `DatabaseFile.ValidateOwnedDataPagesAsync` rejects a map that leaves out data pages, because the live rows fall short of `num_rows`, so the first scan of a large writer-built MEMO or OLE table falls back to `BuildOwnedDataPageIndexAsync`, the whole-file owned-page pass (25,228 page reads on the benchmark MEMO database), and another scan that needs the index meanwhile waits on the `ownedDataPageIndex` gate.
  - Whether Access's table owned-pages maps also list LVAL pages has not been surveyed. Planned in wave 2: pager-b (the promotion and the survey).
- **A crash during `EncryptAsync`, `DecryptAsync` or `ChangePasswordAsync` by path leaves `<db>.reenc-<guid>.tmp` beside the database, and nothing removes it; on Linux and macOS the rename is not durable.** `EncryptionManager.ReplaceFileAtomicAsync` creates the temp file, flushes it and calls `ReplaceFileWithTemp`, and deletes it only when the temp write fails or is cancelled, or when both renames are refused. A crash between creating it and the rename leaves it (the database holds the old or the new contents), and nothing looks for a stale `*.reenc-*.tmp`. On Linux and macOS the directory entry the rename changes is not flushed, so a power loss just after the call returns can still show the old file; the wave-2 crash journal has the same gap. Fix idea: sweep stale `<db>.reenc-*.tmp` files before a path re-encryption, and flush the directory after the rename on Unix. Not planned yet; encryption-containers #3, which rewrites path re-encryption, is where it belongs.
- **A writer over a caller stream that is not a `FileStream` gets no crash recovery from the rollback journal.** Nothing makes a write-back crash-safe today (**Transactions are not atomic**, under "Design flaws"), and wave 2's crash-journal journals only files opened by path or as a `FileStream`: any other caller stream keeps an in-process undo only, so a process crash or power loss during a write-back can leave its bytes torn. A caller-supplied journal stream would cover it. Not planned yet: deferred from wave 2.
- Minor:
  - **Deleting a two-hop overflow row under `DeletedRowDataMode.Clear` or `SecureEraseMode.DeletedRowsAndFreedPages` leaves the middle slot's 4-byte pointer.** `TableRowStore.MarkOverflowRowDeletedAsync` resolves the header to the final target through `TryResolveOverflowRowAsync`, zeroes the target's bytes and the header's pointer and flags the header 0xC000, but never touches the middle slot, which holds a row index and page number, not row data. Repro: the `OverflowRowLayout.TwoHop` row (`SyntheticOverflowRows`), then `DeleteRowsAsync` with secure erase; the middle slot's bytes are unchanged. Fix idea: have the overflow walk report its intermediate slots. Not planned yet.
  - **The surgical index split paths append their pages outside `PageAllocator` (not reproduced).** `IndexBTreeEditor.TryAppendContiguousAsync`, which `TrySurgicalMultiLevelMaintainAsync` and `TrySurgicalCrossLeafMaintainAsync` use, appends through `DatabaseFile.AppendPageAsync`, so the splits never reuse free pages, and an append that fails or lands out of sequence leaves the pages already appended unlinked. Repro to try: make a surgical split append two pages with `WriteFaultStream` failing the second, then look for the first with `PageAudit.FindUnreachableIndexPagesAsync`. Fix idea: reserve the run through `PageAllocator.ReserveContiguousPagesAsync` and a `ReservedPageRuns`, as `TryPlaceTreeAsync` does. Planned in wave 2: write-pipeline-b #4 deletes these paths with `IndexBTreeEditor`, and #2's `IndexPageStore` allocates through `PageAllocator`.

## Values that differ from Access or between writers

- **The writer does not enforce every constraint stored in the file.** The README's "Column defaults and validation rules" limitation documents the first two.
  - Table-level (record) validation rules: a table's `ValidationRule` and `ValidationText` are in the table-level target of its `MSysObjects.LvProp` blob, the block with an empty name, which can come anywhere among the blocks. `ConstraintRegistry` loads only column targets, and no production code calls `ColumnPropertyBlock.FindTableTarget`, so inserts and updates never evaluate a table rule, including rules Access wrote. `TableSchemaEditor.RewriteTableAsync` passes the projected blob to the rebuilt table through `CatalogTableArtifact.PersistedProperties`, where enforcement can register the rule.
  - A stored default or rule the expression engine cannot parse or evaluate is skipped. `ColumnValidationRule.Compile` returns `Unsupported`, `Accepts` returns true for an unsupported rule and for one whose evaluation throws `ArgumentException`, `NotSupportedException`, `InvalidOperationException`, `FormatException`, `InvalidCastException`, `ArithmeticException` or `IndexOutOfRangeException`, and when `ColumnDefaultValue.TryEvaluate` fails, an omitted column stays DBNull, which stores Null or, on a Required column, throws "... is marked NOT NULL and no value was supplied". Examples: `GenGUID()`, `CurrentUser()`, `DLookUp`. So the writer refuses an insert that leaves out a Required ReplicationID column whose default is `GenGUID()`, which Access fills, and never checks a rule that uses `DLookUp`.
  - `ConstraintRegistry.ApplyAsync` (insert) and `ApplyUpdateAsync` (update) skip every check (NOT NULL, AutoNumber generation, defaults, rules and calculated-column recomputation) when the cached constraint list's count differs from the TDEF column count or from the row's length. No trigger is known apart from a positional row of the wrong length, which `TableRowStore` then refuses with `ArgumentException` ("Expected N values for table row but received M") after the earlier rows of a batch are written, but nothing checks that the list matches the columns by name. Fix idea: rebuild the list from the `TableDef`, matching names per position, or throw.
  - Planned in wave 2: constraints-a enforces table rules, evaluates `GenGUID()` and `CurrentUser()` and refuses a write whose default or rule it cannot evaluate, and rebuilds a stale constraint list from the file instead of skipping the checks.
  - Once constraints-a refuses instead of skipping, a table whose stored default or rule uses a function the expression engine lacks (`DLookUp` and the other domain aggregates, `Eval`, or any function it does not implement) refuses every insert, and every update the rule covers, where today the check is skipped. No fixture holds such an expression. Not planned yet: deferred from wave 2; record each function users report, and constraints-a moves this bullet to its own item when it deletes this one.
- **Text comparisons in validation rules, defaults and calculated columns are ordinal and ignore case, rather than following the database sort order.** `CalculatedExpressionCoercion` compares text with `string.Compare(..., StringComparison.OrdinalIgnoreCase)`, which is UTF-16 code-unit order, so a rule such as `>="M"` or `Between "A" And "F"` can accept or reject accented letters and punctuation differently from Access, which compares by the database's sort order (General Legacy, General or General 97). Neither the README nor the design docs mention it. Planned in wave 2: collation compares text in rules and calculated columns by the database sort order.
- **`GeneralLegacyTextIndexEncoder` encodes 1 of the 8 keys of the `Unicode` index on testUnicodeCompV2003.mdb's table `Table` differently from the leaf Access wrote.** A wave-2 probe re-encoded the text index leaves of the Access-authored fixtures (about 1.07M keys in 94 files) with the encoder for each sort order; every other key matched, apart from fixedTextTest*'s `Users2_8_idx`, whose column reads as Null (**Fixed-length Text columns read as Null**). Which character differs is not recorded; collation #1's fixture test skips this index. Not planned yet: deferred from wave 2.
- **New databases and text columns cannot be given a sort order.** `CreateDatabaseAsync`, `CreateTableAsync`, `AddColumnAsync` and `ColumnDefinition` take none, so new Jet4 and ACCDB text columns are stamped General Legacy (0x0409, version 0) and Jet3 columns are left unstamped (**Jet3 table definitions**, under "Unchecked against Access"), while Access 2010 and later create new databases with the General sort order (from memory, not checked). Wave 2's collation keeps the sort order internal and new files General Legacy. Not planned yet: deferred from wave 2.
- **Defaults.** Not planned yet.
  - A Boolean, text or date CLR `DefaultValue` on a column of another type stores one value in the declaring writer and another in every later writer. With no `DefaultValueExpression`, `JetExpressionConverter.ToJetExpression` persists the value as a literal (True or False, a quoted string, `#yyyy-MM-dd HH:mm:ss#`), which a reopened writer compiles (`ColumnDefaultValue`) and converts with Access's rules. The declaring writer applies `ConstraintRegistry.ToAppliedClrDefault`, which reads numbers back from their literal and cuts a `DateTime` to the second but returns every other value as given, for the row encoder to `Convert`. Repro, run as a probe: `true` on a Long Integer column stores 1 and then -1, as Access does; on a Text column it stores "True" and then "-1"; a `DateTime` on a Text column stores "02/29/2024 08:30:15" and then "2/29/2024 8:30:15 AM". Evaluating the literal through the expression engine at registration would fix it, but a text default the engine cannot read would then give no default in the declaring writer too. The `ColumnDefinition.DefaultValue` remarks state the gap.
  - A blank but non-null `DefaultValueExpression` (" ") beside a CLR `DefaultValue` is persisted instead of the CLR literal, because `JetExpressionConverter.ApplyColumn` takes `col.DefaultValueExpression ?? ToJetExpression(col.DefaultValue)`, while `ConstraintRegistry` treats a blank expression as none (`ToConstraint`, `ToAppliedClrDefault`, `HydrateFromTableDef`). So the declaring writer applies the CLR default and a reopened writer none. From the code, not run. Fix idea: treat a blank expression as null in `ApplyColumn`, or reject it in `TableSchemaEditor.ValidateDeclaredDefault`.
  - `ConstraintRegistry.HydrateFromTableDef` and `ToConstraint` keep a `ValidationRule` property on an AutoNumber column, so a rule another tool stored there is checked against generated values, where Jackcess ignores every property on an AutoNumber column. From the code, not run; what Access does is unchecked.
- **Expressions.** Calculated columns, defaults and validation rules share one engine. Not planned yet.
  - Custom `Format` date codes are .NET's: `CalculatedExpressionFormattingFunctions` passes an unrecognised format to `DateTime.ToString(format, CultureInfo.InvariantCulture)`, so `Format(#2020-01-31 06:00#, "mm/dd/yyyy")` gives `00/31/2020` where VBA gives `01/31/2020`. Translate VBA's codes first: `m` and `mm` are the month unless they follow an `h` or precede an `s`, `n` and `nn` are minutes, and `ttttt`, `AM/PM`, `w`, `ww`, `q` and `y` have VBA meanings.
  - The named date formats use .NET's invariant patterns: `Format(d, "Long Date" | "Short Date" | "Long Time" | "Short Time")` and `FormatDateTime(d, 1..4)` use `D`, `d`, `T` and `t`, so `FormatDateTime(DateSerial(2025, 2, 3), 2)` gives `02/03/2025` and `Format(#2020-01-31#, "Short Date")` gives `01/31/2020`, where VBA en-US gives `2/3/2025` and `1/31/2020`; Short Time and Long Date differ too. The numeric named formats also use the invariant culture (`"Currency"` gives the `¤` symbol) and have not been compared with VBA.
  - `DateValue` keeps the time: `CStr(DateValue(#2020-01-31 06:00#))` gives `1/31/2020 6:00:00 AM` and `CStr(DateValue("6:00:00 AM"))` gives `6:00:00 AM`, where VBA gives `1/31/2020` and `12:00:00 AM`. `CalculatedExpressionNormalizer` rewrites every `#...#` literal as `DATEVALUE("...")`, so the fix has to keep a literal's time, for example through a separate internal function for literals.
  - `DateSerial` truncates its arguments (`checked((int)ToDecimal(arg))`) where VBA rounds them half to even: `DateSerial(2020, 1, 1.5)` and `DateSerial(2020, 1.6, 1)` both give 1/1/2020, where VBScript gives 1/2/2020 and 2/1/2020. `ToVbaInteger`, which `TimeSerial` uses, rounds correctly.
  - `Now()` and `Time()` keep fractions of a second, because `CurrentAccessLocalDateTime` is `DateTime.Now`, so `=Now()` and `=Time()` defaults store milliseconds; VBA's `Now` and `Time` are whole seconds. Truncate in `CurrentAccessLocalDateTime`, which `Date()` and `Timer` share.
  - Intermediate numbers are Decimal or Double rather than VBA's Variant subtypes: number literals parse as `double` (`CalculatedExpressionAstFactory.NumberValue`), radix literals become plain decimal numbers, and `AccessVariantOperators` keeps arithmetic on two non-date operands in `decimal`. So `CStr(1/3)` has 28 digits (VBA: 15), `TypeName(&H10)` is `Double` (VBA: `Integer`) and `VarType(&HFFFF)` is 14 (VBA: 2). Fix: carry Integer, Long, Double, Currency and Decimal through literals and operators.
  - A table-qualified field reference is not evaluated, and the error names an internal placeholder. `CalculatedExpressionNormalizer` replaces each bracketed name with its own `__JdwCalcCol<n>` placeholder, and `CalculatedExpressionEvaluationContext.GetNameValue` maps only single placeholders back. Repro: on ACCDB, `CreateTableAsync("T", [Price double, Calc double calculated "[T].[Price]*2"])` succeeds, and an insert that leaves Calc Null throws `InvalidOperationException` "references unknown name '__JdwCalcCol0.__JdwCalcCol1'"; `T.Price*2` fails with unknown name 'T.Price', and `[T]![Price]*2` with a syntax error. A validation rule written that way is never enforced, because a rule whose evaluation fails accepts the value. `IAccessSchema.RenameColumnAsync`, the README and calculated-columns-format-notes.md say the engine does not evaluate table-qualified references. Fix: resolve the table's own qualifier, or reject it when the column is declared, and name the reference as written.
- **Complex columns.** Not planned yet.
  - A multi-value `string` column with no `MaxLength` gets a Memo `Value` column and reports "Multi-value Memo", though Access has no multi-value Memo. `ComplexColumnManager.BuildFlatTableSchema` gives `Value` the parent's `MaxLength`, and `JetTypeInfo.TypeCodeFromDefinition` maps a string whose `MaxLength` is outside 1..255 to Memo, while `ResolveComplexTypeTemplateName` points the `MSysComplexColumns` row at `MSysComplexType_Text` (TEXT(255)). Fix: give the `Value` column Text(255) when `MaxLength` is 0, and refuse a `MaxLength` over 255.
  - `InsertRowAsync<T>` with a POCO whose `byte[]` property holds a complex cell read back through `Rows<T>` throws `InvalidCastException` ("Unable to cast object of type 'System.Byte[]' to type 'System.IConvertible'"). `ConstraintRegistry` (`SuppliedComplexReference`, `TryGetComplexReference`) accepts only a `ComplexIdRef` or an integer as a supplied reference, so the `byte[]` stays in the row and `RowEncoder` calls `Convert.ToInt32` on it. Whether to ignore such a cell, giving the row a fresh reference as for null (Jackcess ignores a value given for a complex column by default), or to reject it with an `ArgumentException` naming the column is the user's call (under "Decisions left to the user").
  - Complex columns on tables the writer creates get no complex-column index. Access gives each one a unique, Required index on the parent row's 4-byte per-row reference, named `<column>_<32 hex>` truncated to 64 characters (for example `Attachments_CFC7F98A63064F2DBDB6822D653AB763` in ComplexFields.accdb), with Long Integer keys (`7F` and a big-endian int with the sign bit flipped). `BuildFlatTableSchema` emits only the flat table's indexes (`MSysComplexPKIndex`, the FK index and, for attachments, `IdxFKPrimaryScalar`), and `IndexHelpers.ResolveIndexes` refuses a declared index on an Attachment or Complex column. `IndexKeyEncoder` encodes such keys, and index maintenance and `ComplexColumnManager.HasComplexColumnIndexAsync` keep them current on Access tables. Fix: emit the index in `CreateTableAsync` and in `AddColumnAsync` of a complex column, together with lifting the schema-rewrite refusal under "Writes refused".
  - Updating an append-only Memo column (column property `AppendOnly`) adds no version-history row, as Access does. The version-history flat table has `_VersionHistory_<GUID>` (the per-row reference), `<memo column name>` (Memo), `Modified_<GUID>` (DateTime) and the AutoNumber key `<table>_VersionHistory_<GUID>`; complexDataTest*.accdb Table1 holds five versions. ## Performance

- **The reader's system-table lookups rescan and decode all of `MSysObjects` on every call.** `CatalogRowReader.FindTableTdefPageAsync` reads the `MSysObjects` TDEF and calls `GetCatalogRowsAsync`, which reads every `MSysObjects` data page through `DatabaseFile.ForEachLiveTableRowAsync`, not the reader's `ReaderPageCache`, and decodes the Id, ParentId, Name, Type and Flags of every catalog row before it matches one; nothing is cached between calls. The reader uses it in `CatalogReader.ResolveTableAsync` for any name that is not a user table, and in `ComplexColumnReader`'s `MSysComplexColumns` and flat-table lookups on every metadata or complex-column read. The linked-table listing and the complex-column object-name lookup also rescan `MSysObjects` on every call, though they decode only the columns they use. Measured with a counting stream on NorthwindTraders.accdb (not re-measured since the catalog scans began decoding only the columns they use): each repeated `GetColumnMetadataAsync("Employees")` (a table with an attachment column) read 217,088 bytes, and each repeated `GetColumnMetadataAsync("MSysObjects")` or `GetColumnMetadataAsync("MSysRelationships")` 208,896, where a cached lookup that stops at the first match reads 20,480 and 12,288. With the page cache off, on NorthwindTraders.accdb `ListLinkedTablesAsync` reads 200,704 bytes over 9 pages and `GetComplexColumnsAsync("Employees")` 430,080 bytes over 13; on odbcLinkerTestV2007.accdb the listing reads 110,592 bytes over 6. Fix idea: cache the decoded catalog rows in `TableCatalog` and drop them whenever the writer changes the catalog, after an audit of the writer's cache invalidation. Planned in wave 2: read-composition-a caches the reader's table resolution and complex-column descriptors, so repeated metadata calls read nothing after warm-up.
- **Reading a table's persisted properties decodes the `LvProp` of every catalog row before the table's own, LVAL pages included, on every call.** `ColumnPropertyReader.ReadLvPropForTableAsync` enumerates `MSysObjects` through `RowDecoder.EnumerateTypedRowsForTdefAsync` with `Id` and `LvProp` wanted, until the row whose `Id` equals the TDEF page, and caches nothing. Column metadata (`SchemaReader`, `HydrateCalculatedResultTypesAsync`), a writer's constraint load (`TableSnapshotReader.ReadLvPropBlockAsync`) and every AddColumn, DropColumn and RenameColumn pay it, so a table late in the catalog reads the property blobs of every object before it. From the code, not measured. Smaller interim fix: scan with only `Id` wanted, then decode the matching row's `LvProp`. Planned in wave 2: read-composition-a reads only the table's own catalog row.
- **An update, and a session's first insert into a table whose TDEF is at page 1024 or below, read every data page of the table, and an update can read every page of the file.** When the writer's single insert-page hint names another table, as it does at a session's first insert, `DataPageInserter.FindInsertTargetAsync` calls `TryFindExistingSystemTablePageAsync` for a TDEF at page 1024 or below, which calls `DatabaseFile.GetOwnedDataPagesAsync`. That validates the owned-pages usage map by reading every page it lists (`ValidateOwnedDataPagesAsync`), and the writer's `DatabaseFile` is built with `canCacheOwnedDataPages = false`, so every such lookup repeats the reads. Inside `UpdateRowsAsync` the old rows are already marked deleted when the re-insert looks for a page, so the live rows fall short of `num_rows`, the map is rejected, and `BuildOwnedDataPageIndexAsync` reads every page of the file, uncached inside a transaction too. `AutoNumberTests` warm the hint with an update to keep this out of their page counts. Repro: on a writer-created ACCDB, `P` (`Id` primary key, `N`; rows 1 and 2) and `C` (`Id` primary key, `PId`); open a writer over `CountingStream`, run `InsertRowAsync("C", [1, 1])`, then `UpdateRowsAsync("P", "Id", 1, {N = "x"})`: the update reads every page. Planned in wave 2: pager-b's owned-page index.
- **Every insert, update and delete on a table in a relationship rebuilds all of the table's indexes from a full decode of its rows.** `IndexMaintainer.TryMaintainIndexesIncrementalAsync` bails (C1c, "foreign-key logical index present") whenever the table's TDEF holds an FK logical index, which the writer emits on both sides of every relationship, because Access Compact & Repair rejected incrementally maintained relationship-backed indexes in probe validation. The bulk rebuild (`MaintainIndexesAsync`) decodes every live row through `TableSnapshotReader.ReadRowsAsync`, re-encodes every key and rebuilds every tree, so each write costs time in proportion to the table's size; on a large table the rebuilt trees reach the REFERENCE usage-map throw, and on some tables the replaced trees stay allocated (both above). index-and-relationship-format-notes.md documents that FK tables take the bulk rebuild. Not planned yet: wave 2 defers removing the C1c bail until the DAO run (under "Before 4.0.0 ships") passes.
- **A delete that a relationship without cascading deletes refuses reads every row of the child table when the child has a MEMO, OLE, Attachment or multi-value column.** `RelationshipEnforcer.PlanCascadeDeletesAsync` calls `FindDependentRowsAsync` before it looks at `CascadeDeletes`. That seeks the child's foreign-key index and then reads every column of each row found (`TryReadAllRowsTypedAsync`), which `DatabaseFile.TryReadColumnValuesTypedAsync` cannot do for a non-null MEMO or OLE value or a complex column's reference, so it falls back to `TableSnapshotReader.ReadRowsAsync` over the whole child table, long values included, only to count the rows for the refusal. A key update refuses from the seek's row locations (`CountDependentRowsOfKeyChangeAsync`). Repro, run as a scratch test on Jet4 and ACCDB: the setup of `ForeignKeyCascadeUpdateTests.Update_RefusedBySeekableRelationshipWithoutCascade_ReadsNoOtherChildPage` (M with 200 rows and a MEMO column over 7 data pages, one row under P.Id 1, FK_M_P not cascading), with `DeleteRowsAsync("P", RowCriteria.Where("Id", 1))` in place of the update, reads all 7 of M's data pages before it refuses. Fix: when the relationship does not cascade deletes, count the seek's locations, leaving out the rows in `cascaded`, and read the rows only on the scan fallback. Not planned yet; it belongs with write-pipeline-a1's cascade plan.
- **`Rows<T>(predicate)` compiles its predicate and lists the table's indexes on every call, and a collection `Include` costs 5-6 times a reference include.**
  - `IndexRowReader.Rows<T>(tableName, predicate, ...)` calls `predicate.Compile()` and `IndexPredicateTranslator.ExtractPushableCriteria` on every call, the typed read builds its materializer again (`RowMapper<T>.Build`), and `RowsInferredAsync` lists the indexes again through `TryPlanIndexReadAsync`. With `PublicSeekBenchmarks` on Relational_1000_10000_v1.accdb (10,000 Orders; not re-measured since captured operands stopped compiling), 1,000 `Rows<T>(o => o.OrderId == key)` lookups took 525 ms and 58 MB, against 38.7 ms through `SeekRowsAsync`, 31.9 ms through `FromIndex(...).WhereEquals` and 2.9 ms for one `Rows<T>()` scan keeping the same keys. read-performance-bottlenecks.md records the numbers and advises explicit seeks in loops.
  - `IncludeLoader.LoadCollectionAsync` loads every child row for all the parents' keys (`BuildChildGroupsAsync`) and only then applies the include's Where, OrderBy, Skip and Take to each parent's list (`ApplyOperations`). With `QueryIncludeBenchmarks` over 1,000 customers and 10,000 orders, a collection include took 52.7 ms and 18 MB, the same include filtered, ordered and capped at five orders per customer 51.9 ms, and a reference include (each order's customer) 9.3 ms and 4 MB.
  - Captured operands are read without compiling, but the predicate and the materializer still compile on every call; planned with wave 2's materializer cache (linq-c) and LINQ plan cache (linq-plan-cache). Profile the `Include` cost before changing it.
- **Index inference scans for a bound its key cannot hold exactly**: a fractional bound on an integral key, or a Currency, Decimal or Single bound with more precision than the key keeps. `IndexSeekFilter` leaves such a comparison to the residual filter, which reads it from the rows the remaining comparisons seek or from a scan, so `r.Id > 1.5` scans. The Date/Time direction rule, which keeps a key that moved away from the matches, could cover these types too and seek `r.Id > 1.5` as `Id >= 2`. Not planned yet; linq-c and linq-plan-cache both edit `IndexRowReader`, where the filter runs.
- **`AccessReader.OpenAsync` reads the 0x80-byte header and then page 0 again: 4,228 bytes in two or more reads.** The stream overload reads the header with `DatabaseFile.ReadHeaderAsync`, and `EncryptionManager.TryDecryptAgileCompoundFileAsync` then reads page 0. The writer reads page 0 once, through `EncryptionManager.ReadOpenHeaderPageAsync`, which the reader could share. Repro: the `CountingStream` in `EncryptionOpenProbeTests.ReaderOpen_ReadsOnlyTheFirstPages` counts 4,228 bytes on an unencrypted ACE file. Not planned yet; encryption-flat-agile #1, which makes `PageFile.ReadHeaderAsync` return the whole 4,096-byte page, may close it.
- **Concurrent scans on a shared reader in `PageReadOptimizationMode.Disabled` run 12-36% slower than in `Auto`, because every page read the cache misses waits for the reader's I/O gate.** `DatabaseFile.ReadPageAsync` reads positionally through `RandomAccess` only after `EnableRandomAccessPageReadsIfSupported` (a path-opened reader in `Auto` or `Enabled` on the net10.0 build) and outside a transaction; otherwise it takes `IoGate`, seeks the shared stream and reads. That covers `Disabled`, every mode of the netstandard2.1 build, and reads inside a transaction. With `AccessReaderConcurrentScanBenchmarks` on the 25,000-row numeric table (405 data pages, more than the default 256-page cache), `Disabled` was 12-36% slower than `Auto` at 4 and 8 simultaneous scans (8 scans: 23-25 ms against 20-21 ms) and 3-9% slower at one, while separate readers took 34-37 ms for 8 scans in either mode. This is not a bug; if `Disabled` matters under concurrency, positional reads on its `FileStream` would take the gate out of page reads. Not planned yet.
- **The writer opens its file with an overlapped handle and the `RandomAccess` hint.** `AccessWriter.CreateStream` uses `FileOptions.Asynchronous | FileOptions.RandomAccess`, and the writer does not set `DatabaseFile.ReadsInlineOnThreadPool`, so its page reads are always offloaded. On Windows an overlapped read completes through the I/O completion port and a thread-pool callback even when the OS cache holds the page; for path-opened readers that cost 14.8-19.1 µs per warm 4 KB read, against 3.8-4.9 µs on a synchronous handle (read-performance-bottlenecks.md §7). Moving the writer to `FileOptions.None`, and possibly to inline reads, needs insert, update and delete A/B measurements with no transaction, with `UseTransactionalWrites` and in an explicit transaction. Not planned yet.
- **Table scans of tables with Attachment or multi-value columns never read ahead, and that exclusion was never measured.** `TableReader.ShouldReadAheadTablePages` refuses read-ahead when `HasLongValueOrComplexColumns` is true (Memo, OLE, Complex and Attachment columns). For MEMO and OLE the exclusion is measured: in `AccessReaderReadAheadEligibilityBenchmarks`, read-ahead moved warm `Auto` scans of a 5,000-row MEMO table and a 2,000-row OLE table by less than the run-to-run noise at cache sizes 0, 2 and 256, because each row's long-value reads dwarf the one data page the prefetch overlaps, while it took the 25,000-row numeric table from 9.9-10.5 ms to 8.6-8.9 ms. A complex column's cell in the main table is a 4-byte reference, so its cost per row depends on the flat-table reading a scan does. Add an Attachment or multi-value table, with and without items, to that benchmark, and drop ComplexType and AttachmentType from the exclusion if read-ahead gains on them. Not planned yet.
- **Why `FileOptions.SequentialScan` on a synchronous handle defeats the OS read-ahead is not understood.** In the page-I/O investigation, 9,800 sequential 4 KB page reads of a copy the OS had not cached took 47 ms with `FileOptions.None` and 654 ms with `SequentialScan` on a synchronous handle (584 ms with `RandomAccess`, 965-1,040 ms on overlapped handles). Repro: make an uncached copy as `AccessReaderColdScanBenchmarks` does (Windows only: `FILE_FLAG_NO_BUFFERING` and write-through), then time the same sequential reads through a `FileStream` opened with each option. read-performance-bottlenecks.md records it as not understood. Not planned yet.
- **AddColumn, DropColumn and RenameColumn copy every row into a new table.** `TableSchemaEditor.RewriteTableAsync` reads every row into a `DataTable` snapshot, writes them into a new `~tmp_<guid>` table and transplants it over the original (`TransplantTempTableToOriginalAsync`), so even a rename costs time and space in proportion to the table. Jackcess's `TableUpdater` adds a column by editing the TDEF in place. Not planned yet: deferred from wave 2, as a separate design that changes the bytes a schema edit leaves.
- **`MinAsync` and `MaxAsync` read every row even when an index orders the column.** They aggregate all the rows the query returns (today through `ToListAsync`; linq-b streams them), although the first or last entry of an index on the column would answer them; `IndexCursor.TryReadLastEntryAsync`, which `AutoNumberMaintainer` uses, already reads a last entry. Not planned yet: deferred from wave 2.
- **Creating an encrypted database writes it in plaintext first and then re-encrypts the whole file.** `CreateDatabaseAsync` takes no encryption settings, so an encrypted file is created unencrypted and then passed to `EncryptAsync`, which writes the whole file again to `<db>.reenc-<guid>.tmp` and renames it over the original. A `CreateDatabaseAsync` overload that writes the encryption descriptor up front is cheap once wave 2's encryption-flat-agile adds the flat Agile page codec. Not planned yet: deferred from wave 2.

## Design flaws

Each of these needs structural work rather than a local fix; the bugs above are many of their symptoms.

- **The facade is the engine.** `DatabaseFile`, about 1,940 lines and taken by about 40 types, is a catch-all: page I/O and `IoGate`, the transaction-journal hook, page decryption, TDEF parsing, the row directory and overflow-row resolution, and the owned-page index. It needs splitting into separate components. Planned in wave 2: core-split-a (implemented on `fix/core-split-a`, not yet merged) and core-split-b.
- **No pager or buffer manager.** Only the reader caches pages (`ReaderPageCache`). Every page the writer reads goes through `DatabaseFile.ReadPageAsync` to the stream or the transaction journal, the writer's snapshot reads use a capacity-0 cache, and no page buffer a caller holds is leased or pinned. `DatabaseFile.PageCount` is the one journal-aware end of file, which every page-number bound and every caller that numbers new pages uses. Index usage maps cannot be written in REFERENCE form, and table owned-pages maps are never promoted (both above). Planned in wave 2: pager-a adds the writer's frame cache, pager-b the usage maps and the owned-page index, and pager-c page leases.
- **Transactions are not atomic.** A `JetTransaction` buffers each dirty page's after-image in a `PageJournal`, and `TransactionLifecycle.CommitTransactionAsync` writes them over the file in place, in ascending page order, then flushes. There is no write-ahead log, before-image or rollback journal, and no recovery on open, so a process, stream or device failure after the first page write leaves part of the transaction in the file. `IsCommitted` and `IsRolledBack` are then both false and `RollbackAsync` throws; the writer drops its catalog and insert-hint caches but keeps its constraint registry, so AutoNumber counters never move back over IDs that may be on disk. Cancellation is honoured only before the first page write. There are no savepoints: an operation that fails inside an explicit transaction (one over `AccessWriterOptions.MaxTransactionPageBudget`, an update that hits a read error or a damaged page after deleting a row, a cascade that a child table's index rebuild refuses after its rows are written) leaves its partial writes in the journal, committing writes them, and the caller must roll back the whole transaction; an implicit `UseTransactionalWrites` transaction is rolled back automatically. Calls without a transaction are not statement-atomic (the data-loss and partial-write items above). The README's "Transaction durability" limitation describes this. Planned in wave 2: savepoints, commit undo, and a sidecar rollback journal, on by default for path-opened files, with recovery when the file is opened (atomicity-a, atomicity-b and crash-journal).
- **The schema is not a model.** Each schema operation re-parses the TDEF and `LvProp`, rebuilds `ColumnDefinition`s and `IndexDefinition`s, and writes a new table. Column, index, foreign-key and property projection are separate helpers (`ColumnDefinition.WithName`, `IndexHelpers.ProjectIndexes`, `PersistedPropertyProjector`, and `RelationshipManager`'s capture and relink) rather than edits to one in-process model. Planned in wave 2: schema-model-core and schema-model-c.
- **No write pipeline or real B-tree.** Insert, update, delete, cascades, complex-item adds and schema rewrites each wire the insert, tombstone and index-maintenance primitives by hand, and an update is a delete plus a re-insert. The B-tree has no real insert, delete or merge: index maintenance splices a single leaf, rebuilds a multi-level tree from its leaves, or rebuilds every index from a snapshot; tables with an FK index always take the full rebuild, and emptied pages are not freed. Planned in wave 2: write-pipeline-a1 (the cascade plan), write-pipeline-a2 (one write path), write-pipeline-b (a real B-tree) and write-pipeline-c (in-place updates).
- **Constraints live in the process, not the file.** Each writer session builds its own constraint registry from the file and its own declarations; a CLR `ValidationRule` delegate cannot be stored, so it binds only the declaring writer (documented, with `ValidationRuleExpression` as the stored alternative). What the writer does not enforce is under "Values that differ" ("The writer does not enforce every constraint stored in the file"). Planned in wave 2: constraints-a and constraints-b.
- **Lossy value model.** Unreadable MEMO and OLE values read as placeholder text or empty arrays, and an unreadable `LvProp` blob as no properties (items above). Planned in wave 2: failure-model-b1.
- **Format knowledge is scattered.** There are 67 `DatabaseFormat.Jet3Mdb` checks in 27 library files, 41 files import `JetTypeInfo` with `using static`, and the only per-format profiles are `TDefHeaderLayout`, `LvalPageLayout` and `IndexLayout`. Jet3 `LvProp` text hard-codes Windows-1252 (above). Planned in wave 2: core-split-b #3 (capability flags on `JetFormat` and a source scan that limits `DatabaseFormat` comparisons) and format-profile-b.
- **The read API does not compose.** `TableReader`'s read loops agree on results but share no scan primitive. `IndexRowReader` returns nothing for linked tables (`ListIndexesAsync`, `EnumerateIndexRowsAsync`). `CatalogReader.ResolveTableAsync` re-reads the TDEF uncached and, for a system table, rescans `MSysObjects` (above). An unknown table reads as empty in the reader, while the writer throws. Planned in wave 2: read-composition-a and read-composition-b.
- **Encryption is not a page layer.** Flat Agile and the CFB Office Crypto formats (Agile CFB, Standard, and the AES-CFB wrapper) are decrypted whole into memory on open rather than page by page, and the writer has no page cipher for flat Agile (above). Planned in wave 2: pager-a moves page encryption into per-scheme codecs, encryption-flat-agile makes flat Agile a page layer, and encryption-containers makes the CFB containers durable and atomic. The CFB containers stay decrypted whole into memory: a segment-addressable reader for them is deferred, not planned in wave 2.
- **Failures are not modeled.** `JetLimitationException` is the only custom exception type, so callers tell a refusal, an unenforceable constraint, a corrupt page, an unreadable long value and a torn commit apart only by exception type and message text, and `LastDiagnostics` is typed only internally. Planned in wave 2: failure-model-a, failure-model-b1 and failure-model-b2.
- **The LINQ layer has no query plan.** `EntityMap` is the one property-to-column mapping and `ValueCoercer` the one value conversion, but:
  - read materializers are compiled on every call, not cached per table definition or row shape: `RowMapper<T>.Build` runs in `TableReader.EnumerateMappedRowsAsync`, `IndexRowReader.ReadIndexRowsAsync` and `LinkedTableReader`, and `DirectRowDecoderBuilder.TryBuild` compiles again; only the insert delegate is cached (`RowMapper.WriteCache`);
  - the `IQueryable` surface runs sync-over-async (`AccessQueryProvider` blocks on `Task.Run(...).GetAwaiter().GetResult()`);
  - index walks do not stream: `IndexCursor.FindRowLocationsForCriteriaAsync` builds a `List` of every matching row location before the first row is materialized;
  - `MinAsync`, `MaxAsync`, `SumAsync` and `AverageAsync` take `Func` selectors and aggregate the result of `ToListAsync` in memory, so memory grows with the row count;
  - nothing is annotated for AOT or trimming: there is no `DynamicallyAccessedMembers`, `RequiresUnreferencedCode`, `RequiresDynamicCode` or `IsAotCompatible` in the repository.

  Planned in wave 2: linq-b (async-only `Query<T>`, streaming aggregates), linq-c (cached materializers, streaming index walks), linq-plan-cache and linq-aot.

## Unchecked against Access

Microsoft Access is not installed on any machine the suite has run on, so none of the skip-guarded DAO tests has run. Wave 2 asks for one full DAO run on a host with Microsoft Access before 4.0.0 ships; who provides the host is the one wave-2 decision left to the user. Each item below waits on that run unless it says otherwise, and the Jet3 items need a DAO engine that opens Access 97 files, which the hosts used so far lack.

- **The library's Jet4 RC4 and ACCDB legacy-password schemes may not be what Access writes.** No fixture is a file Access encrypted, so the library's encrypted formats are checked only against themselves. Jet4 RC4 (`AccessEncryptionFormat.Jet4Rc4`) uses flag 0x02 or 0x03 in raw header byte 0x62 plus a header password, and per-page RC4 keyed with `MD5(dbKey ‖ pageNumber)`; mdbtools and Jackcess describe Jet RC4 differently (the encoding key at 0x3E from the unmasked header, XORed with the page number, and no flag at 0x62). The ACCDB legacy password (`AccdbLegacyPassword`) uses flag 0x07 plus a header password, and `AccdbLegacyPasswordMask` is AesEncrypted.accdb's empty-password pattern XOR "secret", but that fixture holds no password: it is a DAO `CompactDatabase` output and a compacted copy of NorthwindTraders.accdb. ACCDB AES-128 in a CFB wrapper is the library's own layout too. Whether Access opens the library's files, or the library opens Access's, is unchecked. The README's Encryption Support section, its feature table and the `AccessEncryptionFormat` docs say so. It needs Access-authored encrypted fixtures or a DAO run.
- **Attachments the writer stores.** `AttachmentWrapper.Encode` writes the `FileData` wrapper all 24 Access-authored attachments in the fixtures use: typeFlag 0 for raw or 1 for zlib, `dataLen` as the uncompressed content length, and an extension length that counts characters including the NUL. A compressed body is a hand-framed zlib stream (`78 5E`, deflate from `DeflateStream` at Optimal, a big-endian Adler-32 from `Infrastructure/Adler32`). Jackcess 4.0.12's list (jpg, jpeg, gif, png, zip, cab, docx, xlsx, xlsb, pptx) is stored raw and everything else deflated; the fixtures confirm only .jpg (raw) and .txt (compressed). Unchecked: whether Access opens the writer's attachments, and what Access writes for an empty extension (Jackcess writes only the NUL: extChars 1, headerLen 14). The DAO tests that add writer attachments (`DaoStorageMaintenanceTests.ComplexFixture_WriterAttachmentRowsSurviveCompactAndRepair`, and the `DaoValidationFixture` attachment that `DaoCompact_ComplexColumnsWithLvalPayload_SurviveCompactAndRepair` uses) name only .jpg files, which the writer stores raw, so even a DAO run would not exercise the zlib form. Add a .txt attachment to one of them.
- **Expression semantics.** Calculated columns, defaults and validation rules follow rules measured with oleaut32 on Windows or VBScript under LCID 1033, not with Access: `AccessVariantOperators`' date arithmetic (`VarAdd`, `VarSub`, `VarIdiv`, `VarMod`); `And`, `Or`, `Not`, `Xor`, `Eqv` and `Imp` bitwise on numbers and three-valued with Null (`12 And 10` is 8 and `Null Or True` is True, so a calculated Boolean or numeric column can store Null), where Jackcess keeps them logical; `VariantChangeType` conversions, so a Boolean in a Byte calculated column and `CByte(True)` give 255 (`CByte(-1)` and `CByte(256)` throw `OverflowException`); and time-only values on day 0 (1899-12-30) and `TimeSerial` rounding. The `AccessVariantOperators` docs and calculated-columns-format-notes.md say Access was not checked. To check the Byte case: in Access or DAO, create an ACCDB table with a Yes/No field and calculated Byte columns `=[Flag]` and `=CByte(True)`, insert True, and compare the values Access caches with 255.
- **`%` in a calculated expression.** `CreateTableAsync` and `AddColumnAsync` refuse `%` outside strings and `[field]` names (`TableSchemaEditor.ValidateDeclaredCalculatedExpression`), with an `ArgumentException` naming the column and expression, and a table rewrite does not re-check carried-over columns. On a table that already stores such an expression, rows read and schema edits work, but an insert that leaves the column Null and every `UpdateRowsAsync` throw that `ArgumentException` (`CalculatedColumnWriteTests.StoredPercentExpression_ReadsButRejectsWritesThatReevaluateIt`); a stored expression that calls an unsupported function throws `NotSupportedException` the same way. No Access-authored fixture expression contains `%`. Whether Access accepts it is unknown: in VBA a trailing `%` on a number literal is the Integer type suffix, so `5%` would be 5 (not checked against Access). If it does, the writer refuses expressions Access stores.
- **Relationships and foreign-key entries.**
  - On Jet3, `RelationshipManager` emits FK entries in the shape Access 97 wrote in indexTestV1997.mdb, the only Jet3 evidence: a new FK real index has flags 0x00, `used_pages` 0 and a zero statistics slot; entries and ANSI names stay in case-insensitive name order, also after a rename; the parent shares a covering real index that is unique or backs the primary key; and both sides carry the cascade bytes. Unchecked: whether Jet 3.5 accepts or enforces these entries without a Compact & Repair, whether `used_pages` 0 is acceptable (on Jet4, DAO needed a non-zero pointer), whether the name order is required, and whether continuation TDEF pages need `VC` at bytes 2..3. index-and-relationship-format-notes.md §7.19 lists the same points.
  - On Jet4 and ACCDB the parent-side FK entry follows the `fk-dao-baseline` FormatProbe output: the FK logical entry is prepended, the parent shares the first covering real index, the parent-side cascade bytes stay 0, and a new real index carries the 0x80 flag. Access-authored files (indexTestV2000.mdb, NorthwindTraders.accdb) keep entries and names in case-insensitive name order, set the cascade bytes on the parent-side entry too, and share a unique covering real index. Aligning the writer needs the DAO FK compact round trip (`AccessRoundTripTests`); index-and-relationship-format-notes.md §9 lists it.
  - `RenameRelationshipAsync` renames the parent-side FK entry to the new relationship name, though `CreateRelationshipAsync` gives it a hidden `.rB`-style name (`MakeUniqueParentRelationshipLogicalName`, as DAO and Access do: `.rC` in indexTestV1997.mdb, `.rI` in nwind.mdb's Orders), and its comment wrongly says it follows the create convention. Repro: create relationship 'Rel', rename it to 'Zed', and `ListIndexesAsync(parent)` shows an FK index named 'Zed'. `Jet3ForeignKeyIndexTests.RenameRelationship_Jet3_RenamesBothEntriesAndKeepsNameOrder` pins this. Likely fix: keep the parent entry's hidden name and rename only the child side.
  - `DropTableAsync` refuses, before anything is written, a table that any `MSysRelationships` row names as its primary or foreign table, relationships without referential integrity and self-relationships included (`RelationshipManager.FindRelationshipNamesForTableAsync`, `EnsureTableHasNoRelationships`). This rests on DAO `TableDefs.Delete` and `DROP TABLE` failing with error 3303, "currently participates in one or more relationships". `DaoRelationshipDropTests` checks it in three skip-guarded tests: Northwind's Companies, both tables of a non-enforced relationship, and a self-referencing table.
  - Through a self-relationship, a row whose key an update moves is also a dependent row of its old key when its foreign key, after the update's own assignments, still names that key, and `RelationshipEnforcer.PlanCascadeUpdatesAsync` writes the new key into that row's one rewrite: in Tree (`Id` primary key, `ParentId`) with FK_Tree_Self (Tree.Id <- Tree.ParentId) cascading updates, row [1, 1] updated to `Id` 5 becomes [5, 5]. When the update also assigns the foreign key, the assigned value stays unless it is the old key: { Id = 5, ParentId = 3 } gives [5, 3], and { Id = 5, ParentId = 1 } gives [5, 5] (`ForeignKeyCascadeUpdateTests`). Without cascading updates the same rule decides whether the row counts as a dependent row, so { Id = 5, ParentId = 3 } on row [1, 1] is not refused on that row's account. { Id = 5, ParentId = 5 } is refused before the plan, because `EnforceFkOnForeignUpdateAsync` looks for parent 5 in the table as it was before the update ("UPDATE of 'Tree' violates foreign-key constraint 'FK_Tree_Self': no matching row in 'Tree' for the new ParentId value(s)."). What Access does in each case is unchecked.
- **Jet3 table definitions.**

Not planned yet.

Repro: compare raw page 0 of a new Jet3 database with Jet3Test.mdb or testV1997.mdb at those offsets; 0x600 is 01 in both, and 0x602 is 0B in Jet3Test.mdb and 14 in testV1997.mdb.
- **Rows and long values.**
  - The writer ends a row's fixed area after the last non-null fixed column, where Access reserves every fixed column's slot (data-page-row-format-notes.md, "Inside a row"), so a writer row cannot be compared byte for byte with an Access row.   - Jet3 rows: no fixture row has a real (non-dummy) jump-table entry, so the entries `Jet3JumpTable.Write` produces are checked only against the reader rule of mdbtools `mdb_crack_row3` and Jackcess `TableImpl.readJumpTableVarColOffsets`. If Access rejects them, the writer's limit, the `JetLimitationException` message and the README's "Table and row size" item change.

- **Schema edits.**

## Decisions left to the user

- **Who provides a host with Microsoft Access for the DAO run** (under "Before 4.0.0 ships"). It is the one wave-2 decision left to the user.
- **Whether a plain `typeof(decimal)` column on a Jet3 `.mdb` becomes Currency instead of throwing `NotSupportedException`.** `ColumnDefinition.NumericPrecision` defaults to 18 and `NumericScale` to 0, so an undeclared decimal column is Decimal(18,0). On Jet3, `JetTypeInfo.ResolveStorageType` creates a decimal column as Currency and refuses a declaration Currency cannot hold, a scale above 4 or more than `CurrencyIntegerDigits` (14) integer digits, so the default is refused with a message that suggests a declaration that fits, `IsCurrency`, or a double; the same declaration works on Jet4 and ACCDB. Creating Currency anyway needs `NumericPrecision` to tell an undeclared precision from a declared 18, so it would have to become nullable or gain a flag.
- **Whether the scaffolder qualifies its type names with `global::`.** `EntityEmitter.Emit` puts its using directives above a file-scoped namespace and names `DateTime`, `DateTimeOffset`, `TimeSpan`, `DateOnly`, `TimeOnly`, `Guid`, `Hyperlink`, `[Column]` and `[Table]` by their simple names, and C# looks a simple name up in the generated namespace and each enclosing one before those usings. `ScaffoldNames.FindTypeHidingSegment` refuses a `--namespace` segment with one of those names, but the tool cannot see the user's project: with a `MyApp.Hyperlink` class, scaffolding into `MyApp.Data` binds every Hyperlink property to it, and a `MyApp.ColumnAttribute` class or a `MyApp.Guid` namespace gives CS0616 or CS0118. The README's scaffolding section documents this. `global::`-qualified property and attribute types, or `using global::...;` directives inside the namespace, would remove it, but either reverses the decision to keep the usings above the namespace, which stops a segment such as `System` from capturing them.
- **Whether `InsertRowAsync<T>` ignores or rejects a complex cell** read back through `Rows<T>` (the complex-columns item under "Values that differ").

## Before 4.0.0 ships

- **Run the full DAO suite, wave 2's skip-guarded tests included, on a host with Microsoft Access, and record the result.** It settles "Unchecked against Access", decides whether `CreateDatabaseAsync` must write the standard system rows, and wave 2 waits on it before letting tables in a relationship leave the full index rebuild they take on every write.
- **Re-run the reader benchmarks on x64, a hard disk, an SMB share, Linux and macOS.** `AccessReader.CreateStream` opens every path-opened reader with `FileOptions.None` in every `PageReadOptimizationMode`, and `DatabaseFile.ReadsInlineOnThreadPool` makes page reads on pool threads, with no `SynchronizationContext` and the default `TaskScheduler`, complete on the calling thread. Both choices rest on one Windows Arm64 machine with local NVMe storage (read-performance-bottlenecks.md §7, "Page I/O handle" and "Inline reads on thread-pool threads"), and their trade-offs matter most on slow storage: each read holds a pool thread; Windows serializes I/O on a synchronous file object, so read-ahead and concurrent scans on one reader queue their reads in the kernel; an inline read cannot be cancelled once started, so a hung SMB read holds its thread until the OS gives up; and on pool threads read-ahead's prefetch completes inline instead of overlapping decoding. On Linux and macOS .NET is believed to map the old hints to `posix_fadvise` (not verified). Go back to `SequentialScan` only if those runs contradict the Arm64 numbers. #### Decisions already made

- Writes: `UseTransactionalWrites` (default false) means durable per call; no statement-journal option; public `PageCacheSize` (default 256); `MaxTransactionPageBudget` limits only explicit transactions.
- Journal: `<db file>-journal`; `UseRollbackJournal` (default true) on path and `FileStream` files that are not containers; one that cannot be created fails the write; a reader of a hot journal gets a pre-crash overlay, or {HotJournalConflict} with nothing changed; a second writer gets {DatabaseInUse} at once; `CreateDatabaseAsync` deletes a stale journal only after `CreateNew`.
- Schema: the reader caches TDEFs for its lifetime, unbounded; VerifyOnHit runs in CI; rewrites keep un-modelled bytes.
- Pipeline: free emptied index pages on user tables only; update in place, keeping unchanged long values; carry unreadable, unassigned MEMO and OLE values raw; a unique non-PK index takes several all-Null keys, which IgnoreNulls omits; cascade updates recurse, and every cascaded row is validated before writing.
- Constraints: an unevaluable default or rule refuses the write {UnsupportedExpression}, with no opt-out; `CurrentUser()` is "Admin"; Guid AutoNumbers get flags 0x43 and `GenGUID()`; malformed declarations throw `ArgumentException`; table rules check the whole post-update row, get a public API and block dropping a column they name.
- Collation: sort order 0 and new files are General Legacy; new tables take the header's order; new Jet3 columns get 0x0409, code page 1252, the col_num copy and General 97 keys; a General key over 510 bytes without suffix tables throws; expressions compare by the sort order; no public sort-order property. format-profile-b decides whether `LvProp` text outside the code page is refused, as names and Text or Memo values are, or stored as '?'; refusing follows the safety rule.
- Values: decode faults follow `StrictParsing` (strict throws `JetCorruptDataException`; lenient gives DBNull or "", never placeholder text); complex items are removed and replaced by ItemId.
- Reads: unknown tables throw {TableNotFound}; `TryGetTableAsync` returns `ValueTask<AccessTableInfo?>`; linked text tables have no indexes; ODBC row reads throw.
- Encryption: Agile rewraps reuse the intermediate key with a fresh salt and HMAC key; path containers rewrap after each changing call, stream containers at commit; a refused rename leaves the original untouched; the statics move to `AccessDatabaseFile`.
- Failures: each site keeps its BCL base and adds `IJetException`; `OnDiagnostic` and an EventSource replace `DiagnosticsEnabled` and `LastDiagnostics`; codes, not messages, are the contract.
- LINQ: async-only `Query<T>`; unsupported operators throw, pointing to `AsAsyncEnumerable()`; aggregates take expressions only; a static materializer cache of 64 shapes per T.
- Repair: only an explicit `RepairAsync` with a dry run; it fixes stray bytes b=1..4, chain headers and the Jet3 header, and refuses a table whose index settings are lost {RepairRefused}.

#### Risks

1. Base drift across 17 mostly serial stages: rebase at the start and find code by symbol.
2. A write that bypasses the pager's scope (the CFB rewrap, Shrink's truncate, direct stream writes) breaks atomicity; keep the fault and crash sweeps green.
3. Stale caches corrupt indexes: one invalidation contract, VerifyOnHit, no reader caches over a writable `PageFile`.
4. Format changes only a DAO run can confirm need Access-fixture or Jackcess evidence and a skip-guarded DAO test.
5. `Assert.Throws<T>` is exact-type: migrate assertions in the commit that changes the type.
6. Two fsyncs per default call on a file (about +2.8 ms on NVMe) and an O(file) container rewrap per call: keep to the benchmark gates, and keep tests off fsyncing temp files where durability is not under test.
7. Access ignores `<db>-journal`, and Unix cannot fsync the journal's directory entry; document both.
8. Wave-1 behaviour must survive: overflow rows, Jet3 LVAL headers and jump tables, explicit-Null inserts, the FK update scope, the DropTable refusal, expression rename rewrites, AutoNumber seeding.
