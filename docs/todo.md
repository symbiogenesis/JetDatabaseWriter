## What the five commits fixed
- **The service-locator problem is gone.** Nothing outside the facades takes `AccessWriter`, `AccessReader` or `AccessBase` any more. `WriterServices` and `ReaderServices` now wire everything explicitly, the two dependency cycles are removed, and `ServiceGraphTests` guards this.
- **Duplicate code was merged:**
  - one `TableCatalog` replaces the two `GetUserTablesAsync` copies;
  - the shared index-descriptor helpers live on `IndexCatalogReader`;
  - the row primitives exist only in `TableRowStore`;
  - `AccessWriter` no longer has its own snapshot copies.
- **The row decoders no longer depend on the reader facade.** `RowDecoder` and `LongValueDecoder` now take `DatabaseFile`, and `ReaderPageCache` reads straight through to pending transaction writes when one is active. That makes the main fix below cheap.
- **The concurrency doc now gives the correct `UseTransactionalWrites` default.**
- **No new defects, apart from one small one, now fixed.** A before/after comparison over all 92 test databases found identical results. The only change was that the "Total rows scanned" diagnostic also counted catalog rows it couldn't decode (25 became 28 on one fixture).   - Result type. Access encodes a calculated column's cached value by its `ResultType` property, and Access-authored columns can carry a different descriptor type. In calcFieldTestV2010's Table1:
    - AllNames is a Text descriptor with a Memo result;
    - MonthlySalary and WeeklySalary are Double descriptors with Currency and Decimal results;

The writer's `TableCatalog` resolved table definitions without `ResultType`. So one insert or update wrote a Double where Access expects a Currency, a 2-byte 1 where it expects 0xFF, and an inline Text wrapper where it expects an LVAL header. A strict reader then threw on the whole table. The fix:
    - A new `ColumnPropertyReader`, extracted from `CatalogReader`, reads the property in both service graphs.
    - `TableCatalog` sets each column's result type, cached per TDEF page until `Invalidate()`.

    - a date minus a date is a Double of days.

- **Defaults: an explicit NULL stored the default, a default could differ between writers or lose precision, and generated columns accepted one.**
  - The explicit-NULL bug.
    - The insert front ends erased the difference between a column left out and an explicit null before the constraints ran. `TableDataWriter.ResolveNamedRow` filled the columns a `RowValues` row did not name with DBNull and turned a named null into DBNull, `NormalizePublicRow` turned positional nulls into DBNull, and `RowMapper.BuildToRow` gave a null property and an unmapped column both DBNull. `ConstraintRegistry.ApplyAsync` then filled the CLR or persisted default into every null.
    - Older Access versions gave every Number column a `DefaultValue` of "0". So once persisted defaults were applied (constraints entry), an explicit null into nwind.mdb's `Products.UnitsInStock`, or into Jackcess's test.mdb and test.accdb Table1, stored 0.
    - A NOT NULL column with a default accepted an explicit null and stored the default, where Access rejects it (error 3314).
  - The explicit-NULL fix. Inserts now follow Access SQL.
    - Every value an insert supplies is stored as given: null and `DBNull.Value` store NULL even in a column with a default, and a NOT NULL column rejects them. A column the insert leaves out gets its default.
    - The new public `DbDefault.Value` (`JetDatabaseWriter.Models`, which prints as "DEFAULT") asks for the default in any insert shape. `ResolveNamedRow` fills the columns a row does not name with it, and `RowMapper.BuildToRow` gives it to a column no readable property maps to. A mapped property whose value is null still stores NULL.
    - `ApplyAsync` replaces each `DbDefault.Value` with DBNull first, before the column-count bail-out, so it never reaches the row encoder, and applies a default only to those columns.
    - AutoNumber, complex-reference and calculated columns still generate or compute their values for null, `DBNull.Value` and `DbDefault.Value`.
    - An update never applies a default, so both `UpdateRowsAsync` overloads reject `DbDefault.Value` with `ArgumentException` before reading any row.
    - The NOT NULL error says "cannot be set to null" for an explicit null and "no value was supplied" for a column left out.
  - Generated columns. Access gives AutoNumber, calculated, Attachment and multi-value columns no default.
    - `CreateTableAsync` and `AddColumnAsync` accepted a `DefaultValue` or `DefaultValueExpression` on them anyway, persisted it and registered it. `ApplyAsync` substitutes a default before it generates an AutoNumber, so the declaring writer stored Id 0, 0, ..., where a reopened writer, whose `HydrateFromTableDef` drops such defaults, generated 1, 2, ....
    - A schema rewrite copies a `DefaultValue` property it finds in LvProp into the rebuilt column and re-registers the table. So a stray property another tool stored on an AutoNumber column started applying after AddColumn, DropColumn or RenameColumn.
    - The new `TableSchemaEditor.ValidateDeclaredDefault` rejects such a default with `ArgumentException` (`ParamName` "columns" or "column") before anything is written, through the new internal `ColumnDefinition.CanHaveDefault` and `DeclaresDefault`. `ConstraintRegistry.ToConstraint` drops it as `HydrateFromTableDef` does, so a stray property stays in the file and is never applied.
    - A `DefaultValue` of `DBNull.Value` counted as a supplied default, so an insert that left a NOT NULL column out stored NULL. It now means no default.
  - Floating-point defaults. `ColumnDefaultValue.Compile` parsed every numeric literal as a `decimal` before it knew the column type, then converted it with `Convert.ToDouble` or `Convert.ToSingle`.
    - A decimal keeps at most 28 fractional digits, so a Double or Single default below about 1e-28 read back as 0.
    - That conversion is not correctly rounded, so about one double in ten and one float in six came back an ulp or more off: 1.2345678901234567E-20 became 1.2345678900000001E-20.
    - A Single default too large for a float went through the expression engine and stored infinity.
    - A numeric literal is now parsed once into a double, a float and a decimal, each null when out of range. Double and Single columns take their own parse, which is exact, and other columns keep the decimal as before. NaN and Infinity are not numeric literals.
  - The bug of two defaults. A CLR `DefaultValue` with no `DefaultValueExpression` is persisted as a literal, and a reopened writer applies that literal, but the declaring writer applied the CLR object. So the two differed whenever the literal did not round-trip:
    - 1e-30 stored 1e-30 and then 0, 0.1f on a Double column stored 0.10000000149011612 and then 0.1, and a `DateTime` kept its milliseconds only in the declaring writer;
    - 0.0000000000000000000123456789m on a Double column stored 1.2345678900000001E-20 and then 1.23456789E-20, and 1.00000005960464477539062501m on a Single column stored 1 and then 1.0000001;
    - 1e39 on a Single column stored infinity and then NULL. By reading the code, 300 on a Byte column, 1e300 on a decimal column and 5 on a GUID column made the row encoder throw on every insert that left the column out in the declaring writer, and stored NULL in a later one;
    - a NaN or infinite default was persisted as "NaN" or "Infinity", which no writer can evaluate.
  - The fix: one default in every writer.
    - The new `ColumnDefaultValue.TryReadBackNumber` reads a default of any CLR numeric type back from its persisted literal as the column's type, through the same literal parse a reopened writer compiles. `ConstraintRegistry.ToAppliedClrDefault` applies that value for every number on every column type, and no default when the literal gives none. A `DateTime` is cut to the whole second, the resolution of an Access date literal.

    - A CLR `ValidationRule` delegate now sees a numeric default as the column's type: 5 on a Double column arrives as 5.0.

  - The handle getter.
    - `DatabaseFile.ReadPageRandomAccessAsync` passed `FileStream.SafeFileHandle` to `RandomAccess.ReadAsync` on every page read. On .NET 6+ that getter is not a field read: it flushes the stream's buffer and seeks the OS file pointer to the stream's position (`SetFilePointerEx`) before it returns the handle, 1.7-2.0 µs per call on the Arm64 machine.

A later replay of the OLE scan's page reads, while other builds ran, could not separate the builds (15-19 µs per read either way); the larger cost, in both modes, was the handle's type.

    - `AccessReader.OpenAsync(path)` opened its file with `FileOptions.Asynchronous`, plus the `RandomAccess` hint in `Auto` and `Enabled` or the `SequentialScan` hint in `Disabled`.   - The offloaded read.
    - On a synchronous handle, `RandomAccess.ReadAsync` and `FileStream.ReadAsync` hand every read to another pool thread and the caller waits for it, even when the caller is itself a pool thread. Most reads start on one: the library awaits with `ConfigureAwait(false)`, and console, ASP.NET Core and worker callers have no synchronization context. The hop cost more than the read: a replayed page read took 6.1-9.8 µs offloaded and 2.6-4.5 µs on the calling thread.
    - `DatabaseFile.ReadsInlineOnThreadPool`, which only `AccessReader.OpenAsync(path)` sets, in every mode, makes `ReadPageAsync` read synchronously when `CanReadInline` sees a pool thread, no `SynchronizationContext` and the default `TaskScheduler`. It reads through `ReadPageRandomAccess`, a `RandomAccess.Read` loop, on the `RandomAccess` path, or `ReadPageFromStream`, a `Stream.Read` loop under `IoGate`, on the seek-and-read path.

    - In an A/B of Release builds, by the same method, a warm `Rows()` of the OLE table went from 40-43 ms to 20-30 ms, of the MEMO table from 76-90 ms to 43-58 ms, and of the numeric table from 12.9-21.8 ms to 9.1-18.4 ms, faster in every run although read-ahead's prefetch now completes inline. Opening an uncached copy and scanning its OLE table took 0.17-0.53 s, against 0.18-1.1 s.
    - The trade-offs. An inline read cannot be cancelled once it has started: the token is checked before every page read, so a cancelled scan stops at its next page, but a read that hangs on a network share holds its pool thread until the OS gives up. On pool threads, read-ahead's prefetch completes before the current page is yielded, so it no longer overlaps decoding.

## Open: found while fixing
These were found while the follow-ups were investigated or fixed, and are listed worst first. Where an entry of "Fixed since 6eab703" already records a bug with its repro, the line here sums it up and names the entry; the rest are recorded here in full. Each says which wave-2 package plans its fix (see "Suggested next steps"), that none does yet, or what evidence it waits on.

### Data loss and broken referential integrity
- **An update whose re-insert fails loses the row.** An update deletes the row and then inserts its new version, and if the insert throws, the delete stays. One way to hit it is an update that grows a row past one data page, which now throws `JetLimitationException`; the README says to use `UseTransactionalWrites` or a transaction for such updates. Another is an update that sets a Currency column, which every Jet3 decimal column is, to a value outside Currency's range; see the decimal entry. Planned in wave 2: atomicity-b makes every call statement-atomic, and write-pipeline-c updates rows in place instead of deleting and re-inserting them.
- **A key update that a later relationship refuses keeps the cascades of the relationships before it.** When a parent key update cascades through one relationship and a later one refuses it, because that one does not cascade updates or its child holds an unreadable MEMO, the first child keeps the new key under the parent's old key unless `UseTransactionalWrites` or a transaction rolls it back. Deletes no longer have this gap. See the follow-up under the OLE entry. Planned in wave 2: atomicity-b, and write-pipeline-a1's cascade plan.
- **Without a transaction, `UpdateRowsAsync` and `DeleteRowsAsync` on a wide table written by an earlier build change the rows and then throw**, leaving the indexes stale, when one of its indexes carries the phantom key column. See the follow-up under the wide-table entry. Planned in wave 2: index-preflight checks that every index can be maintained before a write changes anything.
- **Cascade updates stop at the first level**, so a grandchild keeps the old key as an orphan. See the foreign-key entry. Planned in wave 2: write-pipeline-a1's cascade plan recurses through updates as deletes already do.
- **A delete whose own rows a cascading self-relationship also reaches counts those rows twice.** The TDEF row count and the index row counters end up too low, and the complex-column cascade runs twice for the row. See the foreign-key entry, which gives the cause and the fix. Not planned yet; write-pipeline-a1's cascade plan, which folds self-referencing overlaps, is where it belongs, and its tests should include the repro.
- **Setting a referenced column that is not the primary key to Null orphans its dependent rows**, where Access refuses with error 3200 when updates do not cascade (from memory, not checked). See the foreign-key entry. Not planned yet.
- **`CreateRelationshipAsync` does not check the existing rows**, so an enforced relationship can be created over orphaned keys. See the foreign-key entry. Not planned yet.
- **A POCO whose AutoNumber property is a non-nullable `int` inserts 0, so its second insert duplicates the key.** See the defaults entry. Not planned yet.

- **The reader's system-table lookups rescan and decode all of `MSysObjects` on every call**, 10 to 17 times the bytes they read before 06ccfb3. See the overflow-row entry. Planned in wave 2: read-composition-a caches the reader's table resolution and complex-column descriptors, so repeated metadata calls read nothing after warm-up.
- **An update, and a session's first insert into a table whose TDEF is at page 1024 or below, can read every data page of the table, or of the file.** See the redundant-reads entry. Planned in wave 2: pager-b's owned-page index.
- **`Rows<T>(predicate)` compiles its predicate and lists the indexes on every call, and a collection `Include` costs 5-6 times a reference include.** See the CI part 4 entry. The first is planned with wave 2's LINQ plan cache; profile the second before changing it.
- **`AccessReader.OpenAsync` reads the header and then page 0 again.** See the header-password entry. Not planned yet.

### Unchecked against Access
- **The library's Jet4 RC4 and ACCDB legacy-password schemes may not be what Access writes.** No Access-authored encrypted Jet4 or legacy-password file is among the fixtures: AesEncrypted.accdb, which the legacy-password scheme was built from, turned out to hold no password (see the header-password entry), and mdbtools and Jackcess describe Jet RC4 differently. The writer reads and writes these schemes consistently, but whether Access opens its files, or the writer opens Access's, is unchecked. It needs Access-authored encrypted fixtures or a DAO run. The README's Encryption Support section, its feature table and the `AccessEncryptionFormat` docs now say so: Jet4 RC4, the ACCDB legacy password and ACCDB AES-128 (CFB-wrapped) are the library's own schemes, Access may not open their output, and none of the encrypted formats has been checked against a file Access encrypted. They no longer name Access versions for these schemes or describe `;pwd=` as an Access format.
- **The rest of what only Access can confirm.** The 32 skip-guarded DAO tests cover writer attachments, Jet3 long rows and jump entries, calculated-column renames, the DropTable refusal and more, and none has run here. The writer's own format choices are unchecked too: Jet3 TDEF flags, page bytes 2..3 and trailer, the Jet4 and ACCDB parent-side FK entry and `RenameRelationshipAsync`'s naming (index page-run entry); Jet3 Currency descriptor bytes and the multi-value Decimal `Value` column's flags (decimal entry); the fixed area and trailer of short rows (Jet3 long-row entry); and page-0 bytes 0x600..0x7FF of new Jet3 files (header-password entry). Wave 2 asks for one full DAO run on a host with Microsoft Access before 4.0.0 ships; who provides the host is the one wave-2 decision left to the user.

## Design flaw status
| Flaw | Status | What changed |
|---|---|---|
| Facade is the engine / service locator | **Partly resolved** | Locator and cycles are gone. `DatabaseFile` (about 1,940 lines, injected into about 40 types) is the new catch-all: pager, transaction journal, encryption and table-definition parsing in one class. |
| Reader and writer are separate engines | **Resolved** | The writer no longer opens a second `AccessReader` over its own file. `TableSnapshotReader` decodes through the shared `RowDecoder`, `LongValueDecoder` and `CatalogReader` over the writer's own `DatabaseFile`, so its reads see the transaction journal (bugs 2 and 5–8 fixed). Each decoded row comes back with its location (`LocatedRow`), so nothing pairs rows and locations by position any more. |
| No pager or buffer manager | Open, critical | The cache moved into `ReaderPageCache`, and its eviction bug (bug 1) is now fixed, so table-scan read-ahead no longer needs a cache of at least three pages. There is now one journal-aware end of file, `DatabaseFile.PageCount`, used by every page-number bound and every caller that numbers new pages (see the end-of-file entry above). The writer still has no page cache, and there are no page leases or pins. |
| Transactions not atomic | Open, critical | Rollback no longer breaks the writer: it restores the cached catalog, insert hint and constraint registry (bugs 10–11 fixed). Cancellation can no longer tear a commit, a commit that fails after it started writing pages is no longer reported as rolled back, and the docs now say commit writes in-memory after-images in place, which is not crash-atomic. The format-byte bump is fixed (bug 3). The writer's own reads inside a transaction now see its pending writes (bugs 2 and 5–8). Still no WAL or before-image, so a crash or I/O failure during replay tears the file, and no savepoints. |
| Schema isn't a model | Open | Three duplicate parsers merged. The index paths now read the whole TDEF chain and share `IndexCatalogReader.LocateRealIdxDescStart` instead of their own column-name walks, and in-place TDEF patches go through `LogicalTDefChain.WriteInPlaceAsync` (the wide-table fixes above). Schema rewrites now copy each column whole (`ColumnDefinition.WithName`), project indexes through one `IndexHelpers.ProjectIndexes` that keeps every flag, carry the table's foreign-key indexes and partner links, and carry its persisted properties through `PersistedPropertyProjector`. `DropTableAsync` now refuses a table in a relationship and `RenameColumnAsync` rewrites the expressions that name the column (entries above), but there is still no in-process schema model. |
| No write pipeline or real B-tree | Open | Moved into `TableDataWriter`. Update and delete now change exactly the rows they decoded (`LocatedRow`), and updates run the NOT NULL, AutoNumber and rule checks on the columns they assign. Each operation still wires the insert, tombstone and index-maintenance primitives by hand, an update is still a delete plus re-insert, and the B-tree algorithms are unchanged apart from the multi-level rebuild reserving its pages through `PageAllocator` (end-of-file entry), every index path giving back a run it reserved but never linked, and a full single-leaf root growing into a tree instead of bailing (index page-run entry). |
| Constraints live in the process, not the file | **Partly resolved** | Every writer now loads the column `DefaultValue`, `ValidationRule` and `ValidationText` from `MSysObjects.LvProp` and enforces them, including those Access wrote, and a CLR `DefaultValue` applies after reopen. Inserts follow Access SQL for defaults: an explicit NULL stores NULL, and an omitted column or `DbDefault.Value` takes the default. A numeric CLR default, or one of the column's own type, stores the same value in every writer. Updates run the NOT NULL, AutoNumber and rule checks on the columns they assign (bug 4). A rollback restores the registry (bugs 10–11). AutoNumber seeding now reads the TDEF counter, so IDs are no longer reused across sessions or schema rewrites. Still open: a CLR `ValidationRule` delegate binds only the writer that declared it; expressions the calculated-column engine can't evaluate and table-level rules are skipped; and the registry still skips every check on a table whose constraint list doesn't line up with the TDEF column count. |
| Lossy value model | Open | Complex-column cells are no longer lossy: `Rows()` and the other row reads return every attachment, decoded, and every multi-value item, and version-history cells carry their `Modified` timestamps (see "Fixed since 6eab703"). Updates, cascades and schema rewrites no longer lose data either: the writer's snapshot carries OLE bytes exactly and refuses a MEMO or OLE value it cannot read instead of storing placeholder text. A table's persisted properties are read as the stored bytes of its own `MSysObjects` row, matched by the whole Id, and schema rewrites keep every property. Every read API now returns OLE values as their stored bytes, and the new public `OleObjectValue` unwraps them on request. Unreadable MEMO and OLE values still read as placeholders on the public read path. |
| Format knowledge scattered | Open | The TDEF header offsets (row count, AutoNumber counter, table type, column and index counts, usage-map pointers, and now the complex AutoNumber) live per format in `TDefHeaderLayout`, and the Jet4-only constants that corrupted Jet3 headers are gone. LVAL pages follow a per-format `LvalPageLayout`, which fixed Jet3 long values. The foreign-key index helpers read and write real-index descriptors, logical entries and name records through the per-format `IndexLayout` instead of Jet4's hard-coded offsets, which let the writer emit Jet3 foreign-key entries (index page-run entry). Elsewhere no change: files importing `JetTypeInfo` went from 35 to 40 in the five commits and are 42 now. |
| Read API doesn't compose | Open | Moved into `TableReader`. The read loops now agree on which rows they return, on `maxRows` and on calculated-column types (bug 12 and the drift fix above), but they are still separate loops with no shared scan primitive. `IndexRowReader` still returns nothing for linked tables (`ListIndexesAsync`, `EnumerateIndexRowsAsync`), `CatalogReader.ResolveTableAsync` still re-reads the TDEF uncached and rescans MSysObjects (for a system table, now through `CatalogRowReader`, which decodes every catalog row; see the overflow-row entry's performance follow-up), and unknown tables still read as empty, unlike the writer. |
| Encryption isn't a page layer | Open | Opening a file now reads only page 0 to detect flat Agile, and the writer refuses flat Agile instead of corrupting it. A path writer open opens the file once and reads page 0 once, detection reads the unmasked header password instead of a raw byte, and `DecryptAsync` leaves Access's unencrypted header. The cached AES page transforms now run under their own lock, so concurrent page reads on an AES file no longer fail. Six frozen library-encrypted fixtures under `Databases/Encrypted/` and `EncryptedGoldenFixtureTests` now pin, for every format the reader opens (Jet3 XOR built from Jet3Test.mdb), the plaintext `ReadDecryptedAsync` returns, every decrypted page, the rows and the detected format, so the page-codec and container work that follows can show it changes no byte. Checking an Agile password (flat or CFB) now runs one PBKDF chain instead of three, through one reused `IncrementalHash`: a reader open of the frozen 172 KB Agile fixtures fell from about 153 ms to about 38 ms on .NET 10 and from about 197 ms to about 37 ms on the netstandard2.1 build. Encrypting, decrypting or changing a password by path now flushes the new file and renames it over the database, and refuses with the database unchanged when the rename is blocked, instead of deleting the database first (see the path re-encryption entry). Flat Agile and the CFB Office Crypto formats are still decrypted whole into memory, and the writer still has no page cipher for flat Agile. |
| Failures aren't modeled | Open | `LastDiagnostics` is now built from a typed record internally. Index paths that silently skipped an index they could not parse now throw `JetLimitationException`, a MEMO or OLE value the writer cannot read refuses the write (`InvalidDataException`) instead of storing placeholder text, and a commit that fails after it starts writing is reported as neither committed nor rolled back. `JetLimitationException` is still the only custom exception type. |
| No CI; untested netstandard2.1 build | **Resolved** | `ci.yml` builds the solution in Release with every analyzer as an error and runs the suite on net10.0 and on net8.0, which loads the netstandard2.1 build, on every push to main and every pull request. A release tag publishes the package that run built and tested, versioned from the tag by MinVer, with package validation (CI parts 1–4). CI runs on Windows only. |
| LINQ layer has no mapping model | **Partly resolved** | It depends on reader services instead of the facade, which makes a package split easier. `EntityMap` is now the one mapping model: every typed path maps properties to columns through it, honouring `[Column]`, `[NotMapped]` and `[Table]`. There is still no query plan: reads compile materializers per call, `RowMapper` and `RuntimeRowMapper` coerce values differently, the IQueryable surface runs sync-over-async, the index walk builds a `List` instead of streaming, and nothing is annotated for AOT. |

## Suggested next steps
Wave 1 is done, and so is wave 2's encryption-prep (see the intro). What remains, ordered by risk, data loss first. The wave-2 roadmap, `scratchpad\plans\_wave2-roadmap.md`, merges the plans for the open design flaws into 35 packages in 17 stages; the package names here and under "Open: found while fixing" are its names.
1. **Stop the writer losing data (wave 2).** Each open bug that loses rows, properties or consistency is planned:
   - an update whose re-insert fails, and a key update refused after an earlier cascade: atomicity-b makes every call statement-atomic, write-pipeline-c updates rows in place, and write-pipeline-a1 plans every cascade before writing;
   - updates and deletes on wide tables from earlier builds that apply and then throw: index-preflight (stage 1);
   - a torn file after a crash or an I/O failure during commit, the "Transactions not atomic" design flaw: savepoints, commit undo, and a sidecar rollback journal, on by default for path-opened files, with recovery when the file is opened (atomicity-a, atomicity-b and crash-journal).
2. **Close the referential-integrity gaps.** Cascade updates through several levels are planned (write-pipeline-a1). The self-referencing delete that counts a row twice, a referenced non-key column set to Null, `CreateRelationshipAsync` over orphaned rows and the POCO `int` AutoNumber are not planned yet; the first three belong with write-pipeline-a1's cascade plan.
3. **Stop storing or reading values wrong without an error.** Jet3 LvProp text gets the database's code page in format-profile-b, which should also refuse a character the code page lacks, as names and values do. A string into a Binary column, the silently skipped overflow row and fixed-length Text read as Null are not planned yet.
4. **Close the remaining design flaws (wave 2).** The plans for the twelve open rows of the table above start with splitting `DatabaseFile` and a real pager, which also writes REFERENCE usage maps for large tables and large indexes (the index rebuild that throws, the incomplete owned map and the whole-file reads). Then come write atomicity (item 1), the schema model, the write pipeline and a real B-tree (several Null keys in a unique index, freed index trees), read composition (the catalog-lookup cost), encryption as a page layer, typed failures, the format profile and the LINQ query plan.
5. **Fix the writes that are refused or left half done, outside wave 2**: schema changes on Access tables with a complex column, whose properties a rewrite now keeps; the inline long-value budget; case-only column renames; the flat tables a drop leaves allocated; `AddAttachmentAsync`'s per-call index rebuild, unless write-pipeline-a2's single write path removes it; the two `CreateTableAsync` refusals that come after its first write; and the `*.reenc-*.tmp` file a crash during re-encryption by path leaves.
6. **Smaller fixes**: the default, expression, complex-column, naming, table-property rename, encryption-detection, documentation and tooling items under "Values that differ from Access or between writers", and the reader's second header read. Two tidy-ups go with them: `SchemaEvolutionTests.RenameColumnAsync_ChangesOnlyTheColumnName` can give Jet3 its Decimal(10,2) column and the `Description` and `DefaultValueExpression` on its Name column again (decimal entry), and the 20 line-number links in `concurrency-and-lock-ordering.md` are stale (`DatabaseFile.cs#L190` for `IoGate`, which is now at line 223, for example).
7. **Settle the open design questions, which are the user's call**: whether a plain `typeof(decimal)` column on Jet3 should become Currency (decimal entry), whether the scaffolder qualifies its type names with `global::` (object-name and scaffolder entry), and whether `InsertRowAsync<T>` ignores or rejects a complex cell (complex-columns entry).
8. **Before 4.0.0 ships**:
   - run the full DAO suite, wave 2's skip-guarded tests included, on a host with Microsoft Access, and record the result; it also decides whether `CreateDatabaseAsync` must write the standard system rows, and wave 2 waits on it before letting tables in a relationship leave the full index rebuild they take on every write;
   - re-run the reader benchmarks on x64, a hard disk, an SMB share, Linux and macOS (page-read entry);
   - once 4.0.0 is on nuget.org, set `PackageValidationBaselineVersion` (CI part 4 entry).

The per-claim results, with current file:line evidence and fix notes for all 14 flaws, are in `scratchpad\recheck.json` and `scratchpad\recheck-digest.md`.
